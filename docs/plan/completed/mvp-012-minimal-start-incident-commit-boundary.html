MVP-012 - Minimal Start Incident Commit Boundary

Status: implemented and merged via PR #13; parser coverage follow-up merged via PR #14

Created: 2026-05-19. Completed slice path: docs/plan/completed/mvp-012-minimal-start-incident-commit-boundary.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-012-functional-spec. Merged commit: ef9c862. Parser coverage follow-up commit: 7888e0a.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, and 08 - Runtime Logging & Trace.

Phase 3 eventually needs a Basic Incident System, but MVP-012 should not implement the whole lifecycle. It proves only one write-side action: an opted-in USER_MESSAGE turn may commit a model-proposed start_incident through an injected Commit and Effects boundary.

Local implementation truth comes from completed MVP-001, MVP-002, MVP-003, MVP-004, MVP-005, MVP-006, MVP-007, MVP-008, MVP-009, MVP-010, and MVP-011.

Goal

Add the smallest incident write path after the read-only active incident context: parse one optional life_action.start_incident from a role-model decision and commit one active incident plus its raw audit log through an injected fake finalizer. Preserve the existing visible reply flow when no incident action is proposed.

Current Scope

  • One event type remains in scope: USER_MESSAGE.
  • One optional model decision field is in scope: life_action.
  • One life action type is in scope: start_incident.
  • The required top-level decision action remains visible_reply; life_action is only an optional sibling when explicitly enabled.
  • The Role Model Loop may include life_action in allowed_actions only when the caller opts into MVP-012 incident-start behavior.
  • The incident commit path uses an injected fake LifeIncidentStartFinalizer that durably exposes the started incident and matching life_incident_started RawEventLogEntry atomically.
  • If no life_action is present, the user turn skips incident commit and continues to the existing assistant visible reply commit.
  • MVP-012 does not compose incident starts with living-state patches in the same turn. A later reviewed slice may define that ordering.

Explicit Non-Goals

  • No concrete LifeIncidentStore, database, migration, filesystem store, queue, background worker, scheduler, replay worker, or production persistence adapter.
  • No complete_incident, cancel_incident, resume_incident, go_idle, no_change, replacement, interruption, backgrounding, deduplication, reconciliation, or incident queue behavior.
  • No INCIDENT_COMPLETION, TIMER, NEED_THRESHOLD, scheduled directive, tool result, asset result, or maintenance event type.
  • No concrete active-incident conflict resolution. The injected finalizer may reject an attempted start, but MVP-012 does not decide how to replace, interrupt, or cancel an existing incident.
  • No body effects, virtual body drift, Live2D status, asset lookup, proactive message, retrieval, continuity write, active thread, scheduled directive, productivity tool, or permission matrix.
  • No live model provider and no external service calls.
  • No Runtime Kernel route, priority, scheduling, or interruption policy changes.
  • No durable state mutation outside the injected incident-start finalizer.

Minimal Schema

CharacterDecision Addition

type CharacterDecision = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  action: "visible_reply"
  visible_reply: { text: string }
  life_action?: StartIncidentLifeAction
}

StartIncidentLifeAction

type StartIncidentLifeAction = {
  type: "start_incident"
  incident: LifeIncidentStartDraft
}

LifeIncidentStartDraft

type LifeIncidentStartDraft = {
  type: "idle" | "eat" | "drink" | "sleep" | "rest" | "work" | "think" | "wait" | "custom"
  title: string
  remaining_seconds?: number
  interrupt_policy: "interruptible" | "background" | "protected"
  resume_policy: "resume" | "ask_model" | "cancel"
}

The model does not provide incident_id, status, started_at, expected_end_at, source_event_ids, effects, or Live2D hints in MVP-012. The runtime and injected finalizer own committed identity, timestamps, and audit visibility.

LifeIncidentStartFinalizeRequest

type LifeIncidentStartFinalizeRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  life_action_type: "start_incident"
  commit_time: string
  draft: LifeIncidentStartDraft
  started_incident: ActiveIncidentSnapshot
  committed_log_entry: RawEventLogEntry
  user_id?: string
  conversation_id?: string
}

LifeIncidentStartCommitResult

type LifeIncidentStartCommitResult =
  | {
      schema_version: "0.1"
      trace_id: string
      event_id: string
      event_type: "USER_MESSAGE"
      status: "life_incident_start_skipped"
    }
  | {
      schema_version: "0.1"
      trace_id: string
      event_id: string
      event_type: "USER_MESSAGE"
      status: "life_incident_started"
      started_incident: ActiveIncidentSnapshot
      committed_log_entry_id: string
    }
  | {
      schema_version: "0.1"
      trace_id: string
      event_id: string
      event_type: "USER_MESSAGE"
      status: "life_incident_start_rejected"
      failure: { stage: string; code: string; message: string }
    }

Functional Requirements

ID Requirement
FR-1 Without explicit incident-start opt-in, existing MVP-011 behavior and tests remain unchanged, and allowed_actions must not include life_action.
FR-2 With incident-start opt-in, Role Model Loop renders allowed_actions = ["visible_reply", "life_action"] and instructions that permit only optional life_action.type = "start_incident", including the allowed incident.type, interrupt_policy, and resume_policy enum values enforced by the parser.
FR-3 Incident-start opt-in and living-state patch opt-in are mutually exclusive in MVP-012; asking for both must return a structured user-turn preflight stop before user-visible message commit or adapter invocation.
FR-4 Parsing accepts a valid visible reply with no life_action and returns the same visible-reply decision shape as today.
FR-5 Parsing accepts a valid life_action.start_incident sibling and attaches trusted trace_id and event_id from the model input.
FR-6 Parsing rejects unsupported life action types, extra fields, missing incident draft fields, unsupported incident types or policies, empty titles, non-numeric or negative remaining_seconds, and any model-provided committed-only fields such as incident_id, status, started_at, source_event_ids, effects, or Live2D hints.
FR-7 A malformed life_action output appends the existing role_model_turn_failed raw log with stage = "parse_output" and must not append incident commit or visible reply commit logs.
FR-8 If a parsed decision has no life_action, Commit and Effects returns life_incident_start_skipped without calling the incident finalizer and the user turn proceeds to assistant visible reply commit.
FR-9 If a parsed decision has start_incident, Commit and Effects builds a started active incident snapshot with runtime-generated incident_id, status = "active", started_at = commit_time, and source_event_ids = [event_id], then validates that snapshot through character.state.current.validate_active_incident_snapshot().
FR-10 The successful incident-start path builds a life_incident_started RawEventLogEntry and passes both the started incident and that log entry to the injected finalizer for atomic durable visibility instead of using the ordinary raw_event_log.append() path.
FR-11 If the injected finalizer rejects the start or returns a malformed result, Commit and Effects appends life_incident_start_rejected, returns life_incident_start_rejected, and user-turn orchestration stops before assistant visible reply commit. The already committed user visible message and role-model turn log remain intact.
FR-12 User-turn orchestration wires the optional incident-start finalizer through after the role-model turn and before assistant visible reply commit, without changing Runtime Kernel intake, recent-message projection, active-incident context reading, or visible reply commit validation.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Use fakes for the incident finalizer, raw log, visible conversation, role-model adapter, clock, and IDs.
  • Reuse existing active-incident validation from character.state.current. The committed started incident snapshot must pass validate_active_incident_snapshot(); do not duplicate the type, policy, timestamp, remaining-seconds, or source-ID checks in the incident-start commit path.
  • Reuse or extend the existing visible-reply decision normalizers in runtime.contracts for the base schema_version, action, and visible_reply checks. The new life-action parser must add only the optional life_action.start_incident validation instead of revalidating the visible-reply decision shape separately inside Role Model Loop.
  • Reuse runtime.contracts.normalize_role_model_turn_result() for commit-boundary result validation.
  • Deep-copy model decisions, drafts, started incident snapshots, finalize requests, raw logs, and returned results so caller mutation cannot alter audit data.
  • Keep Runtime Kernel and Character State Engine read behavior unchanged.
  • Keep the user turn ordering explicit: user visible message commit, role model turn, optional incident start commit, assistant visible reply commit.
  • Do not add a general incident package or store abstraction beyond the one finalizer protocol needed by this slice.

Acceptance Criteria

  • Existing MVP-001 through MVP-011 tests continue to pass.
  • A default user turn still renders no life_action allowed action and commits the visible reply as before.
  • An incident-start-enabled user turn renders life_action as an allowed action and accepts one valid start_incident decision.
  • A valid start_incident decision commits one active incident and one matching life_incident_started raw log through the injected finalizer before the assistant reply is committed.
  • A valid decision with no life_action skips the incident finalizer and preserves the existing visible reply flow.
  • If living-state patch and incident-start write dependencies are both wired, the user turn returns user_turn_stopped at user_turn_preflight after intake and before any visible conversation append, model call, write commit, or assistant reply commit.
  • Malformed life action output fails before incident commit and visible reply commit.
  • Finalizer rejection or malformed finalizer output appends a life_incident_start_rejected raw log and stops before assistant visible reply commit.
  • No concrete incident store, complete/cancel/resume action, interruption policy, new RuntimeEvent type, body state, retrieval, tool, Live2D, scheduler, provider call, or additional model action is added.
  • The development journal records source context, files touched, checks run, review notes, and next action.
  • Future ideas discovered during planning are recorded in future-slices.html.

Implementation Boundaries

  • Runtime Kernel remains unchanged.
  • Character State Engine remains read-only in this slice; it only supplies reusable incident constants and the already implemented active-incident context shape.
  • Role Model Loop owns rendering the opt-in allowed action, parsing optional life_action.start_incident, and logging malformed model output through existing role-model failure logs.
  • Commit and Effects owns incident-start validation, started incident snapshot construction, commit/reject raw log construction, and finalizer result validation.
  • User-turn orchestration owns opt-in wiring, rejects mutually enabled write action families before user-visible message commit, and stops before assistant visible reply if incident start commit rejects.
  • Raw Event Log behavior changes only by adding the incident-start commit/reject raw log kinds needed for this write boundary.

Implementation Results

  • Added shared incident constants and normalize_start_incident_life_action() in runtime.contracts, while keeping the base visible-reply decision validation shared with prior slices.
  • Reused the shared incident type, policy, and remaining_seconds validators from runtime.contracts inside character.state.current so active-incident read validation and start-draft validation cannot drift.
  • Extended Role Model Loop with explicit allow_incident_start opt-in, ["visible_reply", "life_action"] allowed actions, incident-start instructions that enumerate the parser-enforced incident type and policy values, and malformed life_action parse failures through the existing role_model_turn_failed raw log.
  • Added commit_effects.incident_start as the narrow Commit and Effects boundary for building runtime-owned active incident snapshots, constructing life_incident_started success RawEventLogEntry records, validating finalizer success, and appending life_incident_start_rejected logs on rejection.
  • Wired run_user_message_turn() so an injected LifeIncidentStartFinalizer opts into the incident-start path after the role-model turn and before assistant visible reply commit.
  • Kept living-state patch and incident-start composition rejected for MVP-012; the user turn can opt into one write-side model action family at a time, and the mutually enabled configuration now stops during preflight before user-visible message commit.
  • Added focused unit and integration coverage for parsing, malformed drafts, allowed-action scoping, atomic finalizer success, finalizer rejection, skipped starts, deep-copy audit data, and user-turn ordering.

Review Notes

  • MVP-012 is the incident equivalent of the first living-state write slice, but narrower: start only, no complete/cancel/resume, and no composition with state patches yet.
  • The model proposes a draft; the runtime generates committed identity, timestamps, status, and source IDs.
  • The finalizer is the only boundary allowed to durably expose a started incident and its matching life_incident_started RawEventLogEntry; success logs are not appended through ordinary raw_event_log.append(). A malformed success result must mean no durable incident/log visibility occurred.
  • If implementation pressure suggests concrete storage, interruption, body effects, Live2D, or completion events, park those as future slices.

Open Questions

  • Should later incident starts require an active-incident source that proves no current active incident exists, or should the concrete store own that conflict check? Not in MVP-012.
  • Should remaining_seconds become expected_end_at at commit time or stay as a duration hint until a scheduler slice exists? MVP-012 records only the minimal fields tests require.
  • Should a future slice allow state_patch and life_action in the same decision? Not until ordering and rejection behavior are specified.
