MVP-006 - Visible Conversation Recent Source

Status: completed and recorded

Created: 2026-05-16. Implemented: 2026-05-16. Completed archive path: docs/plan/completed/mvp-006-visible-conversation-recent-source.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages checked for this slice are 02 - Runtime Architecture, 06 - Character State Engine & Retrieval Management, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Phase 1 calls for a minimal user turn loop where recent visible messages feed DecisionContext, the Role Model Loop calls the model, Commit and Effects stores the visible reply, and Raw Event Log records the turn.

Local implementation truth comes from MVP-001, MVP-002, MVP-003, MVP-004, and MVP-005. MVP-004 defined the read-side RecentVisibleMessage contract through an injected source. MVP-005 added committed user visible records. The narrow next step is to map committed visible conversation records into the existing recent-message source contract without adding storage or orchestration.

Goal

Add the smallest read-side bridge from already committed visible conversation records to the MVP-004 RecentVisibleMessage shape. MVP-006 should implement an injected, read-only source adapter that can supply recent user and assistant visible records to the existing Role Model Loop context builder. This slice must not add a concrete database, full user-turn orchestrator, new runtime event type, model provider, retrieval index, character state, or new visible-message write behavior.

Current Scope

  • One existing read contract: RecentVisibleMessagesSource.read_recent_visible_messages().
  • One new injected provider boundary: read committed visible conversation records for one conversation before the current event.
  • Two supported committed visible record kinds: user_visible_message from MVP-005 and assistant_visible_reply from MVP-003.
  • One mapping target: the existing MVP-004 RecentVisibleMessage shape.
  • Extra fields from committed visible records, including kind, source, user_id, and output_id, are not exposed in DecisionContext.
  • The existing Role Model Loop remains responsible for final recent-message validation, ordering, current-event exclusion, and budget selection.
  • The new adapter copies input and output snapshots so caller mutation cannot alter returned context records.
  • The adapter may live near the existing Role Model Loop source protocol for now; do not create a full Character State Engine package in this slice.
  • Focused tests cover mapping, validation failures, copy isolation, and integration with build_decision_context().

Explicit Non-Goals

  • No concrete ConversationLog storage adapter, file store, database, migration, transaction, index, or pagination API.
  • No writes to visible conversation records, raw logs, model I/O logs, state stores, or any external service.
  • No full user-turn orchestrator across Runtime Kernel, user projection, Role Model Loop, and assistant commit.
  • No change to MVP-001 event normalization, MVP-002 model adapter contract, MVP-003 assistant visible-reply commit behavior, MVP-004 context budget rules, or MVP-005 user projection behavior.
  • No new model actions, live provider calls, prompt semantics, streaming, retries, or provider configuration.
  • No retrieval index, embeddings, keyword search, summaries, compaction, replay UI, or exact source expansion.
  • No CharacterRuntimeState, living state, virtual body, incidents, scheduled directives, active threads, tools, Live2D, assets, permissions matrix, or confirmation policy.
  • No schema unification of user and assistant visible records beyond a read-side projection into RecentVisibleMessage.
  • No reconciliation for visible append failures and no idempotency policy for persistent stores.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-006 should implement the contract in Python 3 and test it with unittest.

VisibleConversationRecordsRequest

type VisibleConversationRecordsRequest = {
  schema_version: "0.1"
  conversation_id: string
  before_event_id: string
  before_created_at: string
  max_candidate_records: 24
}

VisibleConversationRecordSource

interface VisibleConversationRecordSource {
  read_visible_conversation_records(
    request: VisibleConversationRecordsRequest
  ): VisibleConversationRecord[]
}

The source is injected and read-only. A test fake may return in-memory records. Concrete storage remains a future slice.

UserVisibleMessage Input

type UserVisibleMessage = {
  schema_version: "0.1"
  message_id: string
  trace_id: string
  source_event_id: string
  kind: "user_visible_message"
  role: "user"
  conversation_id: string
  created_at: string
  text: string
  source: { runtime_event_type: "USER_MESSAGE" }
  user_id?: string
}

AssistantVisibleReply Input

type AssistantVisibleReply = {
  schema_version: "0.1"
  output_id: string
  trace_id: string
  source_event_id: string
  kind: "assistant_visible_reply"
  conversation_id: string
  created_at: string
  text: string
  source: {
    decision_action: "visible_reply"
    role_model_status: "decision_ready_for_commit"
  }
  user_id?: string
}

RecentVisibleMessage Output

type RecentVisibleMessage = {
  schema_version: "0.1"
  message_id: string
  trace_id: string
  source_event_id: string
  conversation_id: string
  role: "user" | "assistant"
  created_at: string
  text: string
}

User records copy message_id. Assistant records map output_id to message_id and set role to assistant. No other committed-record fields pass through to model context.

Functional Requirements

ID Requirement
FR-1 The adapter accepts the existing MVP-004 RecentVisibleMessagesRequest shape and validates schema_version, conversation_id, before_event_id, before_created_at, and max_candidate_messages.
FR-2 For a valid request, the adapter calls the injected visible-record source exactly once with the same conversation, event, timestamp, and candidate limit.
FR-3 The injected visible-record source must return a list. Non-list results fail before any model input is rendered.
FR-4 A user_visible_message record maps to RecentVisibleMessage with the same message_id, trace_id, source_event_id, conversation_id, created_at, and text, plus role = "user".
FR-5 An assistant_visible_reply record maps to RecentVisibleMessage with output_id as message_id, the same trace_id, source_event_id, conversation_id, created_at, and text, plus role = "assistant".
FR-6 The adapter rejects unsupported kind values, missing required identity fields, wrong schema_version, missing or mismatched conversation_id, malformed timestamps, and empty text.
FR-7 The adapter returns only the MVP-004 RecentVisibleMessage fields and strips committed-record implementation fields.
FR-8 The adapter deep-copies the request sent to the source and the records it returns to callers.
FR-9 When used with build_decision_context(), the existing Role Model Loop budget and ordering rules still determine the final recent_visible_messages list.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep runtime behavior deterministic and side-effect free.
  • Do not call clocks, ID generators, model providers, files, databases, network services, or shell commands from the adapter.
  • Keep validation errors explicit enough to identify the bad record or request shape in tests.
  • Keep implementation small and local; no broad refactor of Role Model Loop or Commit and Effects.

Acceptance Criteria

  • A valid mixed list of committed user and assistant visible records becomes valid recent_visible_messages in DecisionContext.
  • User records map by message_id; assistant records map by output_id.
  • The returned messages expose no kind, source, user_id, or output_id.
  • The injected visible-record source is called once with a copied request and the existing candidate limit.
  • Malformed request or malformed visible record fails with no fallback records.
  • Existing MVP-001 through MVP-005 tests pass without behavior changes.
  • Future ideas discovered during planning are recorded in future-slices.html.
  • The development journal records files touched, tests run, review notes, and next action.

Test Plan

Unit Tests

  • Maps one user_visible_message to the exact RecentVisibleMessage output shape.
  • Maps one assistant_visible_reply using output_id as message_id and role = "assistant".
  • Strips implementation-only fields from returned recent messages.
  • Rejects unsupported record kind, missing required ID, wrong schema version, mismatched conversation, malformed timestamp, and empty text.
  • Rejects a non-list result from the injected visible-record source.
  • Copies request and result snapshots so source-side or caller-side mutation cannot change returned records.

Integration Tests

  • build_decision_context() with the new adapter includes mapped user and assistant records in character_snapshot.recent_visible_messages.
  • run_role_model_turn() snapshots the rendered model input with mapped recent messages in the completed role-model raw log.
  • Existing recent-message ordering, current-event exclusion, duplicate detection, and budget tests continue to pass through the Role Model Loop.

Implementation Boundaries

  • The read adapter satisfies the existing RecentVisibleMessagesSource protocol.
  • The injected visible-record provider is read-only and has no append, update, delete, or transaction behavior.
  • Role Model Loop remains the only model-call boundary and still owns rendering and parsing.
  • Commit and Effects remains the only write-side visible transcript boundary.
  • Runtime Kernel remains unchanged.
  • Character State Engine extraction remains future work; this slice should not introduce broad state, incident, retrieval, or continuity modules.
  • Reuse existing validation helpers and constants where possible instead of retyping schema, timestamp, text, identity, or extra-key checks. In particular, prefer the shared runtime.contracts helpers such as reject_extra_keys, require_equal, require_string, and validate_iso8601_timestamp, plus existing Role Model Loop constants such as RECENT_VISIBLE_MESSAGES_MAX_CANDIDATES. Because _validate_recent_visible_message() is currently private in role_model.loop, the implementation must either keep the adapter close to that module or extract the smallest shared helper. Do not call or copy that private validator from another module.

Error And Fallback Behavior

  • Malformed adapter request raises a validation error before reading visible records.
  • Malformed visible source output raises a validation error before model input rendering.
  • Unsupported visible record kinds fail closed instead of being silently ignored.
  • No raw log is appended for source-read failures in this slice because context-build logging is still a future slice.
  • No user-visible fallback message is emitted by this adapter.

Review Notes

  • This spec intentionally chooses the read-side projection before the full user-turn orchestrator because MVP-004 and MVP-005 already define the two sides that need to connect.
  • The adapter maps committed record shapes into the existing recent-message shape rather than widening DecisionContext.
  • A concrete store would force persistence, ordering, and idempotency choices that are not needed to prove the mapping contract.
  • Do not hide ordering or budget policy in the adapter; keep those rules in the existing Role Model Loop path until a reviewed Character State Engine slice moves them.
  • Implementation should reuse or extract existing validators/constants for the overlapping RecentVisibleMessage and shared contract checks; duplicated timestamp, schema, empty-text, and extra-key validation would be review debt.
  • Residual implementation risk: _validate_recent_visible_message() is private today. MVP-006 should avoid cross-module private-helper coupling by colocating the adapter with the private validator or extracting a deliberately shared helper.

Open Questions

  • Should this adapter later move into a dedicated Character State Engine package? Likely yes, but not until a broader context-builder slice exists.
  • Should malformed historical visible records be skipped instead of failing the context build? MVP-006 should fail closed so bad committed records are visible during tests.
  • Should assistant and user visible records later share one durable schema? Not in MVP-006; this slice only maps both into the read-side context schema.

Future Ideas Discovered During Planning

  • Concrete append-only ConversationLog storage with durable query semantics.
  • Full user-turn orchestrator after the visible recent source is proven.
  • Character State Engine context-builder extraction once there is more than one real context source.
  • Context-build raw logging that records source-read requests and selected message IDs.
  • Shared durable visible conversation message contract if storage or replay needs it.
