MVP-017 - Minimal Cancel Active Incident Commit Boundary v0.1

Status: implemented and merged; PR #20

Created: 2026-05-22. Completed slice path: docs/plan/completed/mvp-017-minimal-cancel-active-incident-commit-boundary.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-017-minimal-cancel-incident-commit. PR: #20.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 09 - MVP Roadmap & Open Questions.

Notion defines Commit & Effects as the only boundary that validates and commits durable incident transitions. It also lists life_action.cancel_incident as a model-proposed action and LifeIncidentStore as the durable incident lifecycle truth. MVP-017 promotes only the smallest cancel transition for the currently active incident.

Local implementation truth comes from completed MVP-011, MVP-012, MVP-013, MVP-014, MVP-015, and MVP-016.

Goal

Let an opted-in USER_MESSAGE turn cancel the currently active incident through Commit & Effects and the InMemoryLifeIncidentStore, expose a query-visible life_incident_cancelled raw log entry, and add no other incident lifecycle behavior.

Current Scope

  • One event family remains in scope: USER_MESSAGE.
  • One new model-proposed life action subtype is in scope: cancel_incident.
  • The turn must opt in to incident cancellation explicitly; default visible-reply turns keep the MVP-016 allowed action set and parser behavior.
  • Cancellation applies only to the active incident for the validated user/conversation scope derived from the source event.
  • The cancel action must identify the active incident by incident_id and include a non-empty model-provided reason.
  • Commit & Effects validates the role-model result, validates the current active incident, builds the cancellation log entry, and finalizes cancellation through the store.
  • InMemoryLifeIncidentStore remains the concrete in-memory incident boundary and must make read_active_incident(request) return None for the cancelled scope after success.
  • The successful cancellation raw log must be visible through the existing Raw Event Log query/debug surface.

Explicit Non-Goals

  • No complete_incident, resume_incident, go_idle, no_change, interruption policy, background incident behavior, replacement behavior, incident queue, or incident completion event.
  • No new RuntimeEvent family, route policy, scheduler, timer, body effect, Live2D status, tool request, retrieval/indexing behavior, database storage, migration, debug UI, or replay execution.
  • No composition of incident cancel with state patches or incident start in the same model-call contract.
  • No default cancellation wiring in ordinary user turns; callers must opt in and provide the concrete cancellation boundary.
  • No changes to the MVP-016 RoleModelInputEnvelope split except the minimum allowed-action subtype marker and instruction text needed for the cancel opt-in.
  • No history query API in InMemoryLifeIncidentStore; the raw log is the truth for the cancelled transition in this slice.

Minimal Schema

CharacterDecision Extension

type CharacterDecision = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  action: "visible_reply"
  visible_reply: { text: string }
  life_action?: {
    type: "cancel_incident"
    incident_id: string
    reason: string
  }
}

The action stays a visible-reply turn with an optional life action, matching the MVP-012 incident-start pattern. The allowed life-action subtype is selected by the caller's explicit cancel opt-in.

LifeIncidentCancelCommitRequest

type LifeIncidentCancelCommitRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  life_action_type: "cancel_incident"
  incident_id: string
  reason: string
  user_id?: string
  conversation_id?: string
}

LifeIncidentCancelFinalizeRequest

type LifeIncidentCancelFinalizeRequest = LifeIncidentCancelCommitRequest & {
  commit_time: string
  active_incident: ActiveIncidentSnapshot
  cancelled_incident: {
    schema_version: "0.1"
    incident_id: string
    type: string
    status: "cancelled"
    title: string
    started_at?: string
    expected_end_at?: string
    remaining_seconds?: number
    interrupt_policy: "interruptible" | "background" | "protected"
    resume_policy: "resume" | "ask_model" | "cancel"
    cancelled_at: string
    cancellation_reason: string
    source_event_ids: string[]
  }
  committed_log_entry: RawEventLogEntry<"life_incident_cancelled">
}

cancelled_incident.source_event_ids should preserve the active incident's source IDs and append the cancelling event_id once. The existing active-incident read validator remains active-only; a cancelled snapshot is only a commit/log artifact in this slice.

Functional Requirements

ID Requirement
FR-1 Add a shared CANCEL_INCIDENT_ACTION = "cancel_incident" contract constant and a narrow normalizer for life_action.cancel_incident that requires only type, incident_id, and non-empty reason.
FR-2 Extend or extract Role Model Loop's existing allow_incident_start life-action opt-in path into a subtype-specific start-vs-cancel selection path so a caller may allow incident start or incident cancel, but never both and never alongside state patch in this slice. Do not copy a parallel parser path.
FR-3 Render cancel-specific instructions only for the cancel opt-in, while reusing the existing LIFE_ACTION allowed-action envelope and carrying one explicit allowed_life_action_type marker so direct Role Model input validation cannot swap start-vs-cancel parsing by changing only instructions.
FR-4 When cancel is not opted in, reject life_action.cancel_incident before commit through the existing role-model parsing/validation failure path.
FR-5 Add a new commit_effects.incident_cancel boundary that builds a cancel commit request from a normalized USER_MESSAGE event and role-model result, returning skipped when the decision has no life action.
FR-6 The cancel commit boundary must read/validate the active incident for the source-event scope before finalizing, reject if there is no active incident, and reject if the requested incident_id does not match the current active incident.
FR-7 On success, Commit & Effects builds one life_incident_cancelled raw log entry and finalizes cancellation through the injected finalizer/store before the assistant visible reply is committed.
FR-8 InMemoryLifeIncidentStore must implement the cancel finalization boundary, add life_incident_cancelled to runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, stage the success log through the existing expose_committed_success_entry() helper, clear only the matching active incident scope after Commit & Effects confirms raw-log visibility, and return copy-safe results.
FR-9 After a successful cancel, read_active_incident(request) for the same scope returns None; other identified scopes remain unchanged.
FR-10 If finalization fails, raw-log success visibility staging fails, post-confirm incident-clearing completion fails or observes a changed active incident, the store/log instances differ, no active incident exists, incident IDs mismatch, or a storage/source adapter raises unexpectedly, Commit & Effects returns a structured rejected result and appends a life_incident_cancel_rejected log through the ordinary raw-log path. Failures before visibility confirmation must leave the active incident unchanged and no query-visible cancel success entry. Failures after visibility confirmation intentionally leave the already-confirmed life_incident_cancelled entry query-visible and add a later life_incident_cancel_rejected audit entry, producing a success-plus-rejection audit pair for post-confirm completion failures.
FR-11 The successful life_incident_cancelled entry must be visible through raw_event_log.query() and must agree with the commit result on trace ID, event ID, incident ID, cancellation time, reason, and committed log entry ID.
FR-12 The implementation must reuse, move, extract, or compatibility-export existing shared code surfaces instead of duplicating them: runtime.contracts.validate_normalized_user_message_event(), normalize_role_model_turn_result(), normalize_start_incident_life_action() or a shared subtype-specific extraction from it, VISIBLE_REPLY_ACTION, LIFE_ACTION, START_INCIDENT_ACTION, character.state.current.build_active_incident_request(), validate_active_incident_request(), validate_active_incident_snapshot(), runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, runtime.logging.confirm_committed_success_entry_visibility(), runtime.logging.discard_committed_success_entry_visibility(), InMemoryLifeIncidentStore.read_active_incident(), the raw-log protocol's expose_committed_success_entry(), character.state.incidents._incident_scope_from_request(), _drop_none_identity_fields(), role_model.loop._validate_allowed_actions(), _life_action_allowed(), and _instructions_for_allowed_actions(). The current start-only life-action normalizer and allow_incident_start path must be extended or extracted for subtype-specific start vs cancel handling, not copied into a parallel parser.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep the implementation small and parallel to the already proven incident-start commit boundary where that reduces risk.
  • Keep Commit & Effects as the only writer for cancellation; the role model proposes, and the store only finalizes validated commit requests.
  • Keep InMemoryLifeIncidentStore scoped, copy-safe, and in-memory only.
  • Keep tests deterministic with fake clocks, fake IDs, fake adapters, and in-memory stores/logs.
  • Do not add generalized incident lifecycle abstractions unless two implemented actions need them during review.

Acceptance Criteria

  • MVP-016 is recorded under completed plans, and this file is the only active implementation slice.
  • A cancel-opted-in USER_MESSAGE turn can parse life_action.cancel_incident with incident_id and reason.
  • The turn cancels only the active incident for the source-event scope through Commit & Effects and InMemoryLifeIncidentStore.
  • A successful cancel clears the active incident for that scope and exposes one query-visible life_incident_cancelled raw log entry.
  • No active incident is cleared when there is no active incident, the incident ID mismatches, finalization rejects, visibility staging fails, the active incident changes before completion, or the store/log instances differ.
  • Default visible-reply turns, state-patch opt-in turns, and incident-start opt-in turns keep their current behavior.
  • No complete/resume/go-idle/no-change/interruption/queue/scheduler/body/Live2D/tool/retrieval/database behavior is added.
  • The development journal records source context, files touched, checks run, review notes, next action, future ideas, and whether active slice scope changed.

Test Plan

Unit Tests

  • Normalize valid and malformed life_action.cancel_incident decisions, including missing/empty incident_id, missing/empty reason, extra fields, and unsupported subtype in the wrong opt-in.
  • Render role-model input for cancel opt-in and assert allowed actions, instructions, and the compact MVP-016 context envelope remain valid.
  • Assert start, cancel, and state-patch opt-ins cannot be composed in one USER_MESSAGE model call.
  • Build and validate cancel commit/finalize requests and life_incident_cancelled log entries.
  • Finalize cancel through InMemoryLifeIncidentStore and assert same-scope active incident is cleared, other scopes remain, copies are safe, and query-visible success logs are staged/confirmed.
  • Reject no-active, incident-ID mismatch, raw-log mismatch, staging failure, and changed-before-completion paths without clearing the wrong active incident.
  • Assert post-confirm completion failures return a rejected result while preserving the already-query-visible life_incident_cancelled entry and appending a later life_incident_cancel_rejected entry.

Integration Tests

  • Start an active incident with the concrete store, then run a cancel-opted-in USER_MESSAGE turn and assert the turn result, store read, and raw-log query all show the cancellation.
  • Run a cancel-opted-in turn with no active incident and assert the user turn stops at the cancel commit boundary with a rejection log and no visible assistant reply commit.
  • Run a cancel-opted-in turn with a mismatched incident_id and assert the original active incident remains visible.
  • Run existing incident-start, living-state patch, visible-reply-only, and full unittest discovery gates to prove current behavior did not widen or regress.

Implementation Boundaries

  • runtime.contracts owns shared action constants and life-action normalization.
  • role_model.loop owns allowed-action rendering, cancel-specific instruction text, adapter invocation, output parsing, and role-model logs.
  • commit_effects.incident_cancel owns cancel commit request construction, active-incident validation, cancellation log construction, finalizer result validation, rejection logs, and success/rejection result envelopes.
  • character.state.incidents.InMemoryLifeIncidentStore owns scoped in-memory finalization and the existing read contract; it does not become a lifecycle history query API.
  • runtime.user_turn may coordinate the optional cancel boundary in the same narrow way it coordinates incident start, but it should not own cancellation validation.
  • character.state.context should not change except through existing active-incident read behavior if tests need the current active incident in model context.

Review Notes

  • This is a minimal Commit & Effects cancel boundary, not the full incident lifecycle.
  • The highest risk is clearing active incident state without a query-visible success log; finalization must keep state and log visibility atomic.
  • The second risk is accepting cancellation for a stale or invented incident ID; Commit & Effects must re-read and match the current active incident for the event scope.
  • The main duplication risk is copying the incident-start validators wholesale without sharing contract helpers or store scope helpers. Extract only when it reduces real duplicated validation in this slice.
  • Implementation review must verify the cancel success kind uses the existing atomic finalizer visibility path: ATOMIC_FINALIZER_SUCCESS_KINDS, expose_committed_success_entry(), confirm_committed_success_entry_visibility(), and discard_committed_success_entry_visibility().
  • Post-confirm completion failures are a deliberate audit edge case: once life_incident_cancelled visibility is confirmed, the commit boundary cannot hide that success entry, so it reports the later completion failure with a structured rejected result and a life_incident_cancel_rejected entry in the same trace.
  • Implementation review must verify the Role Model Loop extends or extracts the current start-only life-action parser path for subtype-specific start vs cancel handling instead of adding a second parser.
  • Keep the raw log as the only cancelled-history truth for now; do not add store history APIs or persistent storage.
  • Do not add interruption semantics. A user message may cancel an active incident only because the model proposed the opted-in cancel action and Commit & Effects accepted it.

Open Questions

  • Should later persistent LifeIncidentStore retain cancelled incident history directly, or continue to derive it from the Raw Event Log? Not in MVP-017.
  • Should cancellation produce body, living-state, Live2D, or scheduler effects? Not in MVP-017.
  • Should user interruption automatically cancel, interrupt, or background incidents before the model sees the turn? Not in MVP-017.

Future Ideas Discovered During Planning

  • Complete, resume, go-idle, and no-change incident lifecycle commit boundaries after cancel is proven.
  • Runtime Kernel user-interruption policy that can mark incidents interrupted/background before a user turn.
  • Persistent incident lifecycle storage with transition history and migrations.
  • INCIDENT_COMPLETION runtime events after active lifecycle transitions are stable.
  • Body/living-state/Live2D effects for incident lifecycle transitions.
  • Retrieval indexing over incident lifecycle episodes once raw transition truth is stable.
