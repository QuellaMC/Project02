MVP-001 - Runtime Event Intake and Raw Logging

Status: implemented and tested

Created: 2026-05-14. Implemented: 2026-05-14. Completed record: docs/plan/completed/mvp-001-runtime-event-intake-and-raw-logging.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages are 01 - Framework Overview, 02 - Runtime Architecture, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Notion direction: all triggers become RuntimeEvents, the Runtime Kernel owns event intake and routing, and Raw Event Log preserves runtime truth.

Local implementation direction comes from AGENTS.md and Development Workflow: build one small behavior slice, write tests, implement only that behavior, then record the result in the journal.

Goal

Implement the smallest runtime foundation that accepts a USER_MESSAGE-like RuntimeEvent, normalizes it, assigns event and trace identifiers, appends one raw log entry through a logging interface, and returns a deterministic routing result without calling a model.

Current Scope

  • RuntimeEvent input shape for USER_MESSAGE only.
  • event_id assignment when missing.
  • trace_id assignment when missing.
  • schema_version assignment.
  • created_at normalization when missing.
  • Basic event type validation.
  • Basic message text validation.
  • RawEventLog append interface.
  • Deterministic route result.
  • Python implementation under src/runtime/.
  • Ignored runtime artifact root at artifacts/.
  • Focused unit tests.
  • One integration test for Runtime Kernel intake to raw log append.
  • Development journal entry after implementation.

Minimal Schema

These TypeScript-style shapes define the behavior contract. MVP-001 implements the contract in Python 3 and tests it with unittest.

RuntimeEventInput

type RuntimeEventInput = {
  type: "USER_MESSAGE"
  payload: {
    text: string
    user_id?: string
    conversation_id?: string
  }
  event_id?: string
  trace_id?: string
  created_at?: string
  schema_version?: string
}

RuntimeEvent

type RuntimeEvent = {
  event_id: string
  trace_id: string
  type: "USER_MESSAGE"
  created_at: string
  schema_version: "0.1"
  payload: {
    text: string
    user_id?: string
    conversation_id?: string
  }
}

RawEventLogEntry

type RawEventLogEntry = {
  log_id: string
  trace_id: string
  event_id: string
  kind: "runtime_event_received"
  created_at: string
  schema_version: "0.1"
  data: {
    event: RuntimeEvent
  }
}

RuntimeRouteResult

type RuntimeRouteResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  model_needed: false
  next_step: "logged_only"
}

For MVP-001, "USER_MESSAGE" is still the only accepted event type. The route implementation should populate event_type from the normalized RuntimeEvent.type field instead of duplicating the literal constant, so a later reviewed event type can reuse the route contract without rewriting existing fields. The model_needed and next_step values are event-type-specific route policy, not universal defaults. MVP-001 registers only the USER_MESSAGE route policy, which returns model_needed = false and next_step = "logged_only".

Normalization Rules

  • type must be exactly "USER_MESSAGE".
  • payload.text must be a string with at least one non-whitespace character. Accepted text is preserved as provided.
  • Provided event_id and trace_id values are valid when they are non-empty strings after trimming. Valid provided IDs are preserved exactly.
  • Missing, empty, or whitespace-only event_id and trace_id values are treated as absent and generated by the injected ID generator.
  • Missing created_at means the field is absent and is assigned from the injected clock. Provided created_at, including explicit null, must be a valid ISO-8601 timestamp string with a datetime component and is preserved when valid.
  • Missing schema_version becomes "0.1". Provided schema_version must be "0.1"; other values are rejected until compatibility handling exists.
  • The raw log entry is appended only after event validation and normalization succeeds.
  • The raw log interface for this slice is append-only and should expose no update or delete operation.

Implementation Boundaries

  • Runtime Kernel owns event intake, normalization, validation, ID assignment, trace assignment, and deterministic route selection for this slice.
  • Raw Event Log is represented by a minimal append interface. The implementation may use an in-memory fake for tests.
  • Clock and ID generation must be injected or mockable so tests can assert deterministic output.
  • Generated ID format is an implementation detail behind the ID generator. Tests should assert fake generated values, not a global future ID scheme.
  • The runtime artifact root is artifacts/. This slice does not add a file-backed raw log adapter yet; storage remains the append interface.
  • No Character State Engine, Role Model Loop, Commit & Effects Engine, database adapter, or external service should be introduced unless required to satisfy this exact contract.
  • Future-compatible code should derive downstream fields from normalized runtime records while keeping accepted event types limited to the active slice.
  • Future route policies should be added one event type at a time through tested routing cases, not by widening the current USER_MESSAGE route.

Failure Behavior

  • Unsupported event type returns a validation error and does not append a raw log entry.
  • Missing payload or empty text returns a validation error and does not append a raw log entry.
  • Unsupported schema_version or malformed created_at returns a validation error and does not append a raw log entry.
  • Raw log append failure returns an error and does not return a successful route result.
  • ID or clock generation failure, if the chosen implementation can fail, returns an explicit runtime error.

  • The logging interface is justified because raw logging is part of the behavior contract and must remain replaceable before a real database exists.
  • The implementation should not widen this into chat, memory, character state, or provider selection.
  • Future-compatible code should derive downstream fields from normalized runtime records while keeping accepted event types limited to the active slice.
