MVP-002 - Local Character Conversation Core

Status: completed

Created: 2026-06-04. Completed: 2026-06-04. Archived spec: docs/plan/completed/mvp-002-local-character-conversation-core.html. Previous slice archived at docs/plan/completed/mvp-001-basic-relay-cli.html. Suggested implementation branch: feature/mvp-002-local-character-conversation-core.

Source Context

Product direction comes from the Notion project hub Live Character Framework, especially 01 - Framework Overview, 02 - Runtime Architecture, and 08 - Runtime Logging & Trace.

Long-term direction: a living character runtime where user messages enter a central path, character context shapes the answer, and accepted visible output is recorded as product truth.

Local rebuild direction comes from AGENTS.md and AGENTS.repo.md. The repo should grow from working vertical slices. MVP-001 proved a strict one-line relay command. MVP-002 turns that runnable path into the first local character conversation capability.

Previous Product

The current product is a one-message relay utility. It accepts one command-line message, validates the boundary, calls a deterministic local relay agent, and prints one reply line. 

node src/relay-cli.ts -- "are you there?"

# stdout
relay: are you there?

That proves the command path and validation contract, but it is not yet a character product. There is no local character identity, no conversation session, no visible transcript, and no stable central unit for "one character turn".

New Product Capability

After this slice, the local product can run a small character conversation session with one built-in character. The user should be able to talk to the character across multiple turns in a local CLI session, and the product should keep the visible transcript for that session. 

pnpm chat

Mira is ready.
You: are you there?
Mira: I'm here. Tell me what you need.
You: I'm tired.
Mira: I remember you said "are you there?" Stay with me for a minute.
You: /exit

The important change is not the exact sample wording. The important change is that the product gains a central local conversation core: 

user message
  -> local character profile
  -> recent session transcript
  -> character turn generation
  -> validated visible reply
  -> committed transcript entries

Goal

Build one solid local character conversation core that can support a week of focused work: character identity, session transcript, one-turn execution, multi-turn local CLI usage, deterministic agent behavior, and tests around successful and failed turns.

Current Scope

  • One built-in local character profile with stable identity and display name.
  • One in-memory conversation session for local CLI use.
  • Visible message records for user messages and character replies.
  • A character turn runner that validates input, builds recent visible context, calls a local character agent, validates the reply, and commits the turn to the session transcript.
  • A deterministic local character agent that can produce stable, context-aware replies for tests and manual use.
  • A local chat CLI that lets a user run a short multi-turn session.
  • Compatibility with the existing MVP-001 relay command unless the implementation thread explicitly records why the product contract should change.
  • Focused unit and CLI tests covering the conversation core, transcript behavior, invalid input, invalid agent replies, and local chat behavior.

Explicit Non-Goals

  • No live model provider call, API key, provider config, prompt template, or model selection.
  • No Twilio, WhatsApp, webhook, HTTP server, browser UI, or external provider edge.
  • No durable persistence, database, replay surface, trace store, or migration from old runtime data.
  • No memory, retrieval, tools, scheduler, Live2D, assets, plugin system, or background worker.
  • No Runtime Kernel, Character State Engine, Role Model Loop, Commit and Effects Engine, or old runtime module restoration from legacy/typescript.
  • No multi-character support, account system, authentication, or cross-session continuity.

Finished Slice

The product should feel like the smallest real local version of the Live Character Framework: one user can start a local session, send a few messages, receive character-owned replies, and trust that the visible transcript reflects exactly what happened in that session.

Before MVP-002 After MVP-002
One command turns one message into an echo-style relay reply. One local chat session turns user messages into character replies.
No character identity exists in the runnable product path. A built-in character profile owns the visible replies.
No session transcript exists after a reply is produced. User and character messages are appended to an in-memory session transcript.
The next message cannot use recent local context. The character turn receives recent visible messages from the session.
The only product unit is a relay result. The central product unit is a validated character turn result.

Functional Requirements

ID Requirement
FR-1 The product defines one built-in local character profile with stable ID and display name.
FR-2 The product can create an in-memory conversation session for that character.
FR-3 A successful character turn appends the normalized user message and validated character reply to the session transcript in order.
FR-4 The character turn runner passes recent visible transcript context to the local character agent.
FR-5 Invalid user input fails before the character agent is called and leaves the transcript unchanged.
FR-6 Invalid character replies fail before transcript commit and leave the transcript unchanged.
FR-7 The local chat CLI supports a short multi-turn session and a clear exit command.
FR-8 The existing relay command remains available as the MVP-001 smoke path unless a documented compatibility decision changes it.

Acceptance Criteria

ID Criterion
AC-1 A user can start the local chat command and complete at least two user-message turns with one built-in character.
AC-2 The second turn can see recent visible session context from the first turn.
AC-3 Each committed successful turn records exactly one user visible message and one character visible reply.
AC-4 Failed input validation and failed reply validation are atomic: no partial transcript entries are committed.
AC-5 The local character agent is deterministic under tests and requires no network or credentials.
AC-6 The implementation includes focused tests for the turn runner, session transcript, local character agent seam, and chat CLI boundary.
AC-7 pnpm lint, pnpm typecheck, pnpm test, strict unused-symbol TypeScript, and whitespace checks pass.

Implementation Boundaries

  • The conversation core owns session state, visible transcript records, turn execution, validation, and atomic commit behavior.
  • The local character agent owns deterministic reply generation for this slice.
  • The chat CLI owns terminal input/output, prompting, exit handling, and mapping core failures to user-visible errors.
  • The existing relay module remains the compatibility smoke path unless the implementation thread records a narrower change.
  • Future runtime vocabulary may guide names, but this slice should introduce only the structures needed by the runnable local conversation path.

Test Plan

  • Unit tests for creating a session with the built-in character profile.
  • Unit tests proving successful turns append user and character visible messages in order.
  • Unit tests proving recent visible context is passed to the local character agent.
  • Unit tests proving invalid input and invalid replies leave the transcript unchanged.
  • CLI boundary tests for a short local chat session, exit command, stdout prompts/replies, stderr errors, and process exit code.
  • Regression tests proving the MVP-001 relay command still satisfies its existing contract if preserved unchanged.

Future Pressure

Once this local conversation core is solid, later slices can replace the deterministic agent, add trace logging, introduce persistence, connect external transports, or grow toward the larger runtime architecture from Notion. Those decisions should be made from the pressure created by this working conversation path.
