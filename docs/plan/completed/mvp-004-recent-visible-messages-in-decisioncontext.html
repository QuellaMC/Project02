MVP-004 - Recent Visible Messages in DecisionContext

Status: completed, implemented, and tested

Created: 2026-05-15. Implemented: 2026-05-16. Completed slice path: docs/plan/completed/mvp-004-recent-visible-messages-in-decisioncontext.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages checked for this slice are 02 - Runtime Architecture, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Phase 1 still calls for a minimal user turn loop where the Character State Engine builds DecisionContext from recent messages only, Role Model Loop calls the model, Commit and Effects stores the visible reply, and Raw Event Log records the turn.

Local implementation truth comes from MVP-001, MVP-002, and MVP-003. The runtime can now normalize a USER_MESSAGE, call an injected fake role-model adapter for a visible_reply decision, and commit one assistant visible reply through an injected append-only interface. The model still sees only the current event; no recent conversation tail exists yet.

Goal

Add the smallest context-building behavior after MVP-003: include a bounded, normalized recent visible message tail in DecisionContext for a normalized USER_MESSAGE event when a conversation-scoped read-only source is supplied. The slice must not add concrete storage, a full user-turn orchestrator, retrieval, character state, new model actions, or new commit behavior.

Current Scope

  • One accepted event type: normalized USER_MESSAGE.
  • One call type remains user_message_visible_reply.
  • One allowed action remains visible_reply.
  • One new context field: character_snapshot.recent_visible_messages.
  • One bounded context source: recent visible messages for the same conversation_id.
  • One read-only injected interface for recent visible messages; no concrete database or file adapter.
  • One deterministic recent-message budget: read at most 24 candidate messages, then include at most six messages and at most 1200 approximate text tokens in model context.
  • Message records are copied and normalized before reaching model input or raw logs.
  • Existing Role Model Loop success and failure logging continues to snapshot the rendered model input.
  • Focused unit tests for recent-message validation, ordering, limiting, and context rendering.
  • One integration test showing recent messages flow into model input and completed role-model raw log data.

Explicit Non-Goals

  • Concrete ConversationLog storage, migrations, query language, pagination, or transaction behavior.
  • Writing user-message records into a conversation log.
  • Changing MVP-003 commit behavior or visible output schema.
  • Full user-turn orchestration across Runtime Kernel, Role Model Loop, and Commit and Effects.
  • Live model provider calls, provider configuration, streaming, retries, or network access.
  • Retrieval index, embeddings, keyword search, memory tools, source expansion, summaries, compaction, or replay UI.
  • CharacterRuntimeState, living state, virtual body, incidents, scheduled directives, active threads, continuity, tools, Live2D, or assets.
  • New model actions, state patches, incident actions, tool requests, scheduled directive actions, or continuity writes.
  • Permission matrix, confirmation policy, external side effects, UI delivery outbox, or notification path.
  • Changing the MVP-001 normalized event schema, except to read the existing optional conversation_id.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-004 should implement the contract in Python 3 and test it with unittest.

RecentVisibleMessage

type RecentVisibleMessage = {
  schema_version: "0.1"
  message_id: string
  trace_id: string
  source_event_id: string
  conversation_id: string
  role: "user" | "assistant"
  created_at: string
  text: string
}

message_id may be a committed assistant output_id or a future visible user-message ID. The current USER_MESSAGE event remains in DecisionContext.event and must not be duplicated inside recent_visible_messages.

RecentVisibleMessagesRequest

type RecentVisibleMessagesRequest = {
  schema_version: "0.1"
  conversation_id: string
  before_event_id: string
  before_created_at: string
  max_candidate_messages: 24
}

RecentVisibleMessageBudget

type RecentVisibleMessageBudget = {
  max_messages: 6
  max_text_tokens: 1200
  token_count_strategy: "approx_chars_per_4"
}

MVP-004 uses a deterministic approximate token counter: ceil(len(text) / 4). It must not add a real tokenizer dependency or model-specific token accounting in this slice.

RecentVisibleMessagesSource

interface RecentVisibleMessagesSource {
  read_recent_visible_messages(
    request: RecentVisibleMessagesRequest
  ): RecentVisibleMessage[]
}

The interface is read-only. A test fake may return in-memory records. A concrete storage adapter remains a future slice.

DecisionContext

type DecisionContext = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  call_type: "user_message_visible_reply"
  event: {
    type: "USER_MESSAGE"
    text: string
    created_at: string
    user_id?: string
    conversation_id?: string
  }
  character_snapshot: {
    recent_visible_messages: RecentVisibleMessage[]
  }
  allowed_actions: ["visible_reply"]
}

RoleModelInput

type RoleModelInput = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  instructions: string
  decision_context: DecisionContext
}

RoleModelTurnResult, CharacterDecision, and MVP-003 visible commit schemas remain unchanged in this slice.

Functional Requirements

ID Requirement
FR-1 The context builder accepts only a normalized USER_MESSAGE event with schema_version = "0.1".
FR-2 If the source event has no conversation_id, the context builder returns recent_visible_messages = [] and does not call the recent-message source.
FR-3 If the source event has a conversation_id, the builder calls the injected recent-message source exactly once with that ID, the current event_id, the current created_at, and max_candidate_messages = 24.
FR-4 Only provider records with schema_version = "0.1", matching conversation_id, supported role, valid timestamps before the current event timestamp, and non-empty text are accepted.
FR-5 The current source event is excluded from recent_visible_messages by matching source_event_id or message_id against the current event_id.
FR-6 Duplicate provider records with the same message_id or source_event_id fail context validation before adapter invocation.
FR-7 The builder applies RecentVisibleMessageBudget after validation and current-event exclusion, selecting the newest accepted records that fit max_messages = 6 and max_text_tokens = 1200. Messages that exceed the remaining token budget are skipped, not truncated.
FR-8 Approximate token count is calculated deterministically from message text with ceil(len(text) / 4); no real tokenizer, model-specific counter, or external dependency is introduced.
FR-9 The selected messages are ordered oldest-to-newest in DecisionContext, regardless of provider return order.
FR-10 Returned context and model input use deep-copied message snapshots so provider-side mutation cannot alter rendered model input or raw log snapshots.
FR-11 render_role_model_input() validates the new character_snapshot.recent_visible_messages shape before rendering.
FR-12 run_role_model_turn() can receive an optional recent-message source and includes recent messages in the logged model_input when the turn succeeds or fails after rendering.
FR-13 The Role Model Loop still calls at most one injected adapter and still returns decision_ready_for_commit for a valid visible-reply decision.

Non-Functional Requirements

  • Keep behavior deterministic for the same normalized event and provider records.
  • Preserve all MVP-001, MVP-002, and MVP-003 public contracts unless this spec explicitly changes the context shape.
  • Do not let Role Model Loop query concrete storage directly; use an explicit read-only interface or input boundary.
  • Keep validation strict enough that malformed provider records cannot enter model input silently.
  • Keep recent-message budget values as named constants instead of scattered literals.
  • Use existing timestamp and shared contract validation helpers where they fit.
  • Avoid adding broad Character State Engine scaffolding beyond the context-source behavior required by this slice.
  • Do not add speculative adapters, storage folders, retrieval APIs, state stores, background workers, or model-provider code.

Acceptance Criteria

  • A normalized USER_MESSAGE with conversation_id can build a DecisionContext containing a message-count and approximate-token bounded recent visible message tail.
  • A normalized USER_MESSAGE without conversation_id builds a valid context with an empty recent-message tail and no source call.
  • Malformed, mismatched, unsupported-role, or empty-text message records fail context validation before adapter invocation.
  • Current-event duplicate records are excluded from the recent-message tail.
  • Duplicate recent-message message_id or source_event_id records fail context validation before adapter invocation.
  • Records with created_at greater than or equal to the current event created_at fail context validation before adapter invocation.
  • Selected messages fit both max_messages = 6 and max_text_tokens = 1200 under the approximate token counter.
  • The rendered RoleModelInput includes character_snapshot.recent_visible_messages.
  • The successful role-model raw log snapshot includes the same rendered recent-message tail.
  • The Role Model Loop still uses the injected fake adapter and does not call a live provider or external service.
  • MVP-003 commit tests continue to pass unchanged.
  • Relevant unit and integration tests pass.
  • The development journal records files changed and tests run.
  • Future ideas discovered during planning are recorded in future-slices.html.

Test Plan

Unit Tests

  • Builds a context with empty recent_visible_messages when no conversation_id is present.
  • Calls the recent-message source once with max_candidate_messages = 24 when conversation_id is present.
  • Normalizes accepted recent visible messages and orders them oldest-to-newest.
  • Limits the context tail to six messages after ordering/filtering.
  • Limits the context tail to 1200 approximate text tokens using ceil(len(text) / 4).
  • Skips messages that would exceed the remaining token budget without truncating message text.
  • Excludes the current source event from the recent-message tail.
  • Rejects duplicate recent-message message_id and source_event_id values.
  • Rejects source records with created_at equal to or later than the current event timestamp.
  • Rejects malformed provider records, unsupported roles, mismatched conversation IDs, invalid timestamps, and empty text.
  • Validates character_snapshot.recent_visible_messages during model input rendering, including the rule that non-empty recent messages require a non-empty context event conversation_id.
  • Protects rendered model input from provider-side mutation through copies.

Integration Tests

  • Normalized USER_MESSAGE plus fake recent-message source to rendered RoleModelInput, fake adapter call, parsed decision, and role_model_turn_completed raw log containing recent messages.
  • Malformed recent-message source output fails before adapter invocation.

Implementation Boundaries

  • Runtime Kernel remains responsible for event intake and normalization only.
  • Character State Engine conceptually owns context building. MVP-004 temporarily keeps the minimal recent-message source path in role_model.loop to avoid a speculative Character State Engine package before there is a second context source.
  • This temporary ownership must end when state, incidents, retrieval, active threads, context-build raw logs, or another context source is added; that future slice should move recent-message context behind a proper Character State Engine/context-builder boundary.
  • Role Model Loop remains responsible for rendering model input, invoking the injected adapter, parsing visible-reply decisions, and logging model turns.
  • Commit and Effects Engine remains unchanged; MVP-003 continues to own visible output commit and commit/reject raw logs.
  • RawEventLog remains append-only. This slice relies on existing role-model turn logs to snapshot model input with recent messages.
  • No concrete database, network client, model provider, renderer, scheduler, worker, retrieval index, or tool implementation is introduced.

Failure Behavior

  • Invalid source event shape raises the existing role-model validation error before provider access or adapter call.
  • Missing conversation_id is not an error; it produces an empty recent-message tail.
  • Malformed provider request handling or provider exceptions propagate before adapter invocation. No retry policy is introduced.
  • Malformed recent-message records fail context validation before adapter invocation so bad context is not sent to the model.
  • Duplicate recent-message identities fail context validation before adapter invocation so ambiguous records are not sent to the model.
  • Over-returned source records at or after the current event timestamp fail context validation instead of being shown to the model.
  • If adapter invocation succeeds but model output parsing fails, existing role_model_turn_failed logging captures the rendered model input with recent messages.
  • No new raw log kind is added for context build failures; a future logging slice can add dedicated context-build logs if needed.

Pre-Code Review Notes

  • The behavior does not already exist; MVP-002 intentionally built context from the current event only.
  • MVP-003 made assistant visible replies available as committed output records, which makes a recent-message context tail the next narrow Phase 1 step.
  • The slice is smaller than a full user-turn orchestrator because it changes only the context passed into the existing fake-adapter loop.
  • The slice is smaller than concrete conversation storage because it reads through an injected source and validates message snapshots.
  • The only schema expansion is character_snapshot.recent_visible_messages plus the read-only request, budget, and message shapes needed to build it.
  • Security risk stays low because the source is read-only, no external side effects are introduced, and the allowed model action remains visible_reply.

Post-Code Review Notes

  • The implementation keeps MVP-004 inside role_model.loop instead of adding a speculative Character State Engine package before a second context source exists.
  • This is temporary ownership only: once state, incidents, retrieval, active threads, context-build logs, or another context source enters scope, the recent-message behavior should move behind a Character State Engine/context-builder boundary.
  • build_decision_context() now accepts an optional read-only RecentVisibleMessagesSource; existing callers without a source get a valid empty recent-message tail.
  • Recent-message requests are deterministic and use max_candidate_messages = 24.
  • Provider records are strictly validated for schema version, identity fields, matching conversation_id, supported role, valid timestamp before the current event, and non-empty text before model input rendering.
  • The current event is excluded from recent_visible_messages by message_id or source_event_id.
  • Duplicate message_id or source_event_id values are rejected in source-built contexts and render-time validation.
  • render_role_model_input() rejects non-empty recent-message tails when the context event has no non-empty conversation_id.
  • The selected tail uses the newest records that fit max_messages = 6 and max_text_tokens = 1200, skips oversized messages without truncation, and renders oldest-to-newest.
  • render_role_model_input() validates the new character_snapshot.recent_visible_messages shape before adapter invocation.
  • run_role_model_turn() forwards the optional source and existing role-model turn logs snapshot the rendered recent-message context.
  • No concrete storage, retrieval index, orchestration layer, model provider, Commit and Effects behavior, external service, or side effect was added.

Planning Questions Answered From Notion

Question Answer For MVP-004 Notion Basis
Should future conversation storage record user messages in the same store as assistant visible replies? Yes. Future storage should use one ConversationLog as the visible transcript projection, with role or kind fields for user, assistant, proactive, and visible tool messages. RawEventLog remains the separate lossless internal truth. MVP-004 still reads through a fake source and does not add concrete storage. 08 - Runtime Logging & Trace defines ConversationLog as visible user-facing interaction and RawEventLog as lossless internal truth. 06 - Character State Engine & Retrieval Management lists ConversationLog as the visible user-facing raw store.
Should context build failures receive their own raw log kind before debug inspector work starts? Eventually yes, but not in MVP-004. Dedicated decision_context_built and decision_context_build_failed raw log entries should be handled by a later context-build logging or debug-inspector slice, after the context builder has more than one source. 08 - Runtime Logging & Trace requires context inputs, DecisionContext snapshots, context budget usage, errors, and fallbacks to be logged for replay and debugging.
Should the MVP-004 recent-message budget remain fixed once state, incidents, and retrieval context are added? No. max_messages = 6 and max_text_tokens = 1200 are provisional early defaults. A later ContextBudgetPolicy should allocate a dynamic share of model context across recent visible messages, active threads, retrieved context, state/incident/directive briefs, tool results, and runtime notes. Keep max_messages as a safety cap. 06 - Character State Engine & Retrieval Management recommends a deterministic context budget where recent visible messages use only a share of the overall budget, not the whole model-facing context.
