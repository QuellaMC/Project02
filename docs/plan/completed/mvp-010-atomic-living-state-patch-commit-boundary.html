Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace.

Phase 2 needs CharacterRuntimeState writes, but MVP-009 deliberately used a non-durable prepare boundary and treated the raw-log append as the commit point. MVP-010 proves only the next missing runtime contract: a living-state patch success must commit the validated state snapshot and its living_state_patch_committed raw log entry atomically.

Local implementation truth comes from completed MVP-001, MVP-002, MVP-003, MVP-004, MVP-005, MVP-006, MVP-007, MVP-008, and MVP-009.

Goal

Replace the MVP-009 prepare-only living-state patch success path with one injected atomic commit boundary. A successful state patch must make both facts visible together: the committed CharacterRuntimeStateSnapshot and the matching living_state_patch_committed raw log entry. This slice keeps the existing user-turn, role-model, patch-shape, and visible-reply behavior intact.

Current Scope

  • One event type remains in scope: USER_MESSAGE.
  • One state family remains in scope: state_patch.living_state with only current_activity, mood, and toward_user.
  • One success-path boundary changes: the existing MVP-009 prepare/snapshot-candidate path remains the single candidate producer, and its validated candidate is finalized by an injected atomic state-plus-log boundary before assistant visible reply commit.
  • The atomic boundary is still fake/injected for tests. It may be in-memory, but it must model all-or-nothing state and raw-log visibility.
  • The existing committed snapshot validation stays authoritative: source event ID is present, patched fields match, and updated_at equals the runtime-owned commit timestamp.
  • Existing no-patch, malformed-model-output, validation-rejection, store-rejection, and visible-reply-only paths stay behavior-compatible with MVP-009.
  • Tests must prove the assistant visible reply is committed only after the atomic state-plus-log commit succeeds.

Explicit Non-Goals

  • No database, filesystem store, migration, ORM, queue, background worker, scheduler, replay worker, or production persistence adapter.
  • No concrete multi-character lookup and no runtime-inferred character_id; the injected boundary remains caller-bound to the active character.
  • No broad CharacterRuntimeState expansion, state_version, optimistic locking, idempotency key, reconciliation job, or cross-turn deduplication policy.
  • No body state, body drift, need thresholds, active incident, incident queue, scheduled directive, retrieval, continuity write, tool request, Live2D status, asset behavior, proactive message, or new runtime event family.
  • No new Role Model action. The model still returns required action = "visible_reply" and may include only the optional MVP-009 living-state patch when state patching is allowed.
  • No transaction between user visible message projection, state patch commit, and assistant visible reply commit. MVP-010 only atomizes state snapshot plus state-patch raw log.
  • No dedicated context-build log or debug inspector. Existing role-model and state-patch logs remain the audit surface.

Minimal Schema

Snapshot Candidate Path

MVP-010 reuses the existing MVP-009 LivingStatePatchStore.prepare_living_state_patch_commit() path only as the snapshot-candidate producer before finalization. Commit and Effects must not duplicate snapshot construction by independently applying the patch to state in a second code path. If implementation extracts a helper for readability, that helper must be the one shared path used to obtain the candidate snapshot before validation and finalization, not a parallel builder.

The MVP-010 finalizer is a new boundary after that candidate path. It atomically exposes the already validated committed_snapshot and committed_log_entry; it does not create either artifact.

LivingStatePatchFinalizer

type LivingStatePatchFinalizer = {
  finalize_living_state_patch_commit(
    request: LivingStatePatchFinalizeRequest
  ): LivingStatePatchFinalizeResult
}

The MVP-010 finalization boundary must use finalizer/finalize naming. Do not name the new atomic boundary LivingStatePatchStore or call the final step prepare_living_state_patch_commit(). Those names belong to the MVP-009 prepare-only boundary and would blur future concrete persistence ownership.

LivingStatePatchFinalizeRequest

type LivingStatePatchFinalizeRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  commit_time: string
  patch: {
    living_state: {
      current_activity?: string
      mood?: string
      toward_user?: string
    }
  }
  committed_snapshot: CharacterRuntimeStateSnapshot
  committed_log_entry: RawEventLogEntry & {
    kind: "living_state_patch_committed"
  }
  user_id?: string
  conversation_id?: string
}

LivingStatePatchFinalizeResult

type LivingStatePatchFinalizeResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  committed_log_entry_id: string
}

LivingStatePatchAtomicCommitResult

type LivingStatePatchAtomicCommitResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status:
    | "living_state_patch_committed"
    | "living_state_patch_skipped"
    | "living_state_patch_rejected"
  committed_snapshot?: CharacterRuntimeStateSnapshot
  committed_log_entry_id?: string
  failure?: {
    stage:
      | "living_state_patch_commit_validation"
      | "living_state_patch_store"
      | "living_state_patch_finalize"
    code: string
    message: string
  }
}

Functional Requirements

ID Requirement
FR-1 Without state-patch opt-in, all MVP-009 visible-reply behavior remains unchanged.
FR-2 With state-patch opt-in and no model patch, the runtime returns living_state_patch_skipped, appends no state patch raw log, and commits the assistant visible reply as in MVP-009.
FR-3 Malformed model-output patches continue to fail in Role Model Loop parsing before any state commit boundary runs.
FR-4 Commit and Effects still validates the normalized source event, role-model result envelope, living-state patch, committed snapshot candidate shape, source event IDs, patched fields, and runtime-owned timestamp before finalization. The snapshot candidate comes from the existing MVP-009 prepare path or one extracted helper around that same path.
FR-5 On success, Commit and Effects turns the validated snapshot candidate into the committed_snapshot, builds the exact living_state_patch_committed raw log entry, and places both in one LivingStatePatchFinalizeRequest. The finalizer must not revalidate the whole role-model result, rebuild the committed snapshot, or construct the committed log entry.
FR-6 The injected finalizer is the success commit point. It receives already validated commit artifacts and must expose neither the committed snapshot nor the committed raw log entry unless both commit together.
FR-7 If finalization fails, the result is living_state_patch_rejected with failure stage living_state_patch_finalize, one rejection raw log is appended through the existing rejection path, no assistant visible reply is committed, and tests prove no state-plus-success-log pair became visible.
FR-8 The success raw log order remains deterministic from the caller's view: runtime_event_received, user_visible_message_committed, role_model_turn_completed, living_state_patch_committed, visible_reply_committed.
FR-9 The final UserMessageTurnResult keeps the MVP-009 nested results and may include the atomic commit result, but it must not add new model-facing behavior.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Use fakes for the atomic boundary, raw logs, visible conversation, current-state source, role-model adapter, clock, and IDs.
  • Reuse existing runtime.contracts validators and the MVP-008 validate_current_character_state_snapshot() contract.
  • Reuse the MVP-009 prepare/snapshot-candidate path before finalization. Do not add another snapshot builder that applies the living-state patch separately.
  • Keep transaction semantics local to the living-state patch success path; do not introduce a generic transaction framework.
  • Deep-copy all finalized request, snapshot, log, result, and failure data so caller mutation cannot alter audit snapshots.
  • Add living_state_patch_finalize to the supported failure-stage taxonomy in one implementation location only, alongside the existing living-state patch failure stages. Tests should import or derive that stage constant instead of scattering raw string literals.
  • The fake atomic finalizer must expose separate visible lists for durable state snapshots and durable success raw logs. Ordinary rejection logs remain on the existing raw-log fake and must not be used to prove success atomicity.
  • Keep Runtime Kernel and Role Model Loop behavior unchanged except for any adapter type names required to pass the atomic boundary through existing user-turn orchestration.

Acceptance Criteria

  • Existing MVP-001 through MVP-009 tests continue to pass.
  • A successful patch records exactly one atomic finalization and exposes both the committed snapshot and the living_state_patch_committed raw log entry together.
  • A finalization failure exposes neither durable state nor the committed success raw log entry, appends a rejection raw log, and stops before assistant visible reply commit.
  • Validation failures before finalization continue to produce living_state_patch_rejected without calling the finalize boundary.
  • No concrete storage, state versioning, body state, incidents, scheduled directives, retrieval, tools, Live2D, provider calls, scheduler, or new event type is added.
  • The development journal records source context, files touched, checks run, review notes, and next action.
  • Future ideas discovered during planning are recorded in future-slices.html.

Test Plan

Unit Tests

  • Commit and Effects builds a LivingStatePatchFinalizeRequest from already validated artifacts and deep-copies source event, role-model result, patch, committed snapshot, and committed raw log entry before handing it to the finalizer.
  • The snapshot-candidate producer is called once for a patch success; the finalizer receives the same validated snapshot, not a separately reconstructed one.
  • Success calls finalize_living_state_patch_commit() on the fake finalizer once and returns living_state_patch_committed with a copied committed snapshot and committed log entry ID.
  • The fake finalizer records successful commits in separate durable_state_snapshots and durable_success_logs lists so tests can assert all-or-nothing visibility independently of rejection logs.
  • Finalizer failure returns living_state_patch_rejected with the centralized finalize failure-stage constant, appends one rejection log, and leaves the fake finalizer's durable state/success-log lists empty.
  • Malformed committed snapshot candidates are rejected before finalization.
  • No-patch decisions skip finalization and append no state patch log.

Integration Tests

  • Run one state-enabled user turn with fake current-state source, fake atomic finalizer, fake visible conversation, fake adapter, fake raw log, deterministic IDs, and deterministic clock.
  • Assert the success log order includes one atomically committed living_state_patch_committed entry before assistant visible reply commit, and assert that the fake finalizer exposes exactly one durable state snapshot and one durable success log.
  • Assert a finalization failure stops before assistant visible reply append, appends one rejection log through the ordinary raw-log fake, and leaves the fake finalizer's durable state/success-log lists empty.
  • Assert non-state-enabled and state-enabled no-patch user turns preserve MVP-009 visible reply behavior.
  • Run full unittest discovery.

Implementation Boundaries

  • Runtime Kernel remains unchanged.
  • Character State Engine remains the read-side state snapshot validator/source boundary; it does not finalize commits.
  • Role Model Loop remains the model-call and parse boundary; it does not learn about atomic persistence.
  • Commit and Effects owns validation, accepting the validated snapshot candidate as the committed_snapshot, committed-log-entry construction, finalize request construction, finalization failure handling, and user-turn stop behavior.
  • The existing MVP-009 prepare path owns snapshot candidate production until a later concrete persistence slice replaces it with a durable state store contract.
  • The finalizer owns only atomic visibility of the already built committed snapshot and committed success log entry.
  • User-turn orchestration may pass the atomic finalizer through and must keep assistant visible reply commit after state patch finalization.
  • Raw Event Log behavior changes only for the successful living-state patch entry: that entry is committed through the atomic state-plus-log boundary instead of a separate success append.

Review Notes

  • MVP-010 is not a storage/database slice. It proves the transaction contract before choosing a concrete persistence technology.
  • The smallest useful behavior is all-or-nothing visibility for one state snapshot and one committed raw log entry.
  • MVP-010 should not introduce duplicate snapshot-building code. It should reuse the MVP-009 candidate path and only add finalization after validation.
  • State patch validation, snapshot validation, and visible reply projection remain the MVP-009 contracts; this slice should not reopen them unless tests expose a defect.
  • If implementation pressure suggests state versions, idempotency, replay, or concrete database APIs, park those as future slices.

Open Questions

  • Should the eventual concrete store use optimistic locking or append-only snapshot revisions? Not in MVP-010.
  • Should user visible message projection and assistant visible reply commit share the same transaction later? Not in MVP-010.
  • Should finalization failure emit its rejection log through the same atomic boundary? Not in MVP-010; no state mutation has committed, so the existing rejection-log path is sufficient.

Future Ideas Discovered During Planning

  • Concrete database-backed CharacterRuntimeStateStore once the atomic boundary contract is proven.
  • State revision or optimistic locking for concurrent state updates.
  • Idempotency keys and retry/reconciliation behavior for state patch commits.
  • Atomic grouping across user visible projection, state patch commit, and assistant visible reply commit.
