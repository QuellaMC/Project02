MVP-002 - Minimal Role Model Loop with Fake Adapter

Status: completed, implemented, and tested

Created: 2026-05-15. Implemented: 2026-05-15. Completed slice path: docs/plan/completed/mvp-002-minimal-role-model-loop-with-fake-adapter.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages are 01 - Framework Overview, 02 - Runtime Architecture, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Current direction: Runtime Kernel routes events, Role Model Loop is the only model-call boundary, Commit and Effects Engine validates durable changes, and Raw Event Log preserves the runtime truth.

Local implementation truth comes from MVP-001: the runtime can accept a USER_MESSAGE, normalize IDs and timestamps, append one raw event log entry, and return a deterministic logged_only route without a model call.

Goal

Add the smallest testable model-call path after MVP-001. The path accepts an already-normalized USER_MESSAGE event, builds a minimal DecisionContext through a tiny context-builder boundary, renders one deterministic model input through the Role Model Loop, calls an injected fake model adapter, parses a visible_reply-only CharacterDecision, records the model turn through the existing raw log boundary, and returns the parsed decision for a future commit slice.

Current Scope

  • One accepted event type: normalized USER_MESSAGE from the MVP-001 contract.
  • One call type: user_message_visible_reply.
  • One allowed action: visible_reply.
  • Minimal DecisionContext built by a tiny context builder from the current event only.
  • Deterministic model input rendering from the context.
  • An injected RoleModelAdapter interface, tested with a fake adapter.
  • Strict parsing of a JSON-like model output into a CharacterDecision.
  • One raw log entry for the completed role-model turn after parsing succeeds.
  • Focused unit tests for context building, input rendering, adapter calls, and output parsing.
  • One integration test from normalized runtime event to parsed decision and raw log append.

Explicit Non-Goals

  • Live model provider calls.
  • Provider configuration, API keys, retry policy, streaming, or network access.
  • Conversation history or recent visible message retrieval.
  • CharacterRuntimeState, living state, virtual body, incidents, scheduled directives, active threads, continuity, retrieval, tools, Live2D, assets, compaction, or replay UI.
  • Commit and Effects Engine implementation.
  • Visible reply delivery or conversation persistence.
  • State patch actions, incident actions, tool requests, scheduled directive actions, or continuity writes.
  • Changing the MVP-001 raw event intake schema.
  • Changing existing MVP-001 behavior except where an integration seam is required and tested.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-002 implements the contract in Python 3 and test it with unittest.

DecisionContext

type DecisionContext = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  call_type: "user_message_visible_reply"
  event: {
    type: "USER_MESSAGE"
    text: string
    created_at: string
    user_id?: string
    conversation_id?: string
  }
  allowed_actions: ["visible_reply"]
}

RoleModelInput

type RoleModelInput = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  instructions: string
  decision_context: DecisionContext
}

RoleModelAdapterOutput

type RoleModelAdapterOutput = {
  model_id: string
  created_at: string
  raw_text: string
}

RoleModelRawTextJson

type RoleModelRawTextJson = {
  schema_version: "0.1"
  action: "visible_reply"
  visible_reply: {
    text: string
  }
}

RoleModelAdapterOutput.raw_text must be a JSON object matching RoleModelRawTextJson. The parser requires schema_version, action, and visible_reply.text. schema_version must be exactly "0.1", action must be exactly "visible_reply", and visible_reply.text must be a non-empty string after trimming. Extra top-level fields and extra visible_reply fields are rejected in this slice. trace_id and event_id are attached from the source RoleModelInput, not accepted from model output.

CharacterDecision

type CharacterDecision = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  action: "visible_reply"
  visible_reply: {
    text: string
  }
}

RoleModelTurnCompletedLogEntry

type RoleModelTurnCompletedLogEntry = {
  log_id: string
  trace_id: string
  event_id: string
  kind: "role_model_turn_completed"
  created_at: string
  schema_version: "0.1"
  data: {
    model_input: RoleModelInput
    model_output: RoleModelAdapterOutput
    decision: CharacterDecision
  }
}

RoleModelTurnFailedLogEntry

type RoleModelTurnFailedLogEntry = {
  log_id: string
  trace_id: string
  event_id: string
  kind: "role_model_turn_failed"
  created_at: string
  schema_version: "0.1"
  data: {
    model_input: RoleModelInput
    model_output?: RoleModelAdapterOutput
    raw_model_output_snapshot?: unknown
    failure: {
      stage: "adapter_call" | "parse_output"
      code: "adapter_exception" | "malformed_model_output"
      message: string
    }
  }
}

model_output is present only when the adapter returned a valid RoleModelAdapterOutput envelope that failed later parsing. If the adapter returned a malformed envelope, the failed log uses raw_model_output_snapshot instead so future consumers do not mistake an invalid envelope for a valid adapter output.

RoleModelTurnResult

type RoleModelTurnResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  model_called: true
  status: "decision_ready_for_commit"
  decision: CharacterDecision
}

Functional Requirements

ID Requirement
FR-1 The Role Model Loop accepts only a normalized USER_MESSAGE event with schema_version = "0.1".
FR-2 A minimal context-builder boundary builds a DecisionContext from the current event without loading state, history, retrieval, tools, or incidents.
FR-3 The rendered RoleModelInput is deterministic for the same normalized event.
FR-4 The loop calls exactly one injected RoleModelAdapter per accepted event.
FR-5 The default tests use a fake adapter and do not call a live model provider or external service.
FR-6 The parser accepts only raw_text JSON matching RoleModelRawTextJson.
FR-7 Adapter exceptions and malformed adapter output append one role_model_turn_failed raw log entry and do not append a success log entry.
FR-8 After successful parsing, the loop appends exactly one role_model_turn_completed raw log entry.
FR-9 The result envelope preserves the source trace_id, event_id, and event_type.
FR-10 The post-call result states model_called = true and status = "decision_ready_for_commit".

Non-Functional Requirements

  • Keep the implementation deterministic under injected clock, ID generator, and fake adapter.
  • Keep the new code under the smallest module path needed for the role model boundary.
  • Use explicit validation errors for unsupported event types, unsupported schema versions, malformed context, malformed model output, and empty reply text.
  • Do not add speculative provider adapters, state stores, prompt registries, tool registries, or commit/effects abstractions.
  • Preserve MVP-001 tests unless a spec-backed integration change requires a targeted update.

Acceptance Criteria

  • A normalized USER_MESSAGE can produce a deterministic DecisionContext.
  • The fake adapter receives the rendered RoleModelInput exactly once.
  • A valid fake output parses into a visible_reply-only CharacterDecision.
  • The role model turn appends one raw log entry after successful parsing.
  • Malformed model output appends one failure log entry and fails without a success log append.
  • Adapter exceptions append one failure log entry and fail without a success log append.
  • No live model provider or external service is called.
  • Relevant unit tests pass.
  • Relevant integration tests pass.
  • The development journal records files changed and tests run.
  • Future ideas discovered during implementation are recorded in future-slices.html.

Test Plan

Unit Tests

  • Builds minimal DecisionContext from a normalized USER_MESSAGE.
  • Rejects unsupported event type or unsupported schema_version.
  • Renders stable RoleModelInput for the same event.
  • Parses valid fake adapter JSON into CharacterDecision.
  • Rejects malformed JSON, missing or unsupported output schema_version, unknown actions, missing visible_reply, empty reply text, and extra output fields.

Integration Tests

  • Normalized MVP-001 event to fake adapter call to parsed decision to one raw log append.
  • Fake adapter failure or malformed output appends one role_model_turn_failed raw log entry and does not return a successful turn result.

Implementation Boundaries

  • Runtime Kernel remains responsible for event intake and normalization.
  • A minimal context-builder boundary owns DecisionContext construction for this slice. It does not introduce durable character state.
  • Role Model Loop owns model input rendering, fake adapter invocation, and output parsing.
  • RawEventLog remains an explicit append-only boundary for the orchestrating model-call path.
  • Commit and Effects Engine is not implemented in MVP-002; the parsed decision is returned for a later commit slice.
  • No concrete database, model provider, network client, UI, renderer, or tool implementation is introduced.

Failure Behavior

  • Unsupported event type or schema version fails before adapter invocation.
  • Adapter exceptions append one role_model_turn_failed entry with stage = "adapter_call", then propagate as runtime failures.
  • Malformed adapter output appends one role_model_turn_failed entry with stage = "parse_output", then raises a validation error.
  • Failure log entries include the rendered RoleModelInput, a valid model_output or raw_model_output_snapshot when adapter output exists, and a narrow failure code/message.
  • No role_model_turn_completed entry is appended for failed adapter calls or rejected model outputs.
  • Raw log append failure prevents a successful RoleModelTurnResult from being returned.

Pre-Code Review Notes

  • The behavior does not already exist; MVP-001 intentionally stopped before any context or model boundary.
  • Existing RuntimeEvent, RawEventLog, ID generator, clock, and validation style should be reused.
  • A minimal context-builder function is justified because the framework assigns DecisionContext construction to the Character State Engine side of the architecture.
  • A shared role-model module is justified only for model input rendering, fake adapter invocation, and parser behavior.
  • The slice is intentionally smaller than the full Phase 1 user turn loop.
  • Security and persistence boundaries stay narrow because no real provider, tool, or visible output effect exists.
  • The schema introduces only DecisionContext, RoleModelInput, adapter output, and visible-reply decision fields needed for this slice.

Post-Code Review Notes

  • The implementation uses a standalone role_model.loop module instead of wiring the loop behind RuntimeKernel, keeping MVP-001 intake behavior unchanged.
  • The fake adapter boundary is an injected RoleModelAdapter.generate(model_input) protocol; no provider configuration, API key, retry policy, streaming, or network client was added.
  • CharacterDecision parsing and completed-log validation share the same canonical normalizer so reply text trimming cannot diverge between paths.
  • Runtime and role-model raw log entries use a shared runtime.logging.build_raw_log_entry() helper for the common envelope and snapshot copy.
  • Downstream event.type and event_type values are derived from the validated normalized event instead of duplicating the current literal.
  • render_role_model_input() validates the required nested DecisionContext.event fields and rejects unsupported extra context fields before rendering a model input.
  • Optional normalized payload strings are preserved from MVP-001 events, and adapter-side mutation cannot change the model-input snapshot written to the raw log.
  • Completed and failed raw log entries deep-copy their snapshots so caller-side mutation cannot change append-only in-memory log truth.
  • Malformed adapter output and adapter exceptions both append one role_model_turn_failed entry and do not append a success entry.
  • Malformed adapter-output envelopes are logged under raw_model_output_snapshot so model_output remains a valid RoleModelAdapterOutput when present.
  • Role-model log builders validate completed decisions, failure stages, and failure codes before returning appendable raw-log records.
  • Successful fake-adapter turns append one role_model_turn_completed entry after parsing and return a decision_ready_for_commit result.
  • No Commit and Effects Engine, visible conversation persistence, character state, incidents, tools, retrieval, Live2D, assets, or background workers were introduced.

Open Questions

  • Should CharacterDecision gain a generated decision_id in the commit slice, or only when durable decision records are introduced?
  • Should role_model_turn_failed remain a single failure kind after Commit and Effects failure logging exists, or split by failure stage later?
