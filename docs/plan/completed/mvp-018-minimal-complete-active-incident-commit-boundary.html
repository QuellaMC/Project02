MVP-018 - Minimal Complete Active Incident Commit Boundary v0.1

Status: implemented and merged

Created: 2026-05-23. Completed plan path: docs/plan/completed/mvp-018-minimal-complete-active-incident-commit-boundary.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-018-minimal-complete-active-incident-commit-boundary. PR: #21.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 04 - Event Triggers & Runtime Hooks, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Notion lists life_action.complete_incident as a model-proposed decision and makes Commit & Effects the only durable incident transition writer. Notion also describes a later INCIDENT_COMPLETION private event flow. MVP-018 intentionally promotes only the smallest existing USER_MESSAGE commit boundary for completing the current active incident; the private event flow stays parked.

Local implementation truth comes from completed MVP-011, MVP-012, MVP-013, MVP-014, MVP-015, MVP-016, and MVP-017.

Goal

Let an opted-in USER_MESSAGE turn complete the currently active incident through Commit & Effects and the InMemoryLifeIncidentStore, expose a query-visible life_incident_completed raw log entry, and add no timer, scheduler, body, Live2D, proactive-message, follow-up incident, or private INCIDENT_COMPLETION behavior.

Current Scope

  • One event family remains in scope: USER_MESSAGE.
  • One new model-proposed life action subtype is in scope: complete_incident.
  • The turn must opt in to incident completion explicitly; default visible-reply turns keep the current MVP-017 allowed action set and parser behavior.
  • Completion applies only to the active incident for the validated user/conversation scope derived from the source event.
  • The complete action must identify the current active incident by incident_id.
  • Commit & Effects validates the role-model result, re-reads and validates the active incident, builds the completion log entry, and finalizes completion through the store.
  • InMemoryLifeIncidentStore remains the concrete in-memory incident boundary and must make read_active_incident(request) return None for the completed scope after success.
  • The successful completion raw log must be visible through the existing Raw Event Log query/debug surface.

Explicit Non-Goals

  • No INCIDENT_COMPLETION RuntimeEvent, timer, scheduler, private incident-completion role-model call, completed-incident context builder field, or proactive message.
  • No resume_incident, go_idle, no_change, interruption policy, background incident behavior, replacement behavior, incident queue, or follow-up incident chain.
  • No body effect, living-state patch, Live2D status, tool request, retrieval/indexing behavior, database storage, migration, debug UI, or replay execution.
  • No composition of incident completion with state patches, incident start, or incident cancel in the same model-call contract.
  • No default completion wiring in ordinary user turns; callers must opt in and provide the concrete completion boundary.
  • No history query API in InMemoryLifeIncidentStore; the raw log is the truth for the completed transition in this slice.

Minimal Schema

CharacterDecision Extension

type CharacterDecision = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  action: "visible_reply"
  visible_reply: { text: string }
  life_action?: {
    type: "complete_incident"
    incident_id: string
  }
}

The action stays a visible-reply turn with an optional life action, matching the MVP-012 start and MVP-017 cancel pattern. The allowed life-action subtype is selected by the caller's explicit complete opt-in.

LifeIncidentCompleteCommitRequest

type LifeIncidentCompleteCommitRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  life_action_type: "complete_incident"
  incident_id: string
  user_id?: string
  conversation_id?: string
}

LifeIncidentCompleteFinalizeRequest

type LifeIncidentCompleteFinalizeRequest = LifeIncidentCompleteCommitRequest & {
  commit_time: string
  active_incident: ActiveIncidentSnapshot
  completed_incident: {
    schema_version: "0.1"
    incident_id: string
    type: string
    status: "completed"
    title: string
    started_at?: string
    expected_end_at?: string
    actual_end_at: string
    remaining_seconds?: number
    interrupt_policy: "interruptible" | "background" | "protected"
    resume_policy: "resume" | "ask_model" | "cancel"
    source_event_ids: string[]
  }
  committed_log_entry: RawEventLogEntry<"life_incident_completed">
}

completed_incident.source_event_ids should preserve the active incident's source IDs and append the completing event_id once. The existing active-incident read validator remains active-only; a completed snapshot is only a commit/log artifact in this slice.

Functional Requirements

ID Requirement
FR-1 Add a shared COMPLETE_INCIDENT_ACTION = "complete_incident" contract constant and a narrow normalizer for life_action.complete_incident that requires only type and a non-empty incident_id.
FR-2 Extend the current subtype-specific life_action opt-in path to support exactly one of start, cancel, or complete. A caller may allow incident start, incident cancel, or incident completion, but never more than one and never alongside state patch in this slice.
FR-3 Render complete-specific instructions only for the complete opt-in, while reusing the existing LIFE_ACTION allowed-action envelope and carrying allowed_life_action_type = "complete_incident" so direct Role Model input validation cannot swap subtype parsing by changing only instructions.
FR-4 When complete is not opted in, reject life_action.complete_incident before commit through the existing role-model parsing/validation failure path.
FR-5 Add a new commit_effects.incident_complete boundary that builds a complete commit request from a normalized USER_MESSAGE event and role-model result, returning skipped when the decision has no life action.
FR-6 The complete commit boundary must read/validate the active incident for the source-event scope before finalizing, reject if there is no active incident, and reject if the requested incident_id does not match the current active incident.
FR-7 On success, Commit & Effects builds one life_incident_completed raw log entry and finalizes completion through the injected finalizer/store before the assistant visible reply is committed.
FR-8 InMemoryLifeIncidentStore must implement the complete finalization boundary, add life_incident_completed to runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, stage the success log through the existing expose_committed_success_entry() helper, clear only the matching active incident scope after Commit & Effects confirms raw-log visibility, and return copy-safe results.
FR-9 After a successful completion, read_active_incident(request) for the same scope returns None; other identified scopes remain unchanged.
FR-10 If finalization fails, raw-log success visibility staging fails, post-confirm incident-clearing completion fails or observes a changed active incident, the store/log instances differ, no active incident exists, incident IDs mismatch, or a storage/source adapter raises unexpectedly, Commit & Effects returns a structured rejected result and appends a life_incident_complete_rejected log through the ordinary raw-log path. Failures before visibility confirmation must leave the active incident unchanged and no query-visible complete success entry. Failures after visibility confirmation intentionally leave the already-confirmed life_incident_completed entry query-visible and add a later life_incident_complete_rejected audit entry.
FR-11 The successful life_incident_completed entry must be visible through raw_event_log.query() and must agree with the commit result on trace ID, event ID, incident ID, completion time, and committed log entry ID.
FR-12 The implementation must reuse, move, extract, or compatibility-export existing shared code surfaces instead of duplicating them: runtime.contracts.validate_normalized_user_message_event(), normalize_role_model_turn_result(), the existing normalize_life_action() subtype dispatch, normalize_start_incident_life_action(), normalize_cancel_incident_life_action(), VISIBLE_REPLY_ACTION, LIFE_ACTION, START_INCIDENT_ACTION, CANCEL_INCIDENT_ACTION, character.state.current.build_active_incident_request(), validate_active_incident_request(), validate_active_incident_snapshot(), runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, runtime.logging.confirm_committed_success_entry_visibility(), runtime.logging.discard_committed_success_entry_visibility(), InMemoryLifeIncidentStore.read_active_incident(), the raw-log protocol's expose_committed_success_entry(), character.state.incidents._incident_scope_from_request(), _drop_none_identity_fields(), role_model.loop._validate_allowed_actions(), _allowed_life_action_type_for_call(), _validate_allowed_life_action_type(), _life_action_allowed(), and _instructions_for_allowed_actions(). The current start/cancel subtype handling must be extended or extracted, not copied into a parallel parser.
FR-13 runtime.user_turn may coordinate the optional complete boundary like the start and cancel boundaries, but it must keep one write-action opt-in per USER_MESSAGE turn and must require an active-incident source for completion.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep the implementation small and parallel to the proven incident-cancel boundary where that reduces risk.
  • Keep Commit & Effects as the only writer for completion; the role model proposes, and the store only finalizes validated commit requests.
  • Keep InMemoryLifeIncidentStore scoped, copy-safe, and in-memory only.
  • Keep tests deterministic with fake clocks, fake IDs, fake adapters, and in-memory stores/logs.
  • Do not add generalized incident lifecycle abstractions unless they remove real duplication across the implemented start, cancel, and complete actions.

Acceptance Criteria

  • MVP-017 is recorded under completed plans, and this file is the only active implementation slice.
  • A complete-opted-in USER_MESSAGE turn can parse life_action.complete_incident with incident_id.
  • The turn completes only the active incident for the source-event scope through Commit & Effects and InMemoryLifeIncidentStore.
  • A successful completion clears the active incident for that scope and exposes one query-visible life_incident_completed raw log entry.
  • No active incident is cleared when there is no active incident, the incident ID mismatches, finalization rejects, visibility staging fails, the active incident changes before completion, or the store/log instances differ.
  • Default visible-reply turns, state-patch opt-in turns, incident-start opt-in turns, and incident-cancel opt-in turns keep their current behavior.
  • No INCIDENT_COMPLETION event, private completion call, completed-incident context field, proactive output, body/living-state/Live2D effect, scheduler, tool, retrieval, queue, database, or replay behavior is added.
  • The development journal records source context, files touched, checks run, review notes, next action, future ideas, and whether active slice scope changed.

Test Plan

Unit Tests

  • Normalize valid and malformed life_action.complete_incident decisions, including missing/empty incident_id, extra fields, and unsupported subtype in the wrong opt-in.
  • Render role-model input for complete opt-in and assert allowed actions, instructions, subtype marker, and the compact MVP-016 context envelope remain valid.
  • Assert start, cancel, complete, and state-patch opt-ins cannot be composed in one USER_MESSAGE model call.
  • Build and validate complete commit/finalize requests, completed incident snapshots, and life_incident_completed log entries.
  • Finalize complete through InMemoryLifeIncidentStore and assert same-scope active incident is cleared, other scopes remain, copies are safe, and query-visible success logs are staged/confirmed.
  • Reject no-active, incident-ID mismatch, raw-log mismatch, staging failure, and changed-before-completion paths without clearing the wrong active incident.
  • Reject when the active-incident source raises unexpectedly while reading the current active incident, with a structured life_incident_complete_rejected log and no query-visible completion success entry.
  • Reject when the completion finalizer raises an unexpected exception before raw-log success visibility is confirmed, leaving the active incident unchanged and no query-visible completion success entry.
  • Reject when post-confirm active-incident clearing raises unexpectedly after raw-log success visibility is confirmed, preserving the already-query-visible life_incident_completed entry and appending a later life_incident_complete_rejected audit entry.
  • Assert post-confirm completion failures return a rejected result while preserving the already-query-visible life_incident_completed entry and appending a later life_incident_complete_rejected entry.

Integration Tests

  • Start an active incident with the concrete store, then run a complete-opted-in USER_MESSAGE turn and assert the turn result, store read, and raw-log query all show the completion.
  • Run a complete-opted-in turn with no active incident and assert the user turn stops at the complete commit boundary with a rejection log and no visible assistant reply commit.
  • Run a complete-opted-in turn with a mismatched incident_id and assert the original active incident remains visible.
  • Run existing incident-start, incident-cancel, living-state patch, visible-reply-only, and full unittest discovery gates to prove current behavior did not widen or regress.

Implementation Boundaries

  • runtime.contracts owns shared action constants and life-action normalization.
  • role_model.loop owns allowed-action rendering, complete-specific instruction text, adapter invocation, output parsing, and role-model logs.
  • commit_effects.incident_complete owns complete commit request construction, active-incident validation, completion log construction, finalizer result validation, rejection logs, and success/rejection result envelopes.
  • character.state.incidents.InMemoryLifeIncidentStore owns scoped in-memory finalization and the existing read contract; it does not become a lifecycle history query API.
  • runtime.user_turn may coordinate the optional complete boundary in the same narrow way it coordinates incident start and cancel, but it should not own completion validation.
  • character.state.context should not change except through existing active-incident read behavior if tests need the current active incident in model context.

Review Notes

  • This is a minimal Commit & Effects complete boundary, not the private incident-completion event flow.
  • The highest risk is clearing active incident state without a query-visible success log; finalization must keep state and log visibility atomic.
  • The second risk is accepting completion for a stale or invented incident ID; Commit & Effects must re-read and match the current active incident for the event scope.
  • The main duplication risk is copying the incident-cancel module wholesale without extracting the shared commit/finalizer validation shape where it is actually common. Keep the extraction practical and covered by tests.
  • Review follow-up resolved that duplication risk by extracting the shared cancel/complete atomic lifecycle orchestration into commit_effects.incident_lifecycle; cancel and complete still own subtype-specific request parsing, snapshot construction, log schemas, and validation.
  • Implementation review must verify the complete success kind uses the existing atomic finalizer visibility path: ATOMIC_FINALIZER_SUCCESS_KINDS, expose_committed_success_entry(), confirm_committed_success_entry_visibility(), and discard_committed_success_entry_visibility().
  • Post-confirm completion failures follow the MVP-017 audit rule: once life_incident_completed visibility is confirmed, the commit boundary cannot hide that success entry, so it reports the later completion failure with a structured rejected result and a life_incident_complete_rejected entry in the same trace.
  • Implementation review must verify the Role Model Loop extends or extracts the current life-action subtype parser path instead of adding a third parallel parser.
  • Keep the raw log as the only completed-history truth for now; do not add store history APIs or persistent storage.
  • Do not add automatic time-based completion. A user message may complete an active incident only because the model proposed the opted-in complete action and Commit & Effects accepted it.

Open Questions

  • Should later persistent LifeIncidentStore retain completed incident history directly, or continue to derive it from the Raw Event Log? Not in MVP-018.
  • Should completion apply body, living-state, Live2D, or scheduler effects? Not in MVP-018.
  • Should expected-end timers emit private INCIDENT_COMPLETION events? Parked for a later event-intake slice.

Future Ideas Discovered During Planning

  • INCIDENT_COMPLETION RuntimeEvent intake after the user-message completion commit boundary is proven. Promoted as MVP-019.
  • Private incident-completion role-model call with completed_incident context and optional proactive output.
  • Resume, go-idle, and no-change incident lifecycle commit boundaries after complete is proven.
  • Runtime Kernel user-interruption policy that can mark incidents interrupted/background before a user turn.
  • Persistent incident lifecycle storage with transition history and migrations.
  • Body/living-state/Live2D effects for incident lifecycle transitions.
  • Retrieval indexing over incident lifecycle episodes once raw transition truth is stable.
