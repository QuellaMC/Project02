MVP-022 Runtime Component and Operation Registry v0.1

Status: implemented locally and verified; pending PR

Created: 2026-05-31. Active branch: feature/runtime-component-registry.

Source Context

Product direction remains the Notion Live Character Framework, especially 02 - Runtime Architecture, 02A - Runtime Kernel & Operation Routing, 03 - Role Model Loop & Decision Contract, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace. Notion allows an internal operation registry, but the registry must carry schema/contract, policy, privacy/redaction, logging, transaction, and handler ownership instead of being a bare dispatch table.

Local baseline: PR #26 added provider-owned DecisionContext.context_sections, PR #27 added staged commit transaction helpers, and PR #28 added UserTurnWriteActionModule and ModelActionSpec. This slice turns those seams into a component-owned operation foundation for the current user-turn and incident-completion paths before memory, tools, scheduler, Live2D, or productivity actions are added.

Goal

Add a static in-process component registry plus an executable operation registry for built-in runtime components. The first concrete callers are runUserMessageTurn for USER_MESSAGE turns and the deterministic INCIDENT_COMPLETION route for incident-completion event commits. Both callers should consume registry-derived operation handlers while preserving current observable behavior.

Implementation update: the v0.1 static registry, operation registry, RuntimeAccess, user-turn operation routing, and deterministic incident-completion operation routing are implemented and locally verified on feature/runtime-component-registry. The implementation remains limited to built-in in-process components and does not add memory, retrieval, tools, scheduler, Live2D, dynamic plugins, or external effects. June 2 follow-up: current-state, active-incident, and interrupted-incident read sources now use the same registry-backed adapter path as recent visible messages and context sections.

Current Scope

  • Define RuntimeComponent with id, version, enabled, operations, userTurnActions, modelActionSpecs, and contextSectionProviders.
  • Define RuntimeOperationRegistry and an internal RuntimeAccess facade for validated in-process operation execution. This is not a separate top-level architecture box.
  • Use runUserMessageTurn as the first user-turn operation caller with caller.component_id = "runtime.user_turn" and call_type = "user_turn".
  • Use the existing INCIDENT_COMPLETION route as the deterministic event-commit caller with caller.component_id = "runtime.kernel", call_type = "deterministic_event_commit", model_needed = false, and next_step = "incident_completion_commit".
  • Register built-in components only for existing behavior: visible_conversation, role_model, context_sections, living_state when a living-state write action is enabled, and incident_lifecycle when an incident action or deterministic incident-completion commit is enabled. Do not add an empty core component before it owns a concrete operation.
  • Register executable operations that wrap existing behavior: visible_conversation.commit_user_message, role_model.run_turn, visible_conversation.commit_visible_reply, living_state.commit_patch, incident.interrupt_active, incident.start_from_model, incident.cancel_from_model, incident.complete_from_model, incident.complete_from_event, visible_conversation.read_recent_messages, character_context.build_sections, character_state.read_current, incident_lifecycle.read_active, and incident_lifecycle.read_interrupted.
  • Define operation input/output contract validators for each registered operation. Contract IDs are metadata; validators are the executable contract.
  • Define and enforce baseline operation policy: allowed callers, allowed call types, allowed event types, operation category, permission policy ID, privacy/redaction policy, logging policy, transaction policy, and synchronous execution policy.
  • Switch the full user-turn integration path to registry-derived operations/actions/specs/providers instead of keeping a parallel direct-options production path.
  • Preserve existing user-turn result fields, stop codes, role-model envelope fields, visible transcript ordering, commit-effect semantics, and existing commit/reject raw logs unless the active spec explicitly adds operation audit logs.

Explicit Non-Goals

  • No memory retrieval component implementation yet.
  • No memory writes, tool requests, productivity actions, Live2D, assets, scheduled directives, dynamic imports, hot-loaded plugins, marketplace modules, sandboxing, or background workers.
  • No public plugin API and no external component package loading.
  • No operation category that can touch external systems, money, accounts, user files, calendars, messages, private documents, or network services.
  • No database adapter, migration, durable storage technology choice, or cross-process locking.
  • No broad rewrite of Runtime Kernel, Character State Engine, Role Model Loop, or Commit & Effects. Operations wrap existing boundaries; they do not move ownership.

Minimal Types

Persisted runtime records remain at schema_version: "0.1". This slice may add new raw-log kinds for operation audit records, but it must not change the meaning of existing persisted fields. 

type RuntimeComponent = {
  id: string;
  version: string;
  enabled: boolean;
  operations?: RuntimeOperationDefinition[];
  userTurnActions?: UserTurnWriteActionModule[];
  modelActionSpecs?: ModelActionSpec[];
  contextSectionProviders?: DecisionContextSectionProvider[];
};

type RuntimeOperationRequest = {
  schema_version: "0.1";
  trace_id: string;
  event_id: string;
  event_type: "USER_MESSAGE" | "INCIDENT_COMPLETION";
  caller: {
    component_id: string;
    call_type: "user_turn" | "deterministic_event_commit" | "test";
  };
  op: string;
  input: unknown;
};

type RuntimeOperationResult = {
  schema_version: "0.1";
  trace_id: string;
  event_id: string;
  op: string;
  owner_component_id: string;
  status: "succeeded" | "rejected" | "succeeded_with_audit_failure";
  output?: unknown;
  failure?: {
    stage: string;
    code: string;
    message: string;
  };
  committed_log_entry_ids?: string[];
};

type RuntimeOperationDefinition = {
  op: string;
  owner_component_id: string;
  input_contract_id: string;
  output_contract_id: string;
  validate_input: (request: RuntimeOperationRequest) => unknown;
  validate_output: (output: unknown, request: RuntimeOperationRequest) => unknown;
  policy: RuntimeOperationPolicy;
  privacy: RuntimeOperationPrivacyPolicy;
  logging: RuntimeOperationLoggingPolicy;
  transaction: RuntimeOperationTransactionPolicy;
  execution: RuntimeOperationExecutionPolicy;
  handler: (request: RuntimeOperationRequest, input: unknown) => unknown;
};

Policy Contracts

  • Operation category: v0.1 supports read, context_build, model_call, visible_effect, state_write, and life_action. External actions are rejected in this slice.
  • Caller policy: each operation declares exact allowed_callers, allowed_call_types, and allowed_event_types. Unknown caller IDs, unsupported call types, and event-type mismatches are rejected before handlers run. User-turn operations allow runtime.user_turn/user_turn/USER_MESSAGE; the incident-completion event operation allows only runtime.kernel/deterministic_event_commit/INCIDENT_COMPLETION.
  • Permission policy: v0.1 supports only internal_runtime_only and test_only. internal_runtime_only rejects non-runtime. callers even if they appear in allowed_callers; test_only requires call_type = "test". No model output or component can bypass Commit & Effects validation.
  • Privacy and redaction policy: each operation declares whether request input and handler output are logged as full, redacted, or omitted. Model raw output and private internal payloads must not be duplicated into operation audit logs if an existing domain log already stores them.
  • Logging policy: every production operation uses mode = "required" and appends runtime_operation_started before handler invocation and runtime_operation_completed or runtime_operation_rejected after validation/handler result. disabled_for_tests is valid only with test_only. The audit record includes operation name, owner component, caller, policy IDs, trace ID, event ID, and redacted snapshots according to policy. Read and context-build operations log envelope metadata with input/output snapshots omitted; model-call operations reference existing role-model logs without duplicating full model input/output; commit/effect operations keep their existing domain logs and add only the operation envelope.
  • Transaction policy: read operations must use read_only; context_build and model_call operations must use none; visible_effect, state_write, and life_action operations must use existing_commit_effect_atomic and must delegate durable mutation to the existing Commit & Effects function and staged finalizer where applicable.
  • Execution policy: v0.1 supports only sync_in_process. If a handler returns a Promise-like result, RuntimeAccess rejects the operation with async_operation_not_supported. Queue, background, and external tool execution modes are future slices.
  • Failure policy: validation, policy, handler, output-validation, and pre-handler or rejection audit failures return a structured rejected operation result and append an operation rejection log when a normalized event identity is available. If runtime_operation_completed append fails after a handler has returned validated output, RuntimeAccess.execute returns succeeded_with_audit_failure with the validated output and logging failure instead of rejected; callers must not treat that path as retry-safe because durable Commit & Effects work may already have happened. Malformed operation request envelopes with schema, trace, event, event-type, and operation identity return a structured request_validation rejection; malformed envelopes without that identity may still throw as programmer errors.

Functional Requirements

  • FR-1: Registry construction accepts readonly built-in component definitions and returns immutable derived views.
  • FR-2: Duplicate enabled component IDs, duplicate enabled operation names, duplicate user-turn action IDs, duplicate model action spec IDs, and duplicate context section provider IDs are rejected.
  • FR-3: Disabled components are omitted from all derived views and their operations cannot execute.
  • FR-4: RuntimeAccess.execute validates operation request envelope fields before lookup, and returns structured request_validation rejections for malformed envelopes that still carry normalized event identity.
  • FR-5: Operation execution validates caller, call type, event type, permission policy, input contract, output contract, logging policy, privacy policy, transaction policy, and execution policy.
  • FR-6: Operation execution appends operation audit logs using the active raw event log without replacing existing domain-specific raw logs. A failed completed-audit append after handler success reports succeeded_with_audit_failure, not operation rejection.
  • FR-7: Operation handlers for commit/effect behavior call existing Commit & Effects functions and must not write stores or visible output directly.
  • FR-8: runUserMessageTurn uses registry-derived operations for its current spine and write-action integrations without changing committed/stopped result shape.
  • FR-9: Role-model action specs still render and parse the same allowed_actions, allowed_life_action_type, and instructions as PR #28.
  • FR-10: Context section providers still use the PR #26 request, validation, duplicate-section, and clone-safety semantics.
  • FR-11: Operation audit logs do not duplicate full model input/output snapshots; they reference the existing role-model log through trace/event/operation identity.
  • FR-12: Direct dependency injection may remain inside component factory functions and low-level tests, but production user-turn integration must not keep a second direct-options bypass for registered actions/specs/providers/operations.
  • FR-13: The deterministic INCIDENT_COMPLETION path executes incident.complete_from_event through the operation registry, preserves the existing life_incident_completed/life_incident_complete_rejected domain logs, and never calls the model or emits visible conversation output.
  • FR-14: User-turn context reads for current state, active incident, and interrupted incident execute through RuntimeAccess before reaching the existing source contracts. Malformed read outputs are rejected before model adapter invocation through the registry-backed path.

Implementation Boundaries

  • Runtime registry: owns static component validation, derived views, operation lookup, policy validation, privacy/logging enforcement, and operation execution envelopes.
  • Runtime Kernel: remains owner of event intake, normalization, priority, route policy, and deciding user-turn route. It may call the registry but does not become a generic component host.
  • Character State Engine: remains owner of compact context building, provider section validation, current-state reads, active-incident reads, and interrupted-incident reads. The registry only mediates the runtime-facing call.
  • Role Model Loop: remains owner of model input rendering, adapter invocation, output parsing, and model action spec contract validation.
  • Commit and Effects: remains the only durable commit/effect boundary. Operation handlers for writes call existing commit-effect functions.

Review Notes

  • This slice intentionally lays the foundation before memory/tools/scheduler/Live2D so those features register operations instead of becoming hardcoded branches.
  • Queued memory extraction jobs, background execution, and external tool flows are not implemented; MVP-022 marks them unsupported through the sync_in_process execution policy instead of silently accepting async handlers.
  • Keep the first callers concrete: runUserMessageTurn and the existing INCIDENT_COMPLETION deterministic route. Do not design for external plugins while implementing v0.1.
  • Runtime Access is an internal execute facade over the registry, not a revived top-level Runtime Access Kernel.
  • If a registered operation needs a policy not listed here, the behavior is outside this slice unless the active spec is reviewed again.
  • Memory retrieval should be the first future component after this registry, but only as compact selected context. Memory write should wait for a commit/effect boundary.
  • The June 2 adapter migration keeps the proposed architecture staged: runtime orchestration calls RuntimeAccess, the built-in operation adapter validates the envelope and delegates, and the existing domain source remains responsible for the read contract. This is intentionally not a full migration of Character State Engine or incident lifecycle modules into component implementations.

Open Questions

No scope-blocking questions remain for v0.1. The widened scope intentionally includes the existing INCIDENT_COMPLETION deterministic commit path, component-prefixed operation names, and operation envelope audit logs for every registered operation with snapshots omitted or redacted according to policy.

Future Ideas

  • Add memoryRetrievalComponent after this registry, using DecisionContext.context_sections to pass compact retrieved context.
  • Add memory write specs only after a memory commit/effect slice defines validation, logging, permissions, and durable records.
  • Add queued/background operation execution after a concrete memory extraction or external tool slice defines scheduler ownership, durable queue records, retry policy, and result events.
  • Add safe tool/productivity components only after a tool request/result event flow exists.
  • Add external-action permission policy, user confirmation rules, and redaction adapters when the first safe external tool is implemented.
  • Add dynamic plugin loading, sandboxing, marketplace modules, and external component packages only after multiple built-in components prove the static contract.
