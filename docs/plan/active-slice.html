MVP-006 - Real Model Tools And Character State Patch

Status: implemented locally, PR review requested

Created: 2026-06-10. Updated: 2026-06-10. Active spec: docs/plan/active-slice.html. Previous slice archived at docs/plan/completed/mvp-005-structured-role-model-user-turn-foundation.html. Suggested implementation branch: feature/mvp-006-provider-tools-state.

Implementation Status

CT-01 through CT-05 are integrated in the local working tree. The runtime now accepts the versioned toolCalls decision shape, preserves MVP-005 action.visible_reply compatibility parsing, can opt into the NVIDIA-compatible provider with --provider nvidia or PROJECT02_ROLE_MODEL_PROVIDER=nvidia, and keeps deterministic local chat as the default path.

Character State owns the current state fields, living-state brief, patch validation, no-op evidence, immutable before/after snapshots, and file-backed character-state.json storage under the existing per-session runtime directory. Inspect reads stored provider, tool-call, and state-patch evidence without replaying model calls or mutating stored state.

Automated tests use fake adapters and fake provider clients only. Manual NVIDIA smoke remains opt-in: set NVIDIA_API_KEY and run pnpm chat -- --provider nvidia. No live provider call is required for CI or local acceptance checks.

Parallel CT review found and resolved four integration risks before PR handoff: provider error diagnostics now redact echoed API keys, stored livingStateBrief text fails closed if it does not match state, public durable log reads compare accepted state-patch evidence against character-state.json, and trace summaries include provider/tool/state status while state writes wait until visible conversation logging succeeds.

Source Context

Product direction comes from the Notion project hub Live Character Framework, especially 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 06 - Character State Engine & Retrieval Management, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Long-term direction: the model receives a compact DecisionContext, may request scoped capabilities, and the runtime validates, commits, logs, and emits effects.

Local rebuild direction comes from AGENTS.md and AGENTS.repo.md. This slice keeps the rebuilt mainline small and runnable while deliberately adding the first real provider pressure and the first built-in model tool shape.

Current Product Before This Slice

MVP-005 gives the repo a structured role-model-shaped local user turn. A local/fake adapter returns a parsed CharacterDecision, the runtime validates the supported visible_reply action, commits visible conversation records, and stores role-model input/output, parsed decision, and commit evidence in the existing durable local logs. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> build DecisionContext from session, static character profile, recent visible messages, runtime notes
  -> local fake role-model adapter returns {"action":{"type":"visible_reply","text":"..."}}
  -> parse CharacterDecision
  -> validate visible_reply
  -> commit visible conversation and role-model evidence
  -> chat CLI prints Mira's reply

The limitation is now practical, not just architectural. The runtime still has no real model provider path, no provider prompt pressure, no model-facing tool registry, no optional model capability calls, and no durable current character state. Mira can keep visible conversation continuity, but she cannot persist a compact current state such as attention, mood, activity, or social stance unless a future subsystem invents its own path.

Product After This Slice

Local chat should be able to run with either the existing deterministic local adapter or an env-gated NVIDIA-compatible chat-completions provider. The model-facing contract should move from one hard-coded action to a small built-in tool system. The first tools are visible_reply and character_state.patch. The model may request a visible reply and may optionally request a character-state patch; the runtime still validates and commits everything. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> load CharacterRuntimeState
  -> build DecisionContext with recent visible messages and livingStateBrief
  -> render provider prompt with built-in tool schemas
  -> local adapter or NVIDIA provider returns toolCalls JSON
  -> parse and validate requested tool calls
  -> route character_state.patch validation to Character State
  -> validate all requested tool calls before intended mutation
  -> commit visible reply, accepted state patch, and evidence without intentional partial commits
  -> inspect shows provider, tool-call, state before/after, and rejection evidence

This is the first real-world pressure test for the role-model foundation. It should expose malformed JSON, provider errors, unsupported tool calls, state-patch mistakes, and prompt contract gaps while keeping the default local path deterministic and testable.

Goal

Add a minimal built-in model tool system, an env-gated NVIDIA role-model provider adapter, and a Character State module that owns state schema, brief creation, patch validation, and patch application. The runtime should accept model-requested visible_reply and optional character_state.patch tool calls only after validation, then commit visible conversation, state updates, and evidence through the existing runtime/log boundaries.

Core Design

The tool system is plugin-like in organization but built in for this slice. It does not load external plugins, execute arbitrary code, or expose direct mutation APIs to the model. 

Model-facing tool registry
  -> describes allowed tools and input schemas for the current call
  -> parses requested tool calls from model output
  -> rejects unknown, duplicate, missing, or disallowed tool calls

Character State module
  -> owns CharacterRuntimeState, living-state brief, state-patch validation, patch application
  -> does not call the model and does not own visible replies

Runtime commit path
  -> asks tool handlers to validate and plan effects
  -> commits accepted visible reply and state patch after validation
  -> logs before/after state, requested tool calls, accepted plans, and rejection reasons

From the model's perspective, character_state.patch is an optional tool. From the runtime's perspective, it is a proposed durable mutation that must be validated and committed by runtime-owned code. Both descriptions refer to the same object at different boundaries.

Current Scope

  • A built-in model tool registry for the user-turn role-model path.
  • Model-safe built-in JSON contract descriptions for visible_reply and character_state.patch, derived from local TypeScript validators rather than a general schema framework.
  • A versioned CharacterDecision shape based on ordered toolCalls.
  • Compatibility parsing for the existing MVP-005 action.type = "visible_reply" shape while the runtime migrates to tool calls.
  • A minimal Character State module with CharacterRuntimeState, LivingStateCurrent, LivingStateBrief, patch validation, patch application, and immutable snapshots.
  • A deliberately small state shape: mood, energy, attention, currentActivity, and socialOrientation, with tight enums and no history arrays.
  • In-memory and file-backed state storage integrated with the existing per-session local storage layout, without creating a second session root.
  • DecisionContext extension so the model sees livingStateBrief in addition to recent visible messages.
  • An NVIDIA chat-completions role-model provider adapter selected by CLI flag or environment default and authenticated only through environment variables.
  • Provider request rendering that instructs the model to return one JSON object with supported tool calls, not prose or markdown.
  • Provider response parsing, provider error mapping, timeout handling if needed, and raw provider evidence stored in existing role-model evidence snapshots.
  • Runtime validation before intended mutation for accepted visible_reply plus optional character_state.patch, without building a general cross-file transaction framework.
  • Inspect output for allowed tools, requested tool calls, provider metadata, state before/after, accepted state patch, and rejection evidence.
  • Default local chat, trace mode, durable sessions, inspect, and relay compatibility preserved.

Explicit Non-Goals

  • No committed API keys, tokens, provider secrets, or sample bearer tokens.
  • No live provider calls in automated tests; tests use fake adapters or injected fetch clients.
  • No streaming provider UX in this slice. The first provider path uses a complete non-streaming response for deterministic parsing.
  • No OpenAI, Anthropic, local LLM, or multi-provider abstraction beyond the one NVIDIA-compatible adapter and a narrow adapter interface.
  • No external plugin loading, package-based plugin API, dynamic tool discovery, or user-installed tool system.
  • No external side-effect tools, documents, calendars, accounts, web search, file actions, money, messages, or permission matrix.
  • No retrieval index, embeddings, memory search, exact source expansion, summaries, or context.retrieve(query).
  • No scheduler, scheduled directive store, timers, reminders, due events, background worker, or proactive delivery.
  • No life incidents, virtual body drift, need thresholds, Live2D semantic status, asset registry, or renderer integration.
  • No full Runtime Kernel, Character State Engine, Role Model Loop, or Commit and Effects Engine restoration from legacy/typescript.
  • No public API break for MVP-001 relay, MVP-002 conversation core, MVP-003 trace mode, MVP-004 durable sessions, or MVP-005 role-model evidence unless this draft is explicitly revised.

Parallel Child Tasks

This slice is intentionally shaped for five large, independently owned subthreads. CT-01 should freeze the shared model-tool contract before other threads depend deeply on tool-call shapes. CT-02 and CT-03 can proceed in parallel after the tool boundary is clear because the provider adapter only returns raw model output while Character State owns state semantics. CT-04 integrates the accepted contracts into runtime commit behavior, and CT-05 owns CLI, inspect, docs, live smoke, and integration review.

  • CT-01 - Built-In Model Tool Registry
  • CT-02 - NVIDIA Provider Adapter
  • CT-03 - Character State Core
  • CT-04 - Runtime Commit Integration
  • CT-05 - CLI, Inspect, Docs, And Review

Coordination Notes

  • CT-01 owns the generic tool-call envelope, tool names, cardinality rules, parsing, compatibility conversion, and rejection taxonomy.
  • CT-02 owns provider HTTP mapping, env config loading, injected adapter/client creation, fake-client tests, and provider errors. CT-02 does not own final chat CLI flag parsing.
  • CT-03 owns character_state.patch input semantics, state field enums, default state, the single state store API/path, patch validation, patch application, and no-op patch evidence.
  • CT-04 owns runtime orchestration and calls CT-03 APIs. It must not revalidate state enums or create a second state validator.
  • CT-05 owns public CLI flags, env-vs-CLI precedence documentation, inspect formatting, docs, live smoke instructions, and final integration review.

Implementation Boundaries

  • A new model-tool module owns built-in tool metadata, allowed-tool filtering, tool-call parsing, compatibility conversion, and generic tool rejection reasons.
  • The visible reply tool should wrap existing reply validation and commit behavior instead of copying one-line reply validation or visible message allocation.
  • The Character State module owns state types, defaults, brief projection, patch validation, and patch application. Other modules should not duplicate state enum validation or state merge rules.
  • The character-state tool is a thin built-in adapter that exposes model-safe schema and routes validation/planning into Character State.
  • The NVIDIA provider adapter owns HTTP request/response mapping only. It should not know how to commit visible replies or apply character state.
  • The Role Model Loop owns prompt/envelope rendering, provider/local adapter invocation, raw output capture, and parsed decision snapshots.
  • The commit path owns validation-before-mutation ordering, fail-closed rejection evidence, and commit orchestration for visible conversation plus accepted state patches. It should not build a broad cross-file transaction framework for this slice.
  • The existing local storage, file runtime log store, and session store remain the only durable local storage layout for this slice.
  • src/chat-cli.ts owns terminal UX, provider selection flags, session flags, trace output, and clear error messages.
  • src/inspect-cli.ts owns read-only debug output and must not mutate runtime state or call providers.
  • The relay command remains the MVP-001 smoke path and should not move into the model-tool path in this slice.

Minimal User Experience

  • pnpm chat should still work locally without an API key.
  • A provider-selected chat path should fail clearly when NVIDIA_API_KEY is missing.
  • A provider-selected chat path should call the configured model when --provider nvidia is passed or PROJECT02_ROLE_MODEL_PROVIDER=nvidia is set. The CLI flag wins over the environment default.
  • Accepted turns should print Mira's visible reply and may update Mira's current living state when the model requests character_state.patch.
  • Valid no-op state patches should be accepted and visible in inspect as no-op evidence.
  • Rejected provider output or invalid state patches should report a clear runtime error and must not append fake visible messages or intentional partial state changes.
  • pnpm chat -- --trace should keep JSON Lines trace summaries on stderr and may include provider/tool/state commit status when useful.
  • pnpm inspect -- --store <path> --session <session-id> should expose provider, tool-call, and state evidence without replaying or mutating a turn.

Review Decisions Requested

  • Slice status: this draft proposes adding the first real model provider and the first built-in model tool system before retrieval, scheduling, external tools, Live2D, or provider webhooks.
  • Provider scope: this draft proposes one NVIDIA-compatible provider path selected by CLI flag or environment default, non-streaming first, with fake-client tests and a manual live smoke path. CLI flags take precedence over environment defaults.
  • Tool-system scope: this draft proposes built-in model tools only. It does not propose external plugins, arbitrary tool execution, dynamic loading, or a permission matrix.
  • State ownership: this draft proposes that Character State owns all state logic; character_state.patch is only the model-facing built-in tool adapter.
  • Commit semantics: this draft proposes validation-before-mutation user-turn commits. If any required tool call or optional state patch is invalid, the turn rejects without intentional partial visible or state commits. Valid no-op state patches are accepted with explicit no-op evidence.
  • Secret handling: this draft treats any pasted provider key as exposed and requires environment variables only, with no committed secrets or docs that contain private tokens.
  • Compatibility: this draft preserves the local fake adapter as default and supports old MVP-005 visible-reply decision shape during migration.

Future Pressure

Once a real provider, built-in model tool registry, and Character State patch path are working, later slices can add streaming provider UX, retrieval as context.retrieve(query), external productivity tools, scheduled directives, incident lifecycle, virtual body, Live2D semantic status, provider webhooks, replay, or a real plugin mechanism. Those later slices should register capabilities through the built-in model-tool boundary rather than inventing separate model-output contracts.
