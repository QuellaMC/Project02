MVP-020 - Computed User Interruption Context v0.1

Status: implementation PR open

Created: 2026-05-24. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-020-computed-user-interruption-context. PR: #23.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 02A - Runtime Kernel & Operation Routing, 03 - Role Model Loop & Decision Contract, 04 - Event Triggers & Runtime Hooks, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 09 - MVP Roadmap & Open Questions.

Notion describes user messages as higher-priority than active life incidents, says the Character State Engine builds the model-facing context, and eventually wants a compact interrupted-incident context plus durable interrupted/background/resume behavior. MVP-020 intentionally takes only the smallest read-only context step: tell the model that this user turn interrupted an active incident, without changing incident status or adding a new action.

Local implementation truth comes from completed MVP-011, MVP-014, MVP-015, MVP-016, MVP-017, MVP-018, and MVP-019. The existing Character State Engine context builder already reads and validates a compact active_incident brief for normalized USER_MESSAGE events. MVP-020 derives the new flag from that same read instead of adding a second incident lookup or a parallel interruption boundary.

Goal

Add a read-only computed model-context flag so a USER_MESSAGE turn that sees an active_incident also exposes character_snapshot.user_message_interrupted_active_incident = true. This makes the interruption explicit to the model while preserving the current active incident snapshot and all existing commit behavior.

Current Scope

  • Only normalized USER_MESSAGE decision contexts are in scope.
  • When the existing active-incident source returns a valid active incident brief, Character State Engine includes the existing character_snapshot.active_incident and the new computed flag with value true.
  • When no active incident source is configured, or the source returns None, the flag is omitted and minimal contexts stay unchanged.
  • The flag is derived from the same validated active incident brief already used by MVP-011 and MVP-015. No additional source read is allowed.
  • Role Model Loop must accept and render the new field inside decision_context.character_snapshot without changing call_type, current event rendering, instructions, or allowed actions.
  • Existing state-patch, start-incident, cancel-incident, complete-incident, visible-reply, and incident-completion event paths must keep their current behavior.

Explicit Non-Goals

  • No durable interrupted status, background status, incident replacement, or active-incident mutation.
  • No interrupted_incident object, no resume_incident, no go_idle, no no_change, and no new model action.
  • No new Commit & Effects transition, raw-log kind, scheduler event, timer behavior, body effect, Live2D status, tool behavior, retrieval behavior, or asset behavior.
  • No Runtime Kernel priority or route-policy change. The existing USER_MESSAGE route remains the route.
  • No persistent database adapter, migration, completed/interrupted history API, debug UI, replay execution, or context-build raw log entry.
  • No broad DecisionContext reshaping. This slice adds one narrow optional field and keeps the current compatibility shape.

Minimal Schema

DecisionContext Character Snapshot

type DecisionContext = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  character_snapshot: {
    recent_visible_messages: RecentVisibleMessage[]
    living_state_brief?: LivingStateBrief
    active_incident?: ActiveIncidentBrief
    user_message_interrupted_active_incident?: true
  }
}

The new field is a computed presence flag. For MVP-020 it is present only with value true, and only when active_incident is also present for the same USER_MESSAGE context. The field is omitted when there is no active incident; no explicit false value is introduced in this slice.

Model-Facing Example

{
  "character_snapshot": {
    "active_incident": {
      "incident_id": "incident-1",
      "type": "eat",
      "status": "active",
      "title": "Eating lunch",
      "remaining_seconds": 600,
      "interrupt_policy": "interruptible",
      "resume_policy": "resume",
      "source_event_ids": ["event-incident-started"]
    },
    "user_message_interrupted_active_incident": true
  }
}

Functional Requirements

ID Requirement
FR-1 Extend the Character State Engine context-builder contract to allow character_snapshot.user_message_interrupted_active_incident as the only new context field.
FR-2 Set the flag to true only after the existing active-incident source returns a valid active incident brief for the current normalized USER_MESSAGE.
FR-3 Derive the flag from the already-read active_incident_brief; do not add a second active-incident read, new source protocol, new runtime event type, or Kernel policy check.
FR-4 Omit the flag when active_incident is absent because the active-incident source is missing or returns None.
FR-5 Reject malformed model-context inputs where the field is present without active_incident, or where the field value is anything other than true.
FR-6 Update Role Model Loop context validation so rendered model inputs preserve the new flag and continue rejecting unrelated future fields.
FR-7 Keep existing allowed-actions policy unchanged. The flag must not automatically enable cancel, complete, resume, state patch, or any other action.
FR-8 Keep copy-safety behavior: callers and sources must not be able to mutate the emitted context or active-incident brief after construction.
FR-9 Do not append a raw log entry, commit state, clear an incident, schedule an event, or emit a visible output because of this flag.
FR-10 Existing USER_MESSAGE, INCIDENT_COMPLETION, start, cancel, complete, visible-reply, and state-patch tests must keep passing without contract drift.

Non-Functional Requirements

  • Keep the implementation boring and local to the existing Character State Engine context builder and Role Model Loop validation/rendering seam.
  • Reuse existing active_incident brief validation and ActiveIncidentSource request construction.
  • Preserve deterministic behavior and avoid live model providers or external services in tests.
  • Keep the new schema field model-facing only. It is not a persisted runtime record and does not change source-of-truth incident state.
  • Avoid speculative abstractions for interruption policies. Full policy work remains parked until a later durable interruption slice.

Acceptance Criteria

  • A USER_MESSAGE context built with a valid active incident includes both character_snapshot.active_incident and character_snapshot.user_message_interrupted_active_incident = true.
  • A USER_MESSAGE context built without an active incident omits the flag and matches the existing minimal shape apart from unrelated configured sources.
  • The active-incident source receives the existing request shape exactly once per context build.
  • Role Model Loop accepts and renders the new field inside the decision context, while malformed or unrelated future fields are still rejected.
  • The flag does not change allowed actions, instructions, Runtime Kernel routing, raw logging, Commit & Effects behavior, or incident store state.
  • Relevant unit tests and full test discovery pass, and the journal records the files changed and commands run.

Implementation Boundaries

  • Character State Engine: owns computing and placing the read-only flag in DecisionContext.character_snapshot.
  • Role Model Loop: owns validating and rendering the updated context shape into the model input envelope.
  • Runtime Kernel: unchanged. It still normalizes and routes USER_MESSAGE as before.
  • Commit & Effects Engine: unchanged. No new transition or side effect is accepted because of the flag.
  • Persistence and logs: unchanged. Raw truth remains the existing active incident snapshot and runtime/model/commit logs.

Implementation Notes

  • The field name is shared through runtime.contracts.USER_MESSAGE_INTERRUPTED_ACTIVE_INCIDENT_FIELD.
  • character.state.context.build_character_decision_context() sets the flag only after the existing active-incident source returns a valid brief.
  • role_model.loop accepts the field only as literal true and only when active_incident is present in the same character snapshot.
  • No higher-level interruption policy refactor was needed for MVP-020. If a later slice adds durable interrupted_incident or multiple computed character-snapshot fields, promote shared character-snapshot validation into runtime.contracts then.

Review Notes

  • Do not introduce an InterruptedIncidentBrief yet. The active incident remains the only incident object in this context.
  • Do not create a second active-incident helper, flag helper, or policy layer unless the implementation otherwise duplicates real validation logic.
  • Do not infer emotional meaning from the flag. It tells the model the turn interrupted an active incident; the model still decides tone in the existing user-turn call.
  • Keep the flag coupled to active_incident presence. This avoids a broad boolean policy surface before durable interruption behavior is specified.
  • Future-compatible code may leave the validation shape easy to extend to interrupted_incident later, but must not implement that field now.

What It Stores Now

Nothing new is stored. The runtime still stores the same raw event, visible conversation, and incident records. MVP-020 only computes a model-facing view during context construction.

What It Does Not Store Yet

It does not store an interrupted status, remaining time adjustment, resume intent, interruption policy decision, background incident, or post-turn lifecycle action.

What Comes Later

A later durable interruption slice can decide whether an active incident becomes interrupted, continues in background, asks the model to resume, or is cancelled after the user turn. That later slice needs its own state transition, Commit & Effects validation, logs, and tests.

Open Questions

  • Should a later slice replace this presence flag with an explicit interrupted_incident object? Not in MVP-020.
  • Should interrupt_policy = "background" or "protected" produce different context flags? Not in MVP-020.
  • Should future contexts include an explicit false value when no active incident exists? Not in MVP-020.
  • Should the Runtime Kernel perform priority/policy interruption handling before context build? Not in MVP-020.

Future Ideas Discovered During Planning

  • Durable user-interruption lifecycle that records interrupted/background/protected outcomes.
  • resume_incident, go_idle, and no_change life-action commit boundaries after the read-only interruption cue is proven.
  • An interrupted_incident context object that can differ from active_incident after durable policy exists.
  • Context-build raw logs for explaining exactly why the flag was included.
  • Body and Live2D reactions to interruption after durable state transitions exist.
