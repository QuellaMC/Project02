MVP-007 - Minimal User Turn Orchestrator

Status: implemented and tested locally, pending review

Created: 2026-05-16. Implemented: 2026-05-16. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace.

Phase 1 calls for a minimal user turn loop where a USER_MESSAGE enters the Runtime Kernel, recent visible messages feed DecisionContext, the Role Model Loop calls the model, Commit and Effects stores the visible reply, and Raw Event Log records the turn.

Local implementation truth comes from MVP-001, MVP-002, MVP-003, MVP-004, MVP-005, and MVP-006. The narrow next step is to prove one end-to-end composition of the existing boundaries for a single USER_MESSAGE turn.

Goal

Add the smallest orchestrator that composes the already implemented pieces for one user message: Runtime Kernel intake and raw logging, user visible message projection, recent visible context reading, Role Model Loop execution through an injected fake adapter, and assistant visible reply commit. MVP-007 should prove boundary order, trace continuity, and the smallest authoritative USER_MESSAGE route update without adding concrete storage, character state, retrieval, tools, scheduling, a live model provider, or a new runtime event family.

Current Scope

  • One supported input event type: USER_MESSAGE.
  • One orchestration entry point for a single user turn, named by implementation review.
  • One injected RoleModelAdapter; tests use a fake adapter only.
  • One injected raw event log used by all participating boundaries.
  • One injected visible conversation boundary that can append visible records and read existing visible records through the MVP-006 source adapter in tests.
  • One success result envelope that reports the existing nested boundary results and committed visible record IDs.
  • Existing record shapes remain authoritative: normalized RuntimeEvent, UserVisibleMessage, RoleModelTurnResult, VisibleConversationOutput, and existing raw log entries.
  • The orchestrator copies returned snapshots so caller mutation cannot alter stored records or result details.
  • Focused integration tests cover successful composition, current-message exclusion from recent context, malformed input, malformed model output, and visible commit stop behavior.

Explicit Non-Goals

  • No concrete database, file store, migration, transaction manager, idempotency key store, pagination API, or persistent conversation log.
  • No new RuntimeEvent type beyond USER_MESSAGE.
  • No live model provider call, provider configuration, streaming, retry, timeout policy, or prompt expansion.
  • No new model action beyond the existing visible_reply action.
  • No Character State Engine package extraction, living state, virtual body, incidents, scheduled directives, active threads, retrieval index, keyword search, summaries, compaction, or replay UI.
  • No tool execution, permission matrix, user confirmation flow, Live2D status, assets, proactive message, scheduler, or background worker.
  • No rollback or reconciliation if a later boundary fails after an earlier append succeeds.
  • No broad Runtime Kernel route-policy rewrite. MVP-007 includes only one tested route update: USER_MESSAGE routes to model_needed = true and next_step = "user_turn".
  • No schema unification of user and assistant visible records; MVP-006 remains the read-side projection layer.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-007 should implement the contract in Python 3 and test it with unittest.

UserMessageTurnInput

type UserMessageTurnInput = {
  schema_version?: "0.1"
  type: "USER_MESSAGE"
  event_id?: string
  trace_id?: string
  created_at?: string
  payload: {
    text: string
    user_id?: string
    conversation_id?: string
  }
}

UserMessageTurnCommittedResult

type UserMessageTurnCommittedResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "user_turn_committed"
  kernel_route: RuntimeRouteResult
  user_visible_message_result: UserVisibleMessageCommitResult
  role_model_result: RoleModelTurnResult
  visible_reply_result: VisibleReplyCommitResult
  visible_record_ids: {
    user_message_id: string
    assistant_output_id: string
  }
}

MVP007 RuntimeRouteResult

type RuntimeRouteResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  model_needed: true
  next_step: "user_turn"
}

This route is authoritative for MVP-007. The orchestrator may call the Role Model Loop only after Runtime Kernel intake returns this route.

UserMessageTurnStoppedResult

type UserMessageTurnStoppedResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "user_turn_stopped"
  stopped_at:
    | "user_visible_message_commit"
    | "visible_reply_commit"
  kernel_route: RuntimeRouteResult
  user_visible_message_result?: UserVisibleMessageCommitResult | UserVisibleMessageRejectResult
  role_model_result?: RoleModelTurnResult
  visible_reply_result?: VisibleReplyCommitResult | VisibleReplyRejectResult
  failure: {
    code: string
    message: string
  }
}

Adapter-call and model-output parsing failures should keep the existing Role Model Loop behavior: append the existing role_model_turn_failed raw log entry and propagate the exception. MVP-007 should not invent a second model-failure envelope.

Functional Requirements

ID Requirement
FR-1 The orchestrator accepts one UserMessageTurnInput and validates it through a shared Runtime Kernel intake path that also powers RuntimeKernel.handle_event().
FR-2 The orchestrator appends exactly one runtime_event_received raw log entry for the normalized event before any visible conversation append or model adapter call, using the same raw-log append code path as RuntimeKernel.handle_event().
FR-3 Runtime Kernel returns the authoritative MVP-007 USER_MESSAGE route: model_needed = true and next_step = "user_turn". The orchestrator includes this route as kernel_route and does not treat a logged-only route as compatible with a model call.
FR-4 The orchestrator preserves one trace_id and one event_id across the normalized event, user visible projection, Role Model Loop result, assistant visible reply commit, raw log entries, and final result envelope.
FR-5 After successful intake, the orchestrator calls the existing user visible message commit path exactly once before calling the model.
FR-6 If user visible message commit returns a rejected result, the orchestrator stops before the Role Model Loop and returns user_turn_stopped.
FR-7 For a valid projected user message, the orchestrator calls run_role_model_turn() exactly once with the normalized event, injected fake adapter, same raw event log, same clock, same ID generator, and a recent visible message source backed by visible conversation records.
FR-8 The current user message may already be present in the visible conversation log before context is built, but it must not be duplicated into recent_visible_messages; the existing current-event exclusion rules remain authoritative.
FR-9 Malformed model output or adapter exceptions keep the existing Role Model Loop failure behavior and must not append an assistant visible reply.
FR-10 When the Role Model Loop returns decision_ready_for_commit, the orchestrator calls the existing assistant visible reply commit path exactly once.
FR-11 If assistant visible reply commit returns a rejected result, the orchestrator returns user_turn_stopped and does not emit a fallback message.
FR-12 On success, the raw log append order is deterministic for this slice: runtime_event_received, user_visible_message_committed, role_model_turn_completed, visible_reply_committed.
FR-13 On success, visible conversation append order is deterministic: committed user visible message first, committed assistant visible reply second.
FR-14 The final success result returns copied nested result snapshots and the committed message_id / output_id pair.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep runtime behavior deterministic under injected clock, ID generator, fake model adapter, raw log, and visible conversation fake.
  • Do not call files, databases, network services, shell commands, live model providers, or system clocks from tests.
  • Keep implementation small and local; add at most one orchestration module plus the smallest Runtime Kernel intake helper needed to share normalized intake.
  • Do not duplicate Runtime Kernel normalize, append, or route code in the orchestrator. Extract or reuse a shared helper so RuntimeKernel.handle_event() and the orchestrator cannot drift.
  • Reuse existing boundary functions and validators instead of copying their validation logic into the orchestrator.
  • Keep failure behavior explicit and testable; do not hide runtime failures behind character language.

Acceptance Criteria

  • A valid USER_MESSAGE turn with a fake adapter returns user_turn_committed.
  • Runtime Kernel route semantics for USER_MESSAGE are updated to model_needed = true and next_step = "user_turn" through a tested shared route path.
  • The final result carries one stable trace_id and event_id through all nested results.
  • The raw log records one runtime intake, one user visible message commit, one role-model turn completion, and one assistant visible reply commit in order.
  • The visible conversation fake receives exactly two appends in order: user message, assistant reply.
  • Existing prior visible records flow into the Role Model Loop through VisibleConversationRecentMessagesSource.
  • The current user message is not duplicated in recent_visible_messages because it remains the current event.
  • Malformed initial input stops before raw logs, visible appends, and model calls according to the existing Runtime Kernel validation behavior.
  • Malformed model output appends the existing role-model failed log and does not append an assistant visible reply.
  • No concrete storage, state engine, retrieval, tool, Live2D, scheduler, background worker, or external service is added.
  • Future ideas discovered during planning are recorded in future-slices.html.
  • The development journal records files touched, tests run, review notes, and next action.

Test Plan

Unit Tests

  • Builds a success result envelope with copied nested results and stable IDs.
  • Stops before the model when user visible message commit returns a rejected result.
  • Stops after role-model success when assistant visible reply commit returns a rejected result.
  • Rejects or propagates malformed event input through the existing Runtime Kernel validation path.
  • Preserves copy isolation for visible record snapshots and returned result details.

Integration Tests

  • Runs one full user turn with in-memory raw log, in-memory visible conversation fake, deterministic IDs, deterministic clock, and fake model adapter.
  • Verifies RuntimeKernel.handle_event() and the orchestrator use the same intake helper and return the same MVP-007 route semantics for USER_MESSAGE.
  • Asserts raw log kind order: runtime_event_received, user_visible_message_committed, role_model_turn_completed, visible_reply_committed.
  • Asserts visible conversation append order and output IDs.
  • Seeds prior visible conversation records and verifies they appear in the rendered model input snapshot.
  • Verifies the current user message is excluded from recent_visible_messages even though it has already been projected to the visible conversation fake.
  • Verifies malformed model output appends role_model_turn_failed and no assistant visible reply.
  • Runs existing unit and integration tests for MVP-001 through MVP-006.

Implementation Boundaries

  • Runtime Kernel owns event normalization, ID assignment, and the first raw event log append.
  • Commit and Effects remains the only boundary that appends visible user and assistant records.
  • Role Model Loop remains the only boundary that renders model input, calls the adapter, parses output, and logs model success/failure.
  • The MVP-006 visible recent source remains the only bridge from committed visible records to RecentVisibleMessage.
  • The orchestrator owns only the order of existing boundary calls and the top-level result envelope.
  • Add a shared Runtime Kernel intake helper only if needed to expose the normalized event and route; RuntimeKernel.handle_event() must call the same helper rather than keeping a parallel normalize/append/route path.
  • The only route-policy behavior change in this slice is the USER_MESSAGE route from logged-only foundation behavior to model_needed = true and next_step = "user_turn".
  • Do not move existing context-building logic into a Character State Engine package in this slice.
  • Do not add a concrete combined read/write visible conversation store; tests can use a narrow fake that implements only the interfaces this slice already needs.

Implementation Results

  • Added a shared Runtime Kernel intake helper, intake_runtime_event(), that normalizes the event, appends the first raw log entry, routes the event, and is now used by RuntimeKernel.handle_event().
  • Updated the authoritative USER_MESSAGE route to model_needed = true and next_step = "user_turn"; tests no longer assert the old MVP-001 logged_only route.
  • Added runtime.user_turn.run_user_message_turn() as the thin orchestrator that composes existing Runtime Kernel, user visible projection, MVP-006 recent visible source, Role Model Loop, and assistant visible reply commit boundaries.
  • Preserved existing boundary ownership: Commit and Effects still appends visible user and assistant records, Role Model Loop still calls/parses the fake adapter, and Runtime Kernel still owns intake and route policy.
  • Added unit tests for stop envelopes when user visible projection or assistant visible reply commit returns a rejected result.
  • Added integration tests for successful end-to-end composition, shared route semantics with RuntimeKernel.handle_event(), malformed input, malformed model output, raw log order, visible append order, copy isolation, and current-message exclusion from recent_visible_messages.
  • PR review fix: recent visible context now allows a completed prior turn to contribute both its user message and assistant reply even though they share the same source_event_id; duplicate protection is now based on message_id plus the source_event_id / role pair.
  • No concrete storage, live model provider, Character State Engine package, retrieval index, tool execution, Live2D behavior, scheduler, rollback, or reconciliation was added.
  • Current verification: Ruff lint and format checks, mypy, compileall, full unittest discovery, HTML parser checks, and git diff --check passed after implementation.

Error And Fallback Behavior

  • Malformed event input raises the existing Runtime Kernel validation error before any append.
  • User visible message commit rejection returns user_turn_stopped and skips model work.
  • Adapter exceptions and malformed model output use the existing Role Model Loop failed-log behavior and propagate the existing exception.
  • Assistant visible reply rejection returns user_turn_stopped after the rejection raw log is appended.
  • No rollback, retry, reconciliation, or user-visible fallback is added.

Review Notes

  • MVP-007 is intentionally an orchestration slice with one route-policy correction, not a storage or state slice.
  • The sequence should prove that the MVP-001 through MVP-006 contracts already compose before expanding into Phase 2 character state.
  • Current-message exclusion is an important regression target because the user message is projected before the model sees recent conversation history.
  • Do not broaden this into route priority, interruption policy, real provider integration, context-build logging, or transaction semantics.
  • If implementation exposes a small kernel intake helper, document why the existing public API was insufficient, keep the helper specific to normalized intake plus route, and route RuntimeKernel.handle_event() through it.

Open Questions

  • Should the orchestrator eventually live under Runtime Kernel or a thin application service layer? MVP-007 should choose the smallest local placement and avoid package expansion until implementation pressure is real.
  • Should boundary failures eventually return one unified turn-failure envelope? Not in MVP-007; existing boundary failure behavior remains authoritative.

Future Ideas Discovered During Planning

  • Richer Runtime Kernel route policy for priority, interruption, and non-user-message event families after the MVP-007 user-turn route is proven.
  • Concrete append-only ConversationLog storage with read/write semantics and idempotency keys.
  • Transaction or reconciliation handling for partial visible projection failures.
  • Character State Engine context-builder extraction after another context source or state slice exists.
  • Context-build raw logging once debug or replay needs source-read traces.
  • Real provider integration behind the existing RoleModelAdapter after the fake-adapter flow is stable.
