User Turn Action Registry

Status: active implementation slice

Created: 2026-05-31. Active branch: feature/user-turn-action-registry.

Source Context

Product direction remains the Notion Live Character Framework, especially 02 - Runtime Architecture, 02A - Runtime Kernel & Operation Routing, 03 - Role Model Interface & Prompting, and 08 - Runtime Logging & Trace. The Notion direction says the runtime scopes allowed actions by event/call type, the role model proposes structured intents, and Commit & Effects remains the only durable write boundary.

Local trigger: issue 1 says runUserMessageTurn wires one option and branch for every current write capability. Issue 4 says Role Model input uses hard-coded allowed-action prompt/parse families. These issues share the same write-action/action-policy registration seam.

Merge update: PR #26 context provider sections and PR #27 staged commit transaction helpers are now part of main. This slice preserves both baselines and limits its own scope to user-turn write-action registration and role-model action policy registration.

Goal

Introduce a small concrete registry/spec abstraction for the existing user-turn write actions so user-turn orchestration consumes configured action modules and the role-model loop consumes configured model action specs. Preserve current behavior, ordering, statuses, raw logs, and public model input fields.

Current Scope

  • Move existing user-turn write-action wiring for living-state patch, incident start, incident cancel, incident complete, and incident interruption behind registry modules.
  • Keep visible user-message commit, role-model call, and visible-reply commit as the fixed user-turn spine.
  • Replace role-model write opt-in booleans with a model action spec for the existing state-patch and incident action policies.
  • Keep existing allowed_actions, allowed_life_action_type, and instruction strings in the rendered role-model envelope.
  • Keep the one write-action opt-in rule for a USER_MESSAGE turn.
  • Add tests proving current behavior still flows through registry/spec configuration rather than core switch chains.

Explicit Non-Goals

  • No memory writes, retrieval, tools, productivity actions, Live2D, assets, scheduled directives, or new commit-effect modules.
  • No redesign of DecisionContext beyond passing current context sources from action modules.
  • No schema version bump and no new persisted runtime record fields.
  • No change to raw log kind ordering or visible transcript ordering.
  • No broad operation registry, permission matrix, background worker, or plugin system.
  • No changes to PR #26 context_sections provider semantics.
  • No changes to PR #27 staged commit transaction helper semantics.

Minimal Schema

Persisted runtime records remain at schema_version: "0.1". This slice adds only in-process TypeScript configuration types for existing write-action modules and model action specs. It must not add a new durable action type or alter RuntimeEvent, RawEventLogEntry, CharacterDecision, or user-turn result field names.

Acceptance Criteria

  • runUserMessageTurn no longer imports each write-action commit implementation directly.
  • RunUserMessageTurnOptions exposes one write-action registry input instead of one option per write capability.
  • Existing state patch, incident start, incident cancel, incident complete, and incident interrupt behavior, stop codes, result fields, and log ordering are preserved.
  • Role-model rendering and parsing are driven by configured model action specs for existing write policies.
  • The rendered role-model envelope still uses the same allowed_actions, allowed_life_action_type, and instruction values as before.
  • The one write-action opt-in rule is enforced from registry/spec count rather than hard-coded booleans.
  • Future memory/tool/productivity write ideas are parked, not implemented.
  • Focused unit and integration tests pass, then full repo checks pass.

Implementation Boundaries

  • Runtime user-turn orchestration: keeps the fixed turn spine and delegates optional write commits to registered modules.
  • Runtime action modules: adapt existing Commit & Effects implementations into user-turn write-action modules with stop code, result field, preflight, context, and rejection behavior.
  • Role Model Loop: consumes a model action spec to render instructions, allowed actions, and parse policy without one boolean per write family, while preserving PR #26 context-provider forwarding.
  • Commit and Effects: existing commit implementations remain the only durable write/effect boundary, now including PR #27 staged transaction helper internals.

Review Notes

  • This is a refactor slice with behavior preservation tests; any behavior change must be explicitly called out and justified.
  • Keep registry modules concrete and boring. They should be configured from existing implementations rather than inventing generalized future operations.
  • Do not solve the broader DecisionContext envelope split or memory/tool policy shape in this slice.

Open Questions

  • Whether a later memory-write slice should add a new CharacterDecision field or a separate action envelope remains out of scope.
  • Whether action specs should eventually live in a shared runtime contract package should wait for a second event/call type.

Future Ideas

  • Add a memory-write action spec only when a memory commit-effect slice exists.
  • Add tool/productivity action specs only after a safe tool request/result slice defines permission and logging policy.
  • Promote the registry into a broader operation registry only after at least two event families need it.
