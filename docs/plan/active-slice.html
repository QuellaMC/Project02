Staged Commit Transaction Helper

Status: active implementation slice

Created: 2026-05-31. Active branch: feature/staged-commit-transaction-helper.

Source Context

Product direction remains the Notion project hub Live Character Framework. The Notion runtime notes keep the Commit & Effects Engine as the boundary that validates, commits durable state, appends Raw Event Log entries, and emits effects. Local implementation truth for this refactor comes from the current TypeScript source under src/commit-effects/, the raw-log visibility helpers in src/runtime/logging.ts, and the existing lifecycle helpers in src/commit-effects/incident-lifecycle.ts.

The issue target is a P2 refactor: repeated staged transaction flow in incident-start.ts, incident-cancel.ts, incident-complete.ts, incident-interrupt.ts, and living-state.ts. Current behavior must remain observable through the same statuses, failure stages and codes, success-log visibility, staged-visibility discard, and rejected raw-log entries.

Goal

Extract one concrete shared helper for the already-implemented staged commit transaction: call the finalizer, validate the finalizer result, confirm committed success-log visibility, run any post-visible hook, and preserve the caller's existing cleanup and rejection behavior when a transaction fails before durable success visibility.

Current Scope

  • Add focused regression tests for one success path and one staged-visibility rejection path through the helper.
  • Place the helper in src/commit-effects/incident-lifecycle.ts if it can stay narrow and dependency-light.
  • Refactor the duplicated finalizer/visibility/post-visible sequence in the five target commit-effect modules.
  • Preserve module-specific request building, snapshot building, log-entry building, result construction, rejection-log construction, and failure-stage mapping in each caller.
  • Keep the helper generic enough for the current living-state and incident callers without adding a framework/plugin layer.

Explicit Non-Goals

  • No user-turn orchestration changes.
  • No Role Model allowed-action, parser, or DecisionContext shape changes.
  • No memory, retrieval, scheduler, tool, Live2D, asset, or new runtime behavior.
  • No schema changes and no new persisted raw-log kinds.
  • No changes to the interruption semantics currently under separate audit.
  • No broad transaction framework, plugin system, storage abstraction, or new module tree.

Minimal Schema Fields

No schema fields are added or changed. Existing schema_version: "0.1" records, committed success log entries, rejected log entries, finalize request shapes, and finalize result shapes remain unchanged.

Functional Requirements

  • The helper must call any caller-provided raw-log requirement before finalization.
  • The helper must pass a defensive clone to the finalizer and post-visible hook.
  • The helper must validate the finalizer result through a caller-provided validator.
  • The helper must confirm committed success-log visibility through the shared raw-log helper after finalizer result validation.
  • The helper must run the caller-provided post-visible hook only after success-log visibility is confirmed.
  • Raw-log visibility validation errors must still map to malformed_finalize_result where callers currently do so.
  • Unexpected finalizer or post-visible hook errors must still map or propagate exactly as the current module does.
  • Callers must still append the same rejected log entries and return the same rejected result shape on handled failures.

Non-Functional Requirements

  • Keep the helper small, typed, and local to Commit & Effects.
  • Avoid any, non-null assertions, broad casts, and unused exports.
  • Keep existing tests behavior-oriented and avoid coupling tests to private implementation details.
  • Reduce duplication without hiding caller-specific lifecycle semantics.

Acceptance Criteria

  • The five target modules use the shared staged transaction helper for the duplicated finalizer/visibility sequence.
  • At least one existing success path exercises the helper and still exposes exactly one committed success log.
  • At least one staged-visibility failure path exercises the helper and discards staged committed success visibility before appending the rejected log.
  • All existing statuses, failure stages/codes, raw-log kinds, success-log visibility behavior, and rejection-log behavior are preserved.
  • pnpm check passes.
  • pnpm tsc -p tsconfig.json --noEmit --noUnusedLocals --noUnusedParameters passes.
  • The development journal records files changed, tests run, review notes, next action, and schema impact.

Implementation Boundaries

  • Commit and Effects: owns this helper and all changed callers.
  • Raw Event Logging: existing visibility helpers remain the only raw-log visibility mechanism.
  • Runtime Kernel, Character State Engine, Role Model Loop: unchanged.

Review Notes

  • Start incident intentionally treats post-visible hook failure as success after committed success visibility is confirmed.
  • Cancel and complete intentionally append a rejected log after post-visible hook failure while keeping the already confirmed success log visible.
  • Interrupt behavior is not being redesigned in this slice; preserve the current tested behavior even where prior audits flagged semantic drift.
  • Living-state has no post-visible hook; the helper must support that without inventing one.

Open Questions

  • Should living-state adopt a raw-log requirement hook like incident lifecycle finalizers?

Future Ideas

  • Consider a follow-up audit for the interruption post-visible rejection semantics; this slice preserves current behavior only.
