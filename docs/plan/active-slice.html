MVP-021 - Minimal Durable User Interruption Boundary v0.1

Status: implementation PR open

Created: 2026-05-25. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-021-minimal-durable-user-interruption-boundary. PR: #24.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 02A - Runtime Kernel & Operation Routing, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Notion says a user message wins over an active life incident, the runtime marks the incident as interrupted, background, or protected according to policy, and later context includes interruption context. Notion logging examples also call out the durable transition inc_123 active -> interrupted by USER_MESSAGE evt_456. MVP-021 implements the smallest pre-model step: one deterministic immediate policy outcome for each current interrupt_policy, with only "interruptible" moving state to an interrupted_incident.

Local implementation truth comes from completed MVP-011, MVP-014, MVP-015, MVP-016, MVP-017, MVP-018, MVP-019, and MVP-020. The existing code already has active-incident reads, in-memory active incident storage, query-visible start/cancel/complete logs, and a shared incident lifecycle helper. MVP-021 should extend those seams instead of adding a second incident store, second raw-log path, or parallel context validator.

Goal

When a normalized USER_MESSAGE arrives for a scope with one active incident, Commit & Effects evaluates the incident's interrupt_policy and records one deterministic query-visible outcome. "interruptible" moves active_incident to interrupted_incident; "background" keeps the active incident running and records that it continued in background; "protected" keeps the active incident running and records that interruption was protected.

Current Scope

  • Only normalized USER_MESSAGE events are in scope.
  • Only the existing one-active-incident-per-scope model is in scope.
  • All existing active-incident interrupt_policy values are in scope: "interruptible", "background", and "protected".
  • The policy outcome is deterministic runtime behavior. It does not require a model proposal, new model action, or proactive output.
  • The policy evaluation must run through Commit & Effects and produce exactly one success outcome when an active incident exists.
  • For interrupt_policy = "interruptible", the transition must use the incident store finalizer pattern, with raw-log visibility confirmed before active incident state is changed.
  • The interrupted snapshot preserves the active incident's identity and fields, changes status to interrupted, records interrupted_at, and appends the interrupting USER_MESSAGE event ID once to source_event_ids.
  • The in-memory incident store moves the matching scoped record out of the active slot and into one interrupted slot after the life_incident_interrupted success log is query-visible.
  • For interrupt_policy = "background", the active incident remains active and unchanged while Commit & Effects appends life_incident_continued_in_background.
  • For interrupt_policy = "protected", the active incident remains active and unchanged while Commit & Effects appends life_incident_protected_from_interruption.
  • Character State Engine gets a narrow read path for the latest interrupted incident in the same scope and may include character_snapshot.interrupted_incident after an interruptible transition. Background/protected outcomes continue to expose the existing active_incident context with the MVP-020 computed interruption cue instead of an interrupted incident because no durable background/protected incident state exists yet.
  • The existing MVP-020 computed flag remains compatible for read-only paths that still see an active incident, but the durable MVP-021 path should prefer the explicit interrupted_incident brief after an interruptible transition commits.

Explicit Non-Goals

  • No resume_incident, go_idle, no_change, post-turn life action, or incident restart behavior.
  • No background incident storage, protected deferral state, post-turn policy engine, or user-confirmed override. MVP-021 records only the immediate background/protected policy outcome and leaves the active incident unchanged.
  • No incident queue, multiple interrupted incidents per scope, recurring incidents, or replacement behavior.
  • No scheduler changes, timer events, body effects, Live2D status, assets, tools, retrieval, continuity writes, or proactive messages.
  • No new RuntimeEvent family and no broad Runtime Kernel priority rewrite. This slice uses the existing USER_MESSAGE route.
  • No persistent database adapter, migration, replay executor, debug UI, or external service.
  • No change to visible reply commit semantics. The interruption log is internal raw truth, not a user-visible message.

Minimal Schema

Interrupted Incident Snapshot

type InterruptedIncidentSnapshot = {
  schema_version: "0.1"
  incident_id: string
  type: "idle" | "eat" | "drink" | "sleep" | "rest" | "work" | "think" | "wait" | "custom"
  status: "interrupted"
  title: string
  started_at?: string
  expected_end_at?: string
  remaining_seconds?: number
  interrupt_policy: "interruptible"
  resume_policy: "resume" | "ask_model" | "cancel"
  interrupted_at: string
  source_event_ids: string[]
}

The snapshot is durable Commit & Effects output. It keeps the active incident's core fields unchanged except for the lifecycle status and interruption timestamp. It does not add a resume plan, background status, body effect, or model-authored meaning.

Interrupted Incident Brief

type InterruptedIncidentBrief = {
  incident_id: string
  type: string
  title: string
  started_at?: string
  expected_end_at?: string
  remaining_seconds?: number
  interrupt_policy: "interruptible"
  resume_policy: string
  interrupted_at: string
  source_event_ids: string[]
}

The model-facing brief omits status because the field name already carries the lifecycle state. Unlike the active incident brief, the interrupted brief is accepted only when it includes the current user message's event_id in source_event_ids, so a stale interrupted record from an older turn cannot replace current active context. Notion's conceptual interruption object can carry all interruption policies; MVP-021 narrows interrupted_incident to committed "interruptible" transitions and keeps background/protected context on the existing active-incident path until a later durable background/protected policy slice exists.

Policy Outcome

type UserInterruptionPolicyOutcome =
  | {
      outcome: "interrupted"
      kind: "life_incident_interrupted"
      active_incident: ActiveIncidentSnapshot
      interrupted_incident: InterruptedIncidentSnapshot
    }
  | {
      outcome: "continued_in_background"
      kind: "life_incident_continued_in_background"
      active_incident: ActiveIncidentSnapshot
    }
  | {
      outcome: "protected_from_interruption"
      kind: "life_incident_protected_from_interruption"
      active_incident: ActiveIncidentSnapshot
    }

Background and protected outcomes are durable raw-log facts, not new incident statuses in MVP-021. They do not move or rewrite the active incident.

Functional Requirements

ID Requirement
FR-1 Add a Commit & Effects interruption commit boundary for normalized USER_MESSAGE events that reads the current active incident through the existing active-incident read request shape.
FR-2 If no active incident exists for the event scope, return a deterministic skipped result and do not append an interruption outcome log or mutate incident state.
FR-3 If an active incident exists, branch by its validated interrupt_policy and produce exactly one supported outcome: interrupted, continued_in_background, or protected_from_interruption.
FR-4 For interrupt_policy = "interruptible", build an InterruptedIncidentSnapshot that preserves the active incident's identity, type, title, timing, interrupt_policy = "interruptible", resume policy, and prior source IDs; sets status = "interrupted"; sets interrupted_at from the injected clock; and appends the user event ID once.
FR-5 Expose exactly one query-visible life_incident_interrupted raw log for an interruptible transition. The log must include the normalized source event, the active incident snapshot, and the interrupted incident snapshot.
FR-6 For interrupt_policy = "background", leave the scoped active incident unchanged and expose exactly one query-visible life_incident_continued_in_background raw log containing the normalized source event, unchanged active incident snapshot, and outcome = "continued_in_background".
FR-7 For interrupt_policy = "protected", leave the scoped active incident unchanged and expose exactly one query-visible life_incident_protected_from_interruption raw log containing the normalized source event, unchanged active incident snapshot, and outcome = "protected_from_interruption".
FR-8 Use the same atomic visibility rule as start/cancel/complete for the interruptible state-moving path: if success-log staging, query confirmation, finalizer validation, or post-visible state change fails, keep the active incident unchanged and surface a structured rejected result plus rejected raw log where the existing lifecycle pattern requires one.
FR-9 Extend InMemoryLifeIncidentStore narrowly so successful interruptible interruption removes the scoped active incident only after the success log is visible and stores one latest interrupted incident for that scope. Background/protected outcomes must not move or rewrite the active incident.
FR-10 Add a read-only interrupted-incident source/request/brief path for Character State Engine context building. The request must reuse the current event identity fields, remain copy-safe, and accept an interrupted brief only when it is sourced from the current event.
FR-11 For USER_MESSAGE contexts built after an interruptible transition, include character_snapshot.interrupted_incident and omit a duplicate active_incident for the same incident. If an active incident is present, prefer the active context path and do not let an older interrupted record dominate it. For background/protected outcomes, keep the existing active_incident context path.
FR-12 Update Role Model Loop context validation/rendering to accept the new interrupted_incident brief while continuing to reject unrelated future context fields.
FR-13 Wire the user-turn orchestration only enough to run the deterministic interruption policy outcome before the model-facing context is built when the new dependencies are supplied. Treat the interruption finalizer as a durable write-action opt-in that is mutually exclusive with state patch, start, cancel, and complete opt-ins. Missing optional interruption dependencies must not break existing tests or existing no-interruption user turns.
FR-14 Do not add or enable resume_incident, go_idle, no_change, background mutation, protected mutation, scheduler, body, Live2D, tool, retrieval, continuity, or proactive-message behavior.

Non-Functional Requirements

  • Reuse existing lifecycle validation, raw-log, finalizer, and copy-safety patterns from incident start/cancel/complete before adding any new abstraction.
  • Name and reuse exact shared surfaces in implementation: commit_effects.incident_lifecycle helper functions, runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, confirm_committed_success_entry_visibility(), discard_committed_success_entry_visibility(), build_raw_log_entry(), build_active_incident_request(), validate_active_incident_request(), _incident_scope_from_request(), and _drop_none_identity_fields().
  • Keep the implementation deterministic and test-only. No live model provider, external service, or machine-local dependency is allowed.
  • Keep the new interrupted storage surface in memory only and scoped exactly like the existing active incident store. Background/protected outcomes add raw-log facts only.
  • Preserve existing USER_MESSAGE, start, cancel, complete, incident-completion, visible-reply, state-patch, and MVP-020 context behavior unless the new optional interruption boundary is explicitly supplied.
  • Keep errors explicit. Validation and finalizer failures must be inspectable through result status and raw logs, not hidden behind character language.

Acceptance Criteria

  • Given a scoped interruptible active incident and a normalized USER_MESSAGE, the interruption commit returns life_incident_interrupted, exposes a query-visible life_incident_interrupted raw log, clears the active incident read, and makes the interrupted incident readable for that scope.
  • Given a scoped background active incident and a normalized USER_MESSAGE, the policy commit returns life_incident_continued_in_background, exposes a query-visible log with that kind, and leaves the active incident unchanged and readable.
  • Given a scoped protected active incident and a normalized USER_MESSAGE, the policy commit returns life_incident_protected_from_interruption, exposes a query-visible log with that kind, and leaves the active incident unchanged and readable.
  • Given no active incident, the interruption boundary skips without raw-log or store mutation.
  • Given visibility staging, visibility confirmation, malformed finalizer result, or post-visible store conflict, the active incident remains active and the failure is surfaced consistently with the existing lifecycle failure pattern.
  • A USER_MESSAGE context can include character_snapshot.interrupted_incident after an interruptible transition, while background/protected contexts keep using character_snapshot.active_incident. Role Model Loop renders the context without allowing any new life action.
  • Supplying life_incident_interrupt_finalizer alongside another write-action opt-in is rejected during user-turn preflight before the user-visible message, interruption commit, model turn, or later write commit runs.
  • No test needs a live model provider, Notion, external service, concrete database, scheduler, Live2D renderer, asset system, or background worker.
  • Relevant unit tests, integration tests, full unittest discovery, Ruff lint/format, mypy, source compilation, HTML parsing, and git diff --check pass before implementation is called complete.

  • Extend user-turn integration coverage so background and protected active incidents produce their query-visible policy logs before model input rendering while the fake adapter still sees character_snapshot.active_incident.

Implementation Boundaries

  • Runtime Kernel: unchanged except that the existing user-turn path may receive optional interruption dependencies. No new route policy matrix is introduced.
  • Commit & Effects Engine: owns validating and committing the three immediate interruption policy outcomes, raw-log entries, rejected results, and interruptible finalizer contract.
  • Character State Engine: owns the read-only interrupted-incident context brief after Commit & Effects has created durable interrupted truth. It keeps the active-incident context path for background/protected outcomes.
  • Role Model Loop: owns accepting and rendering the new context field only; it does not parse a new life action.
  • LifeIncidentStore: owns the in-memory active-to-interrupted movement and read surface for the current scope. It does not store background/protected status in MVP-021.

  • Add only LIFE_INCIDENT_INTERRUPTED_KIND to runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS because it is the only MVP-021 success kind that moves incident state through a finalizer.
  • The new commit path is deterministic and should not depend on RoleModelTurnResult. If the shared lifecycle helper is too role-model-action-specific, extract only the proven shared validation/log/finalizer helpers needed for this deterministic path.
  • Reuse append_lifecycle_source_event_id_once(), validate_lifecycle_source_event_ids(), require_matching_lifecycle_field(), require_lifecycle_finalizer_raw_event_log(), validate_lifecycle_committed_log_entry(), validate_lifecycle_finalize_result(), build_lifecycle_failure(), build_lifecycle_rejected_result(), and snapshot_lifecycle_value() where those helpers match the interruption contract.
  • Use build_raw_log_entry() for life_incident_interrupted, life_incident_continued_in_background, life_incident_protected_from_interruption, and life_incident_interrupt_rejected. Confirm or discard staged interruptible success visibility with confirm_committed_success_entry_visibility() and discard_committed_success_entry_visibility().
  • Reuse build_active_incident_request() and validate_active_incident_request() for active reads, and reuse _incident_scope_from_request() plus _drop_none_identity_fields() for scoped in-memory store lookup.

  • Keep interrupted_incident as a model-facing brief, not a full internal snapshot with status.

Review Notes

  • Watch for duplicated lifecycle validation copied from cancel/complete. Shared helper extraction is acceptable only where it removes real duplication and preserves current behavior.
  • Watch for hidden widening in user-turn orchestration. MVP-021 should add one optional deterministic pre-model policy outcome boundary, not a general lifecycle engine.
  • Watch for stale active/read-only context behavior. Once an interruptible transition commits, the same turn's model context should see interrupted_incident rather than a duplicate active incident for the same record. Later active incidents should supersede old interrupted records.
  • Watch for policy creep. Resume, idle, cancellation-after-interruption, durable background status, durable protected deferral, and follow-up incident behavior stay parked.

What It Stores Now

It stores one interrupted incident snapshot per scope in the in-memory incident store for successful interruptible transitions. It also stores one query-visible raw log entry for each successful policy outcome: life_incident_interrupted, life_incident_continued_in_background, or life_incident_protected_from_interruption. A later successful active incident start for the same scope supersedes and clears the prior in-memory interrupted slot only after the start success log is confirmed query-visible.

What It Does Not Store Yet

It does not store a resume plan, background incident state, protected deferral state, incident queue, body delta, Live2D status, proactive output, recurrence, long-term database record, replay projection, or debug-inspector view.

What Comes Later

Later slices can decide how interrupted incidents resume, go idle, stay cancelled, become durable background incidents, or receive protected deferral behavior. Those later slices need separate model action contracts, Commit & Effects transitions, policy rules, context examples, raw logs, and tests.

Open Questions

  • Should background/protected outcomes later create durable status records beyond the query-visible policy log? Not in MVP-021.
  • Should the interrupted brief include a computed remaining-time adjustment? Not in MVP-021.
  • Should later contexts include both the interrupted incident and a separate active incident when another incident starts? Not in MVP-021.
  • Should interrupted incident records eventually persist outside the in-memory store? Not in MVP-021.

Future Ideas Discovered During Planning

  • resume_incident, go_idle, and no_change life-action commit boundaries.
  • Post-turn background/protected behavior beyond the immediate query-visible policy outcome.
  • Multiple interrupted incidents or an incident history query surface.
  • Body and Live2D reactions to interruption after durable state transitions are proven.
  • Debug/replay views for incident lifecycle transitions.
