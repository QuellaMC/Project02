MVP-007 - Universal Agent Capability Contract

Status: implemented locally; PR review pending

Created: 2026-06-12. Updated: 2026-06-12. Active spec: docs/plan/active-slice.html. Previous slice archived at docs/plan/completed/mvp-006-real-model-tools-character-state-patch.html. Suggested implementation branch: feature/mvp-007-agent-capabilities.

Implementation Status

MVP-007 is implemented locally across CT-01 through CT-05. The repo now has a static, runtime-owned agent capability contract, a trusted in-process host, bounded capability context and tool definitions, lifecycle hook evidence, inspect rendering, redaction policy, and fixture-backed adapter proofs for first-party built-ins, OpenClaw-style manifests, Hermes-style providers, TencentDB gateway shapes, and MCP-style tools and resources.

The implementation intentionally stops short of a full plugin system. It uses static, in-process adapters and test fakes only. It does not add hot-loaded packages, dynamic imports, marketplace installation, arbitrary plugin code execution, network calls, sidecars, plugin management, or production TencentDB integration.

Current Product Before This Slice

MVP-006 gives the repo a real model-provider path, a built-in model tool registry, a durable current character state, and validated visible_reply plus optional character_state.patch tool calls. The runtime still owns validation and commit. Local chat remains deterministic by default and can opt into the NVIDIA-compatible provider. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> load CharacterRuntimeState
  -> build DecisionContext with recent visible messages and livingStateBrief
  -> render role-model prompt with built-in tool schemas
  -> provider or local adapter returns ordered toolCalls
  -> parse and validate visible_reply and optional character_state.patch
  -> commit visible reply, state patch, and evidence through local runtime logs
  -> inspect reads provider, tool-call, and state-patch evidence

The limitation is now a host-boundary problem. Built-in tools work, but external memory, retrieval, OpenClaw-style plugin manifests, Hermes memory providers, TencentDB gateway calls, and MCP-style servers would each need custom runtime wiring. If implemented directly now, they would likely duplicate tool description, context contribution, lifecycle, health, policy, and evidence logic.

Product After This Slice

The runtime should have one small, explicit capability-host contract. First-party built-ins and adapter fakes can register through that contract, contribute bounded model context, expose model-callable tools, handle tool calls, run lifecycle hooks, report health, and emit inspectable evidence. The current chat behavior should remain compatible unless a capability is deliberately enabled in a test or future slice. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> create RuntimeCapabilityContext
  -> static capabilities contribute context items and provided tools before the model call
  -> role-model input envelope receives bounded capability context and allowed tool definitions
  -> model proposes visible_reply plus optional capability tool calls
  -> runtime validates tool calls against capability policy
  -> capability handlers return planned results, rejections, or evidence
  -> runtime commits visible reply and durable evidence
  -> after-turn hooks run only after commit; rejected turns do not write memory captures
  -> inspect shows capability contributions, tool routing, hook outcomes, health, and redactions

This is not memory implementation yet. It is the host contract that lets TencentDB-Agent-Memory or another memory backend be adapted later without replacing the role-model loop or creating a second tool/runtime/event system.

Goal

Define and wire a universal agent capability contract for static, runtime-owned adapters. The contract must cover manifest metadata, compatibility metadata, configuration shape, lifecycle hooks, tool definitions, context-provider contributions, memory-style recall and capture timing, policy, health, and inspectable evidence. It must prove compatibility through fake adapters for OpenClaw-style manifests, Hermes-style memory providers, TencentDB gateway endpoints, MCP-style tool/resource servers, and existing first-party built-ins.

Core Design

The contract is universal at the boundary, not universal in implementation. Domain modules continue to own domain logic. The capability host only provides one runtime-facing way to declare, invoke, validate, log, and inspect capability behavior. 

AgentCapability
  -> manifest
  -> configSchema
  -> providedTools
  -> contextProviders
  -> lifecycleHooks
  -> runtimePolicy
  -> evidenceSchema

RuntimeCapabilityHost
  -> static registration of trusted in-process adapters
  -> beforeRoleModelCall contribution phase
  -> model tool-call routing phase
  -> afterTurnCommitted capture phase
  -> sessionEnd and health phases
  -> policy, timeout, rejection, and evidence normalization

The common denominator across the researched agent systems is not a shared file format. It is a repeated contract pattern: declare identity and compatibility, expose tools or context, receive runtime context, run lifecycle hooks, return structured outputs or errors, and leave audit evidence. MVP-007 turns that pattern into the repo's local contract.

Current Scope

  • Shared TypeScript contracts for AgentCapabilityManifest, AgentCapability, RuntimeCapabilityContext, lifecycle hooks, provided tools, context items, health, configuration metadata, and evidence snapshots.
  • A static in-process capability registry for trusted first-party adapters and test adapters.
  • Runtime hook points for beforeRoleModelCall, handleToolCall, afterTurnCommitted, onSessionEnd, and health.
  • Bounded context-provider contributions that can be added to DecisionContext without exposing full runtime internals.
  • Capability-provided model tool definitions that reuse the existing allowed-tool and validation path instead of bypassing model-tool validation.
  • Memory-shaped lifecycle semantics: recall/search before prompt, capture/sync only after durable commit, session end after local session closure, and health checks for degraded providers.
  • Policy metadata for side-effect level, confirmation needs, timeout behavior, required vs optional capability failure, privacy/redaction labels, and source-reference requirements.
  • Durable evidence for capability registration, contribution, invocation, rejection, timeout, health, config fingerprint, context source references, and after-commit hook outcomes.
  • Inspect output that can show capability evidence without re-running providers or mutating runtime state.
  • A read-only capability discovery surface so the operator can inspect installed, registered, enabled, and available-for-turn capabilities, and the model can optionally call a bounded discovery tool for current-turn safe summaries.
  • Adapter-proof fixtures for OpenClaw-style manifests, TencentDB-Agent-Memory gateway endpoints, Hermes memory-provider behavior, MCP tool/resource concepts, and current first-party built-in tools.
  • Compatibility preservation for existing MVP-001 through MVP-006 CLI, durable storage, role-model evidence, provider selection, and character-state behavior.

Explicit Non-Goals

  • No dynamic package loading, dynamic imports, npm plugin installation, marketplace, plugin discovery from disk, or arbitrary third-party code execution.
  • No sandbox, permissions UI, OAuth, secrets store, user-installed plugin management, or broad permission matrix.
  • No production TencentDB-Agent-Memory dependency, sidecar process supervisor, live gateway call, SQLite/sqlite-vec storage, BM25/vector index, or real embedding pipeline.
  • No native memory system that duplicates TencentDB-Agent-Memory internals.
  • No generic JSON Schema framework unless the slice proves the current simple input-contract shape cannot represent required compatibility fixtures.
  • No external side-effect integrations such as files, documents, calendars, email, money, browser automation, account changes, or outgoing messages.
  • No scheduler, background worker queue, proactive delivery, Live2D renderer, asset registry, or provider transport beyond local CLI paths already present.
  • No model-initiated plugin install, uninstall, enable, disable, config mutation, package update, or secrets inspection.
  • No replay UI and no re-execution of model calls or capability hooks from stored logs.
  • No breaking change to existing chat, trace, inspect, durable session, NVIDIA provider, built-in model tools, or character-state patch contracts unless this draft is explicitly revised.

Functional Requirements

ID Requirement
FR-1 The repo defines a stable AgentCapabilityManifest with id, display name, version, kind, compatibility metadata, declared capabilities, config metadata, and local trust level.
FR-2 The repo defines RuntimeCapabilityContext containing session, turn, event, trace, timestamp, character, and privacy/redaction information without exposing mutable runtime internals.
FR-3 The static registry rejects duplicate ids, incompatible contract versions, missing required declarations, and unsupported capability kinds before runtime use.
FR-4 The beforeRoleModelCall hook can contribute bounded context items, model tool definitions, runtime notes, and evidence snapshots.
FR-5 Capability-provided tools enter the existing allowed-tool path and cannot mutate state directly from model output.
FR-6 The handleToolCall hook validates capability tool calls, returns accepted output or structured rejection, and records side-effect and confirmation metadata.
FR-7 The afterTurnCommitted hook runs only after durable visible conversation and raw-event evidence for an accepted turn; rejected role-model or commit decisions do not trigger memory capture.
FR-8 Capability failures follow explicit policy: required before-model failures reject the turn, optional before-model failures degrade with evidence, after-commit failures keep the turn committed and log failure evidence.
FR-9 Health checks and session-end hooks are callable through the host and produce inspectable, redacted evidence without changing visible conversation state.
FR-10 OpenClaw-style manifest fixtures, TencentDB gateway fixtures, Hermes memory-provider fixtures, MCP tool/resource fixtures, and first-party built-in fixtures can all map into the internal contract without special runtime paths.
FR-11 Existing MVP-006 local chat, inspect, durable storage, provider selection, and character-state patch tests remain compatible when no additional capability is enabled.
FR-12 The runtime exposes read-only capability discovery: operator inspect can show installed/registered/enabled/available-for-turn status, while any model-facing discovery tool returns only safe current-turn summaries without secrets, private config, filesystem paths, or disabled capability internals.

Implementation Boundaries

  • The first concrete caller is the existing user-message turn path in src/local-runtime.ts; do not create a second runtime path.
  • Existing built-in model tools remain the initial first-party capability proof. Do not duplicate their validation or state-patch semantics.
  • Capability context contributions must be compact views. Raw memory stores, full transcript stores, and external indexes remain outside DecisionContext.
  • Adapters may normalize foreign contracts into local types. Foreign manifests must not become the runtime's internal source of truth.
  • Capability discovery is read-only. It may report ids, display names, kinds, enabled status, current-turn availability, provided tool names, health summaries, and redacted config fingerprints; it must not expose secrets or let the model manage plugins.
  • Evidence is additive. Capability evidence should attach to existing raw-event and inspect paths rather than creating a parallel log store.
  • Policy decisions belong in runtime-owned host code. Model output and adapter output may propose work, but they do not directly mutate durable state.

Child Task Split

The split is intentionally sized for five month-scale child threads. CT-01 is the shared contract gate; CT-02 through CT-05 can proceed independently after that gate by using fakes, fixtures, and narrow integration points until parent review resolves the final merge shape.

Task Thread Scope Dependency
CT-01 Freeze the universal manifest, capability, runtime context, tool, context item, policy, and evidence contracts. Starts first. Other CTs consume this contract.
CT-02 Wire the static host into user-turn lifecycle hooks without changing default behavior. Can begin after CT-01 draft exports exist.
CT-03 Implement capability-provided tools and context-provider contributions through the role-model contract. Can begin after CT-01; integrates with CT-02 host.
CT-04 Add policy outcomes, durable evidence, redaction, and inspect rendering for capabilities. Can begin from CT-01 snapshot factories, then wire to CT-02 and CT-03.
CT-05 Prove OpenClaw, Hermes, TencentDB, MCP, and first-party built-ins map into the universal contract with fakes and fixtures. Can begin after CT-01; depends on final host evidence for integration checks.

Thread Coordination

  • CT-01 is the contract gate. It should land or be shared as the stable export set before other threads implement against it.
  • CT-01 and CT-05 should read the local research notes under docs/plan/research/ before defining compatibility fields or adapter fixtures.
  • CT-02 through CT-05 should avoid editing each other's domain files until CT-01 is stable. Use fake adapters and fixture tests where possible.
  • Each child thread should keep changes inside its task packet, run focused tests, and hand off unresolved integration risks explicitly.
  • The parent integration review owns final naming, cross-task conflict resolution, compatibility checks, and this active-slice update.

Fake Vs Real Plugin Testing

MVP-007 should not execute real external plugin code in automated tests. The test strategy is fake executable capabilities plus real-shape compatibility fixtures. This proves the host contract and adapter mapping without introducing dynamic loading, sidecar processes, network services, databases, or sandbox policy before the runtime boundary is stable.

  • Fake executable capabilities: in-process test adapters that implement the local AgentCapability contract for memory recall, memory capture, search tools, health, required failures, optional degradation, timeouts, and malformed tool declarations.
  • Real-shape fixtures: source-derived OpenClaw, Hermes/Tencent, MCP, and first-party built-in fixture data that maps into the local contract but is never executed as third-party code.
  • Future manual smoke: a production TencentDB-Agent-Memory sidecar or real OpenClaw package can be tested in a later adapter slice behind explicit opt-in setup, but it is not part of MVP-007 CI.

In short: CI gets fake plugins that actually run through the host, plus fixture plugins that prove compatibility. Real plugin execution is a later integration milestone.

Questions Settled During Implementation

  • The first post-slice production adapter remains future work; MVP-007 proves TencentDB-Agent-Memory compatibility with fakes and fixtures only.
  • Capability-provided tools share the existing role-model tool-call envelope and validation path, with host-owned routing for non-built-in tools.
  • Required before-model capability failures reject the turn before commit; optional before-model failures degrade with evidence; after-commit failures preserve the accepted visible turn.
  • The contract uses the local input-contract shape for this slice. JSON Schema remains outside scope until a real adapter needs it.

Future Ideas Parked Outside MVP-007
