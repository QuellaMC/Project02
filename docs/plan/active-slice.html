MVP-019 - Minimal Incident Completion RuntimeEvent Boundary v0.1

Status: implementation PR open

Created: 2026-05-24. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-019-incident-completion-runtime-event. PR: #22.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 02 - Runtime Architecture, 02A - Runtime Kernel & Operation Routing, 03 - Role Model Loop & Decision Contract, 04 - Event Triggers & Runtime Hooks, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Notion makes all triggers enter as RuntimeEvents, lists INCIDENT_COMPLETION as the incident-completion trigger, names Runtime Kernel as the single entry point for all runtime events, and assigns model-needed routing to the Kernel and durable incident writes plus logging to Commit & Effects. Notion also describes later deterministic body effects, optional private model judgment, proactive output, and follow-up incidents. MVP-019 intentionally promotes only the minimal deterministic event boundary and leaves those broader behaviors parked.

Local implementation truth comes from completed MVP-011, MVP-012, MVP-013, MVP-014, MVP-015, MVP-016, MVP-017, and MVP-018. MVP-018 already proved the user-message complete_incident commit path and the life_incident_completed atomic raw-log visibility path.

Goal

Add the first non-user-message runtime event boundary by accepting a minimal INCIDENT_COMPLETION event with an incident_id, routing it through Runtime Kernel without a model call, and committing the active incident completion through Commit & Effects by re-reading and matching the current active incident.

Current Scope

  • One new event family is in scope: INCIDENT_COMPLETION.
  • The new event payload requires incident_id and may carry the same optional user_id and conversation_id identity fields used by active-incident scope reads.
  • Runtime Kernel must normalize, raw-log, and route INCIDENT_COMPLETION as a non-user-message event.
  • The route is deterministic: no model judgment is needed and the next boundary is the incident-completion commit path.
  • Commit & Effects must re-read the active incident for the event scope, compare the active incident_id to the event payload, and reject mismatches.
  • Successful completion produces a life_incident_completed raw log entry, confirms it through the existing atomic success visibility path, clears the matching active incident, and returns a structured commit result.
  • Rejections are structured, logged with life_incident_complete_rejected, and leave active incident state unchanged unless the failure occurs after success visibility is already confirmed.
  • The existing USER_MESSAGE start, cancel, complete, state-patch, and visible-reply flows must keep their current contracts.

Explicit Non-Goals

  • No scheduler, timer generation, expected-end scanning, missed-event reconciliation, or background worker.
  • No private role-model call, no private_incident_completion envelope, and no model output parsing for this event path.
  • No body effects, living-state patch, Live2D status, proactive message, tool request, retrieval, continuity write, or asset behavior.
  • No follow-up incident, incident queue behavior, resume, go idle, no change, interruption policy, or incident chaining.
  • No completed_incident field in DecisionContext and no Character State Engine context-builder change.
  • No persistent database adapter, migration, completed-incident history API, debug UI, replay execution, or generalized scheduler policy.
  • No change to the MVP-018 USER_MESSAGE life_action.complete_incident model-proposed path except shared helpers needed to avoid duplication.

Minimal Schema

INCIDENT_COMPLETION RuntimeEvent

type IncidentCompletionEvent = {
  schema_version: "0.1"
  event_id: string
  trace_id: string
  type: "INCIDENT_COMPLETION"
  created_at: string
  payload: {
    incident_id: string
    user_id?: string
    conversation_id?: string
  }
}

incident_id is required and must be non-empty. Optional identity fields are copied into the active-incident read and finalize requests when provided; absent identity fields preserve the current single-user self-use test scope.

RuntimeRouteResult

type IncidentCompletionRouteResult = {
  trace_id: string
  event_id: string
  event_type: "INCIDENT_COMPLETION"
  model_needed: false
  next_step: "incident_completion_commit"
}

LifeIncidentCompletionEventCommitRequest

type LifeIncidentCompletionEventCommitRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "INCIDENT_COMPLETION"
  incident_id: string
  commit_time: string
  user_id?: string
  conversation_id?: string
}

LifeIncidentCompletionEventFinalizeRequest

type LifeIncidentCompletionEventFinalizeRequest =
  LifeIncidentCompletionEventCommitRequest & {
    active_incident: ActiveIncidentSnapshot
    completed_incident: CompletedLifeIncidentSnapshot
    committed_log_entry: RawEventLogEntry<"life_incident_completed">
  }

life_incident_completed Raw Log Data

type IncidentCompletionEventCompletedLogData = {
  source_event: IncidentCompletionEvent
  completion_source: "incident_completion_event"
  active_incident: ActiveIncidentSnapshot
  completed_incident: CompletedLifeIncidentSnapshot
}

The event path must not fabricate a RoleModelTurnResult, CharacterDecision, or life_action. The same log kind is reused because the durable transition is the same; the completion_source field distinguishes this deterministic event path from the MVP-018 model-proposed user-message path.

life_incident_complete_rejected Raw Log Data

type IncidentCompletionEventRejectedLogData = {
  source_event: IncidentCompletionEvent
  completion_source: "incident_completion_event"
  active_incident_snapshot?: unknown
  completed_incident_snapshot?: unknown
  failure: {
    stage: "incident_completion_event_commit_validation" |
           "incident_completion_event_finalize"
    code: string
    message: string
  }
}

Functional Requirements

ID Requirement
FR-1 Add a shared INCIDENT_COMPLETION = "INCIDENT_COMPLETION" contract constant and a narrow normalized event validator for the new event shape. Do not add other event families in this slice.
FR-2 Extend runtime.kernel event-normalizer and route tables so USER_MESSAGE keeps its current behavior and INCIDENT_COMPLETION is the only supported non-user-message event type.
FR-3 Kernel intake for INCIDENT_COMPLETION must assign missing IDs and schema_version, validate created_at, normalize payload identity fields, append exactly one runtime_event_received log entry, and return the deterministic non-model route.
FR-4 Malformed INCIDENT_COMPLETION inputs, including missing payload, blank incident_id, non-string identity fields, invalid timestamps, unsupported schema versions, and extra payload fields, must fail before any commit attempt.
FR-5 Add a Commit & Effects event-completion boundary that accepts only a normalized INCIDENT_COMPLETION event and does not require or accept a role-model result.
FR-6 The commit boundary must build an active-incident request from the event identity fields by reusing or extracting the existing active-incident request/scope helpers; it must not duplicate scope logic in a parallel implementation.
FR-7 Before finalization, Commit & Effects must re-read the active incident, reject if no active incident exists, and reject if the event payload incident_id does not match the current active incident.
FR-8 On success, Commit & Effects must reuse the MVP-018 completed-snapshot validation rules, set actual_end_at from the commit clock, preserve active source IDs, append the completion event ID once, and build one life_incident_completed raw log entry.
FR-9 InMemoryLifeIncidentStore must finalize the event-driven completion through the same raw-log visibility and same-scope clearing guarantees as MVP-018, while keeping copy-safe reads and no completed-history API.
FR-10 Failures before raw-log success visibility is confirmed must return a structured rejected result, append life_incident_complete_rejected through the ordinary raw-log path, leave the active incident unchanged, and leave no query-visible life_incident_completed entry.
FR-11 Failures after raw-log success visibility is confirmed must preserve the already-query-visible life_incident_completed entry and append a later life_incident_complete_rejected audit entry in the same trace.
FR-12 The successful result must agree with raw_event_log.query() on trace ID, event ID, event type, incident ID, completion time, completed snapshot, and committed log entry ID.
FR-13 The implementation must reuse, move, extract, or compatibility-export existing shared code surfaces instead of duplicating them: runtime.contracts.validate_iso8601_timestamp(), runtime.kernel.EVENT_PAYLOAD_NORMALIZERS, runtime.kernel.EVENT_ROUTE_BUILDERS, runtime.logging.build_raw_log_entry(), runtime.logging.ATOMIC_FINALIZER_SUCCESS_KINDS, runtime.logging.confirm_committed_success_entry_visibility(), runtime.logging.discard_committed_success_entry_visibility(), character.state.current.validate_active_incident_request(), character.state.current.validate_active_incident_snapshot(), character.state.incidents._incident_scope_from_request(), character.state.incidents._drop_none_identity_fields(), commit_effects.incident_complete.build_completed_life_incident_snapshot(), commit_effects.incident_complete.validate_completed_life_incident_snapshot(), and the shared lifecycle failure/finalizer helpers where they fit the event path without faking model data.
FR-14 The event path must prove that no Role Model Loop adapter is invoked, no DecisionContext is built, no visible reply is committed, and no user-turn orchestration is required.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep the new runtime event contract small and table-driven like the existing kernel user-message path.
  • Keep Commit & Effects as the only boundary that clears the active incident or exposes completion success.
  • Keep the event path deterministic and testable with fake clocks, fake IDs, in-memory logs, and in-memory incident stores.
  • Prefer precise shared helpers over a broad lifecycle framework rewrite.
  • Preserve append-only raw logging and the current atomic success visibility contract.

Acceptance Criteria

  • MVP-018 is recorded under completed plans, and this file is the only active implementation slice.
  • A valid INCIDENT_COMPLETION event with incident_id normalizes through Runtime Kernel, appends runtime_event_received, and routes with model_needed = false and next_step = "incident_completion_commit".
  • The commit boundary completes only the matching active incident for the event scope and clears that active incident after the success log is query-visible.
  • The life_incident_completed entry is visible through raw_event_log.query() and carries completion_source = "incident_completion_event".
  • No active incident is cleared when the event is malformed, there is no active incident, the incident ID mismatches, the source read raises, the raw-log instance mismatches, finalization rejects, visibility staging fails, or the active incident changes before completion.
  • Post-confirm clearing failures preserve the query-visible success entry and add a structured rejection audit.
  • Existing USER_MESSAGE routing and MVP-018 model-proposed complete_incident behavior continue to pass unchanged.
  • No scheduler, timer, private role-model call, body effect, Live2D effect, proactive message, follow-up incident, or completed_incident DecisionContext is added.
  • The development journal records source context, files touched, checks run, review notes, next action, future ideas, and whether active slice scope changed.

  • Assert route_runtime_event() returns the deterministic non-user-message route for INCIDENT_COMPLETION and keeps the existing USER_MESSAGE route unchanged.
  • Assert kernel intake appends one runtime_event_received entry with the normalized event snapshot for INCIDENT_COMPLETION.
  • Build and validate event-completion commit/finalize requests, completed snapshots, success logs, rejection logs, and failure envelopes without role-model result data.
  • Finalize an event-driven completion through InMemoryLifeIncidentStore and assert same-scope active incident is cleared, other scopes remain unchanged, copies are safe, and query-visible success logs are staged and confirmed.
  • Reject no-active, incident-ID mismatch, raw-log mismatch, active-source exception, finalizer pre-confirm exception, staging failure, and changed-before-completion paths without clearing active state or exposing success.
  • Reject post-confirm clearing failure with both a visible success entry and a later life_incident_complete_rejected entry.
  • Run existing incident-complete user-message tests to prove the event path did not break MVP-018.

Integration Tests

  • Start an active incident with the concrete in-memory store, intake an INCIDENT_COMPLETION event through Runtime Kernel, pass the normalized event to Commit & Effects, and assert route, result, store read, and raw-log query all show completion.
  • Run an INCIDENT_COMPLETION event with no active incident and assert a structured rejection log and no visible reply/model logs.
  • Run an INCIDENT_COMPLETION event with a mismatched incident_id and assert the original active incident remains visible.
  • Run existing USER_MESSAGE user-turn integration tests to confirm user-message routing and completion opt-in behavior are unchanged.

Implementation Boundaries

  • runtime.contracts owns shared event constants and normalized event validation contracts.
  • runtime.kernel owns event intake, event-type dispatch, payload normalization, raw event received logging, and deterministic route construction.
  • commit_effects.incident_complete owns event-completion commit request construction, active-incident matching, completed snapshot/log construction, finalizer result validation, rejection logs, and success/rejection result envelopes.
  • commit_effects.incident_lifecycle may be extended only for real shared commit/finalizer behavior that applies to both user-message and event-driven completion without model-data assumptions.
  • character.state.incidents.InMemoryLifeIncidentStore owns scoped in-memory finalization and active-incident clearing; it does not become an incident history store.
  • role_model.loop, character.state.context, and runtime.user_turn should remain unchanged unless a test proves a small compatibility export is needed.

Review Notes

  • This is the first non-user-message RuntimeEvent slice, but it must not become the generic event-system slice.
  • The highest risk is pretending the event path is a role-model path. Do not fake RoleModelTurnResult, CharacterDecision, or life_action data to reuse MVP-018 helpers.
  • The second risk is clearing active incident state before the success log is query-visible. Preserve the existing atomic finalizer visibility sequence.
  • The third risk is accepting stale expected-end events. Re-read the active incident and match incident_id at commit time.
  • Keep identity scope boring: optional user_id and conversation_id use the same active-incident scope behavior already proven by the store.
  • Do not implement the source of the event. Tests may directly supply INCIDENT_COMPLETION; scheduler/timer slices can generate it later.
  • Implementation review: the shared active-incident request contract now admits exactly USER_MESSAGE and INCIDENT_COMPLETION, preserving current state reads as user-message-only.
  • Implementation review: the event path adds dedicated no-model completion log builders instead of fabricating RoleModelTurnResult or life_action data.
  • Higher-level refactor proposal: if a second no-model lifecycle event repeats the same finalizer sequence, extract a request-driven lifecycle transition helper that accepts prebuilt commit requests and source-specific log builders without model-result assumptions. MVP-019 parks that refactor because there is only one event-driven lifecycle path.

Implementation Results

  • Added INCIDENT_COMPLETION as the only new runtime event constant, payload normalizer, validator, and deterministic route.
  • Extended active-incident reads so the same scoped request helper works for user-message and incident-completion events.
  • Added commit_life_incident_completion_event() to Commit & Effects. It re-reads the active incident, matches incident_id, builds a completed snapshot with the existing validation rules, stages the success raw log, confirms visibility, then clears the active incident through InMemoryLifeIncidentStore.
  • Reused the existing life_incident_completed success kind and atomic raw-log visibility path, with completion_source = "incident_completion_event" to distinguish the deterministic event path from MVP-018's model-proposed user-message path.
  • Added unit and integration coverage for success, malformed event intake, no-active rejection, incident-ID mismatch, active-source failure, finalizer failure, post-confirm clearing failure, deep-copy safety, and no-model/no-visible-output behavior.
  • Left scheduler generation, private role-model aftermath, body/living-state/Live2D effects, proactive output, follow-up incidents, persistent completed history, retrieval indexing, and completed_incident DecisionContext fields out of scope.

Open Questions

  • Should future scheduler-generated completion events include idempotency keys or expected scheduled time? Not in MVP-019.
  • Should later private incident completion model calls receive completed_incident context and produce proactive output? Not in MVP-019.
  • Should a persistent LifeIncidentStore keep completed history directly or continue deriving it from Raw Event Log? Not in MVP-019.

Future Ideas Discovered During Planning

  • Scheduler or timer generation of INCIDENT_COMPLETION when expected_end_at is reached.
  • Private incident-completion role-model call with completed_incident context and optional proactive output.
  • Body, living-state, and Live2D effects for incident completion.
  • Follow-up incident or chain policy after completion.
  • Persistent incident lifecycle storage with completed history, idempotency, and migrations.
  • Retrieval indexing over completed incident episodes once raw transition truth is stable.
