MVP-009 - Minimal Living State Patch Commit

Status: implemented and in review; PR #9

Created: 2026-05-17. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-009-functional-spec.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace.

Phase 2 adds CharacterRuntimeState, a state snapshot in DecisionContext, and state patch validation and commit. MVP-008 finished only the read-side snapshot. MVP-009 takes the next smallest write-side step: one optional model-proposed living-state patch can be validated and committed through Commit and Effects.

Local implementation truth comes from MVP-001, MVP-002, MVP-003, MVP-004, MVP-005, MVP-006, MVP-007, and MVP-008. The current runtime can complete one USER_MESSAGE turn with visible history, a fake model, a visible reply commit, and an optional read-only living_state_brief.

Goal

Extend the state-enabled USER_MESSAGE turn by allowing the fake role model to return one optional state_patch.living_state alongside the existing required visible_reply. The runtime must validate the patch, commit it through an injected Commit and Effects state boundary, append an auditable raw log entry, and preserve the existing visible reply flow. This slice must not add concrete storage, body state, incidents, scheduled directives, retrieval, tools, Live2D, a live model provider, or a new runtime event family.

Current Scope

  • One supported event type remains USER_MESSAGE.
  • One optional state-patch capability, enabled only when the caller provides both a current-state source and a living-state patch commit store.
  • One optional state_patch.living_state sibling on the existing visible-reply model decision.
  • One tiny living-state patch shape with only current_activity, mood, and toward_user; at least one field must be present.
  • One injected commit store or sink bound by the caller to the active character; runtime code must not infer or hard-code character_id.
  • One Commit and Effects state commit path that validates the patch and appends either living_state_patch_committed or living_state_patch_rejected.
  • Existing visible reply parsing, recent visible messages, current-state read, and user-turn orchestration remain authoritative.
  • Existing callers that do not opt into living-state patch commits continue to see MVP-008 behavior and allowed_actions = ["visible_reply"].
  • Tests use fakes only; no database, file, network, live model provider, scheduler, or clock side effect is introduced beyond the existing injected clock.

Explicit Non-Goals

  • No concrete CharacterRuntimeStateStore, database schema, migration, transaction manager, idempotency key store, or persistence adapter.
  • No full CharacterRuntimeState expansion beyond the already proven living-state brief fields.
  • No model-proposed body_state, virtual body drift, need thresholds, active incident, incident queue, scheduled directive, active thread, retrieval, continuity write, tool request, Live2D status, asset, proactive message, scheduler, or background worker.
  • No standalone state-only model call and no action = "state_patch" output. The user-turn model decision still requires action = "visible_reply" and a valid visible reply.
  • No automatic default state creation when a state source is absent.
  • No rollback or reconciliation if the user visible message was already committed before a later state patch rejection.
  • No dedicated context-build log. The new raw logs cover only the state patch commit or rejection once the model has proposed a patch.
  • No broad Character State Engine context-builder extraction and no broad Role Model Loop output-contract redesign.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-009 should implement the contract in Python 3 and test it with unittest.

MVP009 DecisionContext Excerpt

type DecisionContext = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  call_type: "user_message_visible_reply"
  event: UserMessageEventContext
  character_snapshot: {
    recent_visible_messages: RecentVisibleMessage[]
    living_state_brief?: LivingStateBrief
  }
  allowed_actions:
    | ["visible_reply"]
    | ["visible_reply", "state_patch"]
}

The wider allowed-action list is available only for state-enabled calls. A normal caller with no state commit boundary keeps the MVP-008 ["visible_reply"] contract.

MVP009 CharacterDecision Excerpt

type CharacterDecision = {
  schema_version: "0.1"
  action: "visible_reply"
  visible_reply: {
    text: string
  }
  state_patch?: {
    living_state: {
      current_activity?: string
      mood?: string
      toward_user?: string
    }
  }
}

The model may not set character_id, updated_at, source_event_ids, body_state, or any durable store field. Commit and Effects owns timestamps, source event IDs, and the committed record. The Role Model Loop must normalize this shape through a shared runtime.contracts helper, not through ad hoc patch validation local to the loop.

VisibleReplyCommitProjection

type VisibleReplyCommitProjection = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  action: "visible_reply"
  visible_reply: {
    text: string
  }
}

commit_visible_reply() keeps its existing strict visible-reply-only contract. If the parsed decision contains state_patch, the user-turn orchestrator or Commit and Effects handoff must pass a visible-reply-only projection to the existing visible reply commit path after the state patch commit succeeds. Do not broaden commit_visible_reply() to accept state patch fields in this slice.

LivingStatePatchCommitRequest

type LivingStatePatchCommitRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  patch: {
    living_state: {
      current_activity?: string
      mood?: string
      toward_user?: string
    }
  }
  user_id?: string
  conversation_id?: string
}

LivingStatePatchCommitResult

type LivingStatePatchCommitResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status:
    | "living_state_patch_committed"
    | "living_state_patch_skipped"
    | "living_state_patch_rejected"
  committed_snapshot?: CharacterRuntimeStateSnapshot
  failure?: {
    stage: "living_state_patch_commit_validation" | "living_state_patch_store"
    code: string
    message: string
  }
}

Functional Requirements

ID Requirement
FR-1 Without state-patch opt-in, build_decision_context(), render_role_model_input(), parse_character_decision(), run_role_model_turn(), and run_user_message_turn() preserve MVP-008 behavior and accept only visible_reply.
FR-2 State-patch opt-in requires a current-state source for the model-facing living_state_brief and a separate injected commit store for the write. If either is absent, the user-turn path must not advertise state_patch as allowed.
FR-3 For an opted-in call, DecisionContext.allowed_actions is exactly ["visible_reply", "state_patch"], and the rendered model input includes the MVP-008 living_state_brief.
FR-3a For an opted-in call, render_role_model_input() uses a conditional output contract that explicitly permits optional state_patch.living_state with only current_activity, mood, and toward_user. The existing visible-reply-only instructions remain unchanged for non-opted-in calls.
FR-4 The Role Model Loop still requires action = "visible_reply" and a non-empty visible_reply.text. A standalone action = "state_patch" remains invalid.
FR-5 When state_patch is present and allowed, parsing accepts only state_patch.living_state.current_activity, mood, and toward_user as non-empty strings, with at least one field present, by reusing a shared runtime.contracts.normalize_living_state_patch() helper.
FR-6 Parsing rejects malformed model output before any state commit path runs: state_patch when not allowed, unknown state-patch fields, empty strings, empty living-state patches, body_state, and future state families all produce the existing role_model_turn_failed parse behavior.
FR-7 Commit and Effects validates the normalized USER_MESSAGE source event, role-model result status, trace ID, event ID, decision action, and already-normalized patch before calling the injected commit store. It must reuse runtime.contracts.normalize_role_model_turn_result() for the shared envelope and runtime.contracts.normalize_living_state_patch() for defensive patch validation rather than duplicating schema logic.
FR-7a Before calling the existing commit_visible_reply() path for a decision that also contains state_patch, the user-turn path must build a VisibleReplyCommitProjection and validate it through the existing visible-reply-only contract.
FR-8 The injected MVP-009 patch boundary is a pending, non-durable prepare boundary called at most once per user turn with a deep-copied LivingStatePatchCommitRequest. Caller mutation after the call must not alter raw log snapshots or returned results.
FR-8a The patch request must not accept model-authored updated_at or source_event_ids. The fake prepare boundary used in tests must return a committed snapshot candidate with deterministic runtime-owned updated_at and source_event_ids values derived from the injected test boundary and source event, not from the model patch. Commit and Effects must reject a shape-valid store result as malformed_store_result when the current event_id is absent from source_event_ids, any patched living-state field differs in the returned snapshot, or updated_at does not match the runtime commit timestamp / is older than the source event.
FR-9 On successful state patch commit, Commit and Effects appends one living_state_patch_committed raw log entry containing the source event, role-model result snapshot, normalized patch, and validated committed state snapshot returned by the fake prepare boundary. In MVP-009, the raw-log append is the commit point; the injected patch boundary must not durably mutate state before that append succeeds.
FR-10 If the model returns no state patch, the state commit path returns living_state_patch_skipped, does not call the commit store, and appends no state patch raw log entry.
FR-11 If normalized patch commit validation, the injected store, or committed-snapshot consistency validation rejects the patch, Commit and Effects appends one living_state_patch_rejected raw log entry and the user-turn orchestrator stops before assistant visible reply commit. Malformed model output is not logged as living_state_patch_rejected; it remains a Role Model Loop parse failure.
FR-12 A successful opted-in user turn with a state patch appends raw logs in this deterministic order: runtime_event_received, user_visible_message_committed, role_model_turn_completed, living_state_patch_committed, visible_reply_committed.
FR-13 A successful opted-in user turn without a state patch preserves the MVP-008 raw log order and visible record order.
FR-14 The final UserMessageTurnResult may include living_state_patch_result when the commit path runs, but the existing nested boundary results and visible record IDs remain unchanged.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep tests deterministic under injected fake adapter, fake raw log, fake visible conversation, fake current-state source, fake living-state patch store, fake clock, and fake ID generator.
  • Reuse existing shared validators from runtime.contracts, including reject_extra_keys, require_equal, require_string, require_optional_string, require_matching_identity, and validate_normalized_user_message_event.
  • Promote the current private RoleModelTurnResult envelope validation into runtime.contracts.normalize_role_model_turn_result() and reuse it from both the existing visible reply commit path and the new living-state patch commit path.
  • The shared RoleModelTurnResult normalizer must not broaden visible reply decision validation. It should validate envelope fields and identity while letting each consumer provide or select the appropriate decision normalizer: visible-reply-only projection for commit_visible_reply(), and visible reply plus optional patch for the state patch commit path.
  • Add one shared runtime.contracts.normalize_living_state_patch() helper for the MVP-009 patch shape and reuse it from both Role Model Loop parsing and Commit and Effects validation.
  • Do not change normalize_visible_reply_decision() or commit_visible_reply() to accept state_patch. Use a visible-reply-only projection for the existing visible reply commit path.
  • Render conditional role-model instructions: non-opted-in calls keep the existing visible-reply-only contract, while opted-in calls explicitly allow optional state_patch.living_state and forbid all other extra fields.
  • Reuse MVP-008 state snapshot validation from character.state.current for committed snapshot validation instead of duplicating the snapshot contract.
  • Validate committed snapshot consistency after the fake prepare boundary returns: current event ID must be present, patched fields must match, and updated_at must be the runtime commit timestamp and not older than the source event.
  • Keep state-patch commit code in the Commit and Effects boundary. The Role Model Loop may parse the proposed patch, but it must not commit it.
  • Do not introduce a durable state store in MVP-009. A future concrete store must make state mutation and raw-log append one transaction or otherwise prove equivalent atomicity.
  • Keep Runtime Kernel unchanged except for existing USER_MESSAGE route behavior.
  • Keep implementation small and local; add no placeholder modules, empty future folders, or speculative adapter layers.
  • Keep error behavior explicit and testable; do not hide validation failures behind character language or fallback replies.

Acceptance Criteria

  • Existing MVP-001 through MVP-008 tests continue to pass without opting into state-patch commits.
  • A state-enabled fake model input advertises exactly ["visible_reply", "state_patch"] and includes the read-only living_state_brief.
  • A state-enabled fake model input renders instructions that permit optional state_patch.living_state; non-state-enabled input keeps the visible-reply-only instructions.
  • A fake model output with valid visible reply plus valid living-state patch parses into one normalized CharacterDecision.
  • A model output state patch with future fields, empty values, missing living-state fields, or body_state is rejected as malformed model output before Commit and Effects runs.
  • The fake prepare boundary proves ownership of committed snapshot metadata by returning deterministic updated_at and source_event_ids values that were not present in the model patch, and Commit and Effects rejects shape-valid but semantically inconsistent snapshots.
  • A successful user turn with a patch calls the fake commit store once, appends living_state_patch_committed, then commits the assistant visible reply through a visible-reply-only projection.
  • A normalized patch commit/store rejection appends living_state_patch_rejected, returns a stopped user-turn result, and appends no assistant visible reply.
  • If raw-log append fails after the fake boundary prepares a valid snapshot, no durable state mutation has happened because MVP-009 exposes only a pending prepare boundary.
  • A user turn with no state patch remains compatible with the MVP-008 visible reply flow and raw log order.
  • No concrete storage, state versioning, body state, incidents, scheduled directives, retrieval, tools, Live2D, scheduler, live provider, or new event type is added.
  • Future ideas discovered during planning are recorded in future-slices.html.
  • The development journal records files touched, checks run, review notes, and next action.

Implementation Boundaries

  • Runtime Kernel remains unchanged; it still only routes USER_MESSAGE to the existing user-turn path.
  • Character State Engine remains read-side for this slice. It may continue to own current-state request and snapshot validation, but it must not commit durable state.
  • Role Model Loop may add opt-in allowed-action rendering and parser support for optional state_patch.living_state. It must not call a state store or mutate state.
  • Commit and Effects owns the new living-state patch validation, commit request construction, fake-store prepare call, committed-snapshot consistency validation, committed/rejected raw log entries, and returned commit result.
  • User-turn orchestration may pass the optional state patch capability through, call the state commit path after the role-model turn, then pass a visible-reply-only projection into assistant visible reply commit.
  • Raw Event Log adds only state patch commit/reject entries when a patch is proposed or rejected. No context-build or state-read log kind is added.

Implementation Notes

  • runtime.contracts now owns normalize_living_state_patch(), normalize_role_model_turn_result(), and the optional living-state patch decision normalizer.
  • role_model.loop now advertises ["visible_reply", "state_patch"] only when explicitly opted in with a current-state source, renders conditional state-patch instructions, and rejects disallowed or malformed patch output as role-model parse failures.
  • commit_effects.living_state adds the injected Commit and Effects patch boundary, patch request construction, committed/rejected raw logs, store rejection handling, committed snapshot validation through the MVP-008 state snapshot contract, and post-store consistency validation for source event IDs, patched fields, and runtime-owned timestamps.
  • runtime.user_turn opts in only when both current-state read and living-state patch write boundaries are present, stops before assistant visible reply on patch rejection, and projects a visible-reply-only result before calling commit_visible_reply().
  • commit_visible_reply() remains strict and does not accept state_patch.
  • Runtime Kernel, concrete storage, body state, incidents, scheduled directives, retrieval, tools, Live2D, provider calls, and new event types remain unchanged.

Error And Fallback Behavior

  • Missing state-patch opt-in is not an error; MVP-008 visible reply behavior remains valid.
  • A model-proposed state patch when state_patch was not allowed raises the existing role-model validation error before any commit path runs.
  • Malformed patch output fails in Role Model Loop parsing, appends the existing role_model_turn_failed log, and never calls the injected commit store.
  • Normalized patch commit validation or injected store rejection returns living_state_patch_rejected and appends a rejection log; the user-turn path stops before assistant visible reply commit.
  • No rollback, retry, repair, reconciliation, or user-visible fallback message is added.

Review Notes

  • MVP-009 is the first write-side CharacterRuntimeState slice, but it is still an injected-boundary slice, not a concrete storage slice.
  • The model may propose only semantic living-state fields already visible in MVP-008. The runtime owns timestamps, source IDs, validation, and persistence.
  • Implementation tests should make timestamp and source-event ownership concrete through the fake prepare boundary: model output supplies only the patch fields, while the committed snapshot supplies runtime-owned updated_at and source_event_ids.
  • MVP-009's injected state boundary is intentionally non-durable until the raw log append succeeds. A future durable store slice must not reuse this as a concrete persistence transaction without adding atomic state+raw-log semantics.
  • Keep the existing visible reply action required so the user-turn output contract does not become a broad multi-action redesign.
  • Keep commit_visible_reply() strict and visible-reply-only; a projection is the compatibility boundary for decisions that also carry state_patch.
  • Extract shared RoleModelTurnResult envelope validation before adding the second Commit and Effects consumer so the living-state patch commit path does not copy the private validator from visible_reply.py.
  • Do not duplicate living-state patch validation between Role Model Loop and Commit and Effects; share the small helper in runtime.contracts.
  • If implementation pressure suggests adding state versions, transaction semantics, body state, incidents, or a concrete store, split those into future slices instead.

Residual Implementation Risks

  • Do not broaden normalize_visible_reply_decision() or commit_visible_reply() to accept state_patch. MVP-009 must use the visible-reply-only projection required above before the existing assistant visible reply commit path runs.
  • Do not copy the private RoleModelTurnResult validation from commit_effects.visible_reply into the state patch path. MVP-009 must extract and reuse a shared runtime.contracts.normalize_role_model_turn_result() helper first.
  • Do not implement separate living-state patch validators in role_model.loop and Commit and Effects. MVP-009 must put the patch shape in one shared runtime.contracts.normalize_living_state_patch() helper and reuse it from both boundaries.

Open Questions

  • Should the eventual durable store maintain a separate state_version? Not in MVP-009; fake store returns the MVP-008 snapshot shape only.
  • Should state patch commit and visible reply commit become one transaction? Not in MVP-009; no concrete store or transaction manager exists.
  • Should concrete state mutation and living_state_patch_committed raw-log append be one transaction? Yes, before any durable state store is introduced; MVP-009 explicitly defers this with a non-durable prepare boundary.
  • Should state patch be allowed without a visible reply in private calls? Not in MVP-009; that belongs to a later private life-event slice.

Future Ideas Discovered During Planning

  • Broader LivingStateCurrent fields such as current_scene, energy, current_focus, and last_meaningful_change_at.
  • State patch support for body_state after lazy virtual body is specified.
  • Private state-only calls for incident completion, need thresholds, and scheduled directives.
  • State patch replay and reconciliation once concrete stores and debug inspector exist.
