MVP-014 - Minimal Concrete LifeIncidentStore Start Adapter

Status: implemented locally; PR #16 open

Created: 2026-05-20. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-014-life-incident-store-start-adapter. Pull request: PR #16.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace.

Phase 3 calls for a LifeIncidentStore, but this slice only replaces the MVP-012 incident-start fake finalizer with a concrete in-memory start adapter and proves that its success log remains visible through the MVP-013 Raw Event Log query surface.

Local implementation truth comes from completed MVP-001, MVP-002, MVP-003, MVP-007, MVP-011, MVP-012, and MVP-013.

Goal

Replace the MVP-012 incident-start fake finalizer with a small concrete in-memory LifeIncidentStore / finalizer adapter that durably exposes the started incident and matching life_incident_started Raw Event Log entry through the MVP-013 query surface, without adding the rest of the incident lifecycle.

Current Scope

  • One event type remains in scope: USER_MESSAGE.
  • One life action remains in scope: life_action.type = "start_incident".
  • One concrete in-memory incident store is in scope for the started active incident record.
  • One adapter is in scope: it implements the existing LifeIncidentStartFinalizer protocol used by MVP-012.
  • The same store must implement the existing ActiveIncidentSource.read_active_incident(request) contract with ActiveIncidentRequest so it reuses the shared MVP-011 read boundary.
  • The adapter must stage the already-built life_incident_started entry through the MVP-013 InMemoryRawEventLog committed-success visibility path.
  • The successful user-turn path should expose the started active incident from the store and expose the matching raw log entry through raw_log.query().
  • The adapter may reject a start when an active incident is already stored, but it must not replace, interrupt, queue, complete, cancel, or resume incidents.

Explicit Non-Goals

  • No database, filesystem persistence, migration, repository layer, background worker, scheduler, lock manager, or process-restart durability.
  • No complete_incident, cancel_incident, resume_incident, go_idle, no_change, replacement, interruption, backgrounding, queue, recurrence, reconciliation, or incident completion event.
  • No new RuntimeEvent type, Role Model Loop action, parser behavior, prompt behavior, context field, state patch behavior, body state, Live2D status, tool, asset, retrieval, compaction, or replay executor.
  • No concrete Raw Event Log store beyond the MVP-013 in-memory query helper.
  • No broad CharacterRuntimeStateStore, virtual body store, scheduled directive store, unified retrieval index, debug UI, HTTP endpoint, or CLI command.
  • No change to the model contract: the model still proposes only the MVP-012 start_incident draft and never provides committed-only incident fields.
  • No change to Commit and Effects ownership: Commit and Effects still builds and validates the started incident snapshot and committed log entry before finalization.

Minimal Schema

LifeIncidentStore

type LifeIncidentStore = {
  finalize_life_incident_start(request: LifeIncidentStartFinalizeRequest): LifeIncidentStartFinalizeResult
  read_active_incident(request: ActiveIncidentRequest): ActiveIncidentSnapshot | null
}

The concrete MVP-014 implementation may be an in-memory class, but it should be production-shaped code rather than a test-only recording fake. The read method must use the existing character.state.current.ActiveIncidentSource request shape. Returned incidents must be copies.

ActiveIncidentRequest

type ActiveIncidentRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  user_id?: string
  conversation_id?: string
}

Reuse build_active_incident_request() and validate_active_incident_request() from character.state.current. MVP-014 only proves the store can satisfy this read contract; it does not make the store the default DecisionContext source for every user turn.

LifeIncidentStartFinalizeRequest

type LifeIncidentStartFinalizeRequest = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  decision_action: "visible_reply"
  life_action_type: "start_incident"
  commit_time: string
  draft: LifeIncidentStartDraft
  started_incident: ActiveIncidentSnapshot
  committed_log_entry: RawEventLogEntry
  user_id?: string
  conversation_id?: string
}

Reuse the MVP-012 request shape and the existing ActiveIncidentSnapshot validation. Do not add model-authored committed fields or store-only metadata fields in this slice.

LifeIncidentStartFinalizeResult

type LifeIncidentStartFinalizeResult = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  committed_log_entry_id: string
}

Reuse the MVP-012 result shape so commit_life_incident_start() can keep its current validation and result handling.

Functional Requirements

ID Requirement
FR-1 The new in-memory store adapter implements the existing LifeIncidentStartFinalizer.finalize_life_incident_start() protocol without changing commit_life_incident_start() call sites beyond replacing the fake.
FR-2 The store implements the existing ActiveIncidentSource.read_active_incident(request) contract using ActiveIncidentRequest validation instead of introducing a no-argument duplicate read API.
FR-3 On a valid finalize request, the adapter stores one active incident snapshot and stages the matching already-built life_incident_started RawEventLogEntry through the MVP-013 committed-success visibility helper.
FR-4 After commit_life_incident_start() confirms the finalizer result, querying the same trace through InMemoryRawEventLog.query() with kinds = ["life_incident_started"] returns the stored incident's matching committed log entry exactly once.
FR-5 The stored active incident and the query-visible life_incident_started entry must agree on trace_id, event_id, incident_id, started_at, source_event_ids, and the committed log entry ID.
FR-6 Reading the active incident returns a deep copy. Mutating a read result, finalize request, or query result must not mutate the stored incident or raw log entry.
FR-7 If raw-log success visibility staging fails, the adapter must reject the finalization and must not store an active incident.
FR-8 If an active incident is already present, another start request must fail closed without overwriting the active incident, appending a success log, or adding lifecycle behavior.
FR-9 When no life_action is present, existing MVP-012 skipped behavior remains unchanged and the store adapter is not called.
FR-10 Existing MVP-013 rejection behavior remains unchanged: rejected or malformed finalize paths leave no query-visible life_incident_started entry.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep the adapter small and deterministic with injected raw-log visibility, fake IDs, and fake clocks in tests.
  • Reuse existing ActiveIncidentSnapshot, RawEventLogEntry, SCHEMA_VERSION, and MVP-012 finalize-result validation instead of creating parallel schemas.
  • Keep the implementation future-compatible by naming the store boundary clearly, but do not add database abstractions, migrations, or unused interfaces.
  • Do not duplicate Raw Event Log entries. The success log must appear through the MVP-013 committed-success visibility path, not through ordinary raw_event_log.append().
  • Keep in-memory durability scoped to the store object's lifetime; do not imply process-restart durability.

Acceptance Criteria

  • MVP-013 is recorded under completed plans, and this file is the only active implementation slice.
  • A user turn with a valid life_action.start_incident can use the concrete in-memory store adapter instead of the MVP-012 recording fake.
  • The store exposes the started incident through the existing ActiveIncidentSource.read_active_incident(request) contract after successful finalization.
  • The same turn exposes the matching life_incident_started entry through the MVP-013 Raw Event Log query surface.
  • Rejected starts and visibility-staging failures leave no active incident and no success log query result.
  • The adapter does not add complete/cancel/resume/interruption/queue behavior or any new RuntimeEvent family.
  • The development journal records source context, files touched, checks run, review notes, next action, and future ideas.
  • Future lifecycle, persistent storage, debug UI, and replay ideas remain parked in future-slices.html.

Test Plan

Unit Tests

  • Finalize a valid incident-start request with the concrete in-memory store adapter and assert read_active_incident(request) returns the expected copy-safe active incident through a validated ActiveIncidentRequest.
  • Assert the adapter stages the exact committed_log_entry so commit_life_incident_start() can confirm it and make it query-visible.
  • Assert staging failure prevents an active incident from being stored.
  • Assert a second start while an active incident exists is rejected without overwriting the stored incident.
  • Assert returned incidents and query results are deep copies.

Integration Tests

  • Run a USER_MESSAGE turn with incident-start opt-in, InMemoryRawEventLog, and the concrete in-memory store adapter; assert the turn returns life_incident_started, the store has the active incident, and the trace query includes life_incident_started.
  • Run the no-life_action path and assert the store adapter is not called and existing visible reply behavior remains unchanged.
  • Run a finalizer rejection or staging failure path and assert no active incident is stored and no life_incident_started query result exists.
  • Run full unittest discovery.

Implementation Boundaries

  • commit_effects.incident_start remains responsible for building and validating the started incident snapshot, committed success log entry, rejection log entry, and commit result.
  • The concrete in-memory LifeIncidentStore may live under the Character State Engine area because incident records are character state, but it should remain one small module with no unused future store methods.
  • The store adapter may implement the existing MVP-012 finalizer protocol directly; do not introduce a second incident-start finalizer protocol.
  • The store must implement character.state.current.ActiveIncidentSource for reads; do not add a second no-argument active-incident read API.
  • runtime.logging.InMemoryRawEventLog remains the Raw Event Log query surface; do not create an incident-specific raw-log query path.
  • runtime.user_turn should only need injection of the concrete adapter where tests or callers previously injected the recording fake. MVP-014 does not make the store the default active_incident_source for later DecisionContext builds.
  • Role Model Loop, Runtime Kernel route policy, and visible reply commit behavior remain unchanged.

Review Notes

  • MVP-014 is a concrete adapter slice, not an incident lifecycle slice.
  • The main risk is accidentally creating a hidden second truth: the in-memory store must not keep a started incident without the matching Raw Event Log success entry becoming query-visible.
  • The active-incident read surface must reuse the MVP-011 ActiveIncidentSource contract so MVP-014 does not create duplicate Character State Engine read APIs.
  • The adapter should reuse the existing staging/confirmation contract from MVP-013 rather than appending atomic success logs through the ordinary append path.
  • Implementation note: src/character/state/incidents.py adds one in-memory store that implements the existing incident-start finalizer and ActiveIncidentSource read contracts.
  • Implementation note: targeted unit and integration tests prove successful starts, query-visible life_incident_started logs, copy safety, staging failure rejection, and second-start rejection.
  • The store should prove copy safety now so later persistent stores do not depend on mutable caller-owned dictionaries.
  • Residual risk: the store is a single in-memory active-incident store scoped to object lifetime. It validates user_id and conversation_id when present in requests, but it does not use them for multi-conversation or multi-user isolation.
  • If implementation pressure suggests persistent databases, queues, active-incident interruption, or completion events, park those as future slices.

Open Questions

  • Should the eventual persistent LifeIncidentStore expose a richer query API beyond the existing ActiveIncidentSource current-active read? Not in MVP-014.
  • Should the store become the default active-incident source for following turns? Not in MVP-014; this slice only proves contract compatibility and targeted injection.
  • How should durable or multi-user incident storage key active incidents by user_id, conversation_id, or character identity? Not in MVP-014.
  • How should a durable database transaction coordinate incident writes with Raw Event Log writes? Not in MVP-014.

Future Ideas Discovered During Planning

  • Persistent LifeIncidentStore backed by a database or append-only incident transition table.
  • Multi-conversation and multi-user incident isolation for durable storage.
  • Minimal incident lifecycle follow-up actions: complete, cancel, resume, go idle, and no change.
  • Runtime Kernel user-interruption policy that marks active incidents interrupted or backgrounded.
  • INCIDENT_COMPLETION RuntimeEvent handling after active incident lifecycle commits exist.
  • Debug inspector and replay views that join incident records with Raw Event Log entries by trace and source event IDs.
