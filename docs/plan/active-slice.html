TypeScript Shadow Port - Runtime Foundation Gated Continuation

Status: active implementation slice

Created: 2026-05-29. Active slice path: docs/plan/active-slice.html. Runtime language: Python remains production source of truth. Shadow language: TypeScript. Branch: mvp-typescript-shadow-port.

Source Context

Product direction comes from the Notion project hub Live Character Framework and the migration goal Goal: create a TypeScript shadow port of Project02's current Python runtime foundation. Local implementation truth comes from the current Python runtime foundation and its completed MVP docs.

The local sources read for this slice are README.html, docs/wiki/index.html, docs/plan/index.html, completed MVP-001, MVP-002, MVP-013, MVP-015, MVP-016, MVP-019, MVP-020, the archived MVP-021, src/runtime/contracts.py, src/runtime/logging.py, src/runtime/kernel.py, and the focused Python tests under tests/unit and tests/integration.

The TypeScript implementation is a shadow port only. It must preserve the Python runtime's externally visible contract semantics while using TypeScript-native modules, strict typing, and runtime validation. It does not replace, import into, or route production behavior away from Python.

Goal

Continue the TypeScript foundation beside the existing Python runtime after completed Stages 1-4 of the Notion migration goal. Stages 5, 6, Stage 7A, Stage 7B, Stage 7C, and Stage 8 are implemented and review-gate clean. The current follow-up goal is to close final review parity findings while keeping the TypeScript implementation shadow-only and not switching production runtime away from Python.

Current Scope

  • Create a separate src-ts/ TypeScript source tree and tests-ts/ test tree.
  • Add minimal Node, TypeScript, Vitest, and lint/typecheck tooling at the repository root.
  • Port runtime contract constants, validation errors, RuntimeEvent validators, CharacterDecision visible-reply/state-patch/life-action normalization, role-model turn result normalization, ISO timestamp validation, remaining-seconds validation, identity checks, and extra-key rejection where Python currently enforces it.
  • Port Raw Event Log entry building, entry/query validation, in-memory query behavior, mutation isolation, duplicate log_id behavior, and atomic success entry expose/confirm/discard behavior.
  • Port Runtime Kernel normalization, generated ID behavior, clock injection, raw log entry creation, deterministic routing, and shared intake for USER_MESSAGE and INCIDENT_COMPLETION.
  • Port Character State read-side request builders and validators, current-state snapshot validation, living_state_brief, active/interrupted incident snapshot and brief validation, recent visible message selection, visible-conversation record mapping, and build_character_decision_context.
  • Port Stage 7A visible conversation Commit Effects only: assistant visible-reply commit, user visible-message projection, raw-log entries, validation failures, deterministic IDs/clocks, append ordering, and visible-log side-effect boundary.
  • Port Stage 7B living-state patch Commit Effects only: commit request building, skipped/committed/rejected result unions, injected prepare store, injected atomic finalizer, committed and rejected raw logs, finalizer result validation, raw-log success visibility confirmation/discard, deterministic commit timestamp, and snapshot consistency validation.
  • Port Stage 7C incident Commit Effects: shared lifecycle helpers, incident start, cancel, complete, incident completion event, interruption policy outcomes, atomic finalizer visibility, rejected logs, and copied result shapes.
  • Port Stage 8 user-turn TypeScript orchestration after Stage 7C passed tests and a three-agent review gate.
  • Use deterministic TypeScript tests as parity oracles against the current Python behavior.
  • Run a review gate after each coherent stage and a final full review gate before completion.

Explicit Non-Goals

  • No production runtime switch from Python to TypeScript.
  • No Python source or Python test deletion, rename, weakening, or refactor.
  • No schema_version change from "0.1".
  • No Role Model Loop, Commit and Effects, or user-turn TypeScript port before Stage 5 is complete, clean, and review-gate approved.
  • No Commit and Effects or user-turn TypeScript port before Stage 6 is complete, clean, and review-gate approved.
  • No user-turn TypeScript port before Stage 7C is complete, clean, and review-gate approved.
  • No production database, external persistence adapter, or broader incident queue beyond the current in-memory/finalizer contracts needed by the shadow port.
  • No retrieval, memory, vector database, TencentDB-Agent-Memory, body simulation, scheduled directives, tools, Live2D, assets, UI, web server, database, or persistence changes.
  • No runtime validation library unless a review proves it reduces risk without changing Python's extra-key and shape behavior. Stages 1-4 default to handwritten validators.
  • No broad formatting over unrelated Python or HTML files.

Functional Requirements

ID Requirement
FR-1 Add minimal TypeScript tooling with strict settings including strict, noUncheckedIndexedAccess, and exactOptionalPropertyTypes.
FR-2 All untrusted TypeScript boundary inputs must enter as unknown and be runtime-validated into precise internal types before use.
FR-3 Port the current Python runtime contract behavior for normalized user messages, incident completion events, visible replies, optional living-state patches, optional start/cancel/complete incident life actions, and role-model turn results.
FR-4 Preserve Python's field-specific trim behavior: user message text is preserved after non-empty validation; visible replies, state patch fields, incident IDs, titles, and reasons are trimmed where Python trims them.
FR-5 Preserve current extra-key behavior. In particular, INCIDENT_COMPLETION.payload, raw log entries, raw log queries, decisions, state patches, and life actions reject unsupported keys, while USER_MESSAGE.payload projects supported keys only.
FR-6 Port Raw Event Log behavior with deep-copy mutation isolation, query filtering, duplicate-id checks, and atomic success entry expose/confirm/discard semantics.
FR-7 Port Runtime Kernel intake so missing or blank event_id and trace_id are generated in event-then-trace order, missing created_at uses the injected clock, missing schema_version becomes "0.1", one runtime_event_received log is appended, and routing happens only after append succeeds.
FR-8 USER_MESSAGE must route to { model_needed: true, next_step: "user_turn" }; INCIDENT_COMPLETION must route to { model_needed: false, next_step: "incident_completion_commit" }.
FR-9 Stage 5 must preserve the Python Character State read-side and context contracts: exact request/snapshot/brief/context shapes, extra-key rejection, copy safety, active-over-interrupted incident precedence, stale interrupted incident omission, recent-message current-event exclusion, deterministic ordering, and message/token budgeting.
FR-10 Stage 6 must preserve the Python Role Model Loop boundary: exact input envelope shape, allowed-action and instruction selection, adapter interface, JSON model-output parsing, CharacterDecision validation, context_build/adapter_call/parse_output failure logs, completed-turn logs, copy safety, and decision-ready result shape without committing effects.
FR-11 Stage 7A must preserve the Python visible conversation Commit Effects boundary: user visible-message projection, assistant visible-reply output, committed/rejected raw-log entries, commit validation failures, trusted-identity behavior, raw-log-before-visible append ordering, append-failure behavior, and copy safety without living-state, incident, finalizer, or user-turn behavior.
FR-12 Stage 7B must preserve the Python living-state patch Commit Effects boundary: build a normalized commit request from USER_MESSAGE and role-model result, skip with no side effects when no patch exists, prepare a snapshot through the injected store, validate snapshot consistency, build the exact living_state_patch_committed raw log entry, finalize through the injected atomic finalizer, confirm or discard raw-log success visibility, and append one living_state_patch_rejected log for commit/store/finalize failures.
FR-13 Stage 7C must preserve Python incident Commit Effects: start, cancel, complete, incident-completion-event, and interruption commits; exact committed/rejected/skipped result shapes; active incident read request shapes; snapshot transition validation; finalizer result validation; raw-log success staging, confirmation, and discard; policy-outcome logs for background/protected interruption; and Python-specific post-visible completion behavior.

Non-Functional Requirements

  • TypeScript should be idiomatic, strict, and concise, with no any, as any, @ts-ignore, broad casts, or unnecessary non-null assertions.
  • Use literal unions and const objects instead of enums so the code remains compatible with Node's erasable TypeScript syntax.
  • Keep helpers only where they reduce duplication or express a real runtime boundary.
  • Keep TypeScript source/test layout separate from Python source/test layout.
  • Add Stage 5+ TypeScript directories only when the stage receives real implementation and focused tests.

Implementation Boundaries

  • TypeScript Runtime Contracts: owns contract constants, error types, and runtime validation into exact contract shapes.
  • TypeScript Raw Logging: owns raw log entry construction, query validation, in-memory storage visibility, and atomic success staging behavior.
  • TypeScript Runtime Kernel: owns event intake normalization, raw log append request, and route selection for implemented event types only.
  • TypeScript Character State Read-Side: owns read request builders, source-facing snapshot validation, compact model-facing briefs, recent visible message selection, visible-conversation mapping, and DecisionContext assembly for Stage 5.
  • TypeScript Role Model Loop: owns Stage 6 model input envelope rendering, allowed-action policy, adapter invocation, JSON model-output parsing, CharacterDecision validation, and role-model success/failure raw-log entries. It does not commit effects.
  • TypeScript Commit Effects Stage 7A: owns visible conversation commit effects only: validated assistant/user visible records, raw committed/rejected logs, and injected visible-log append side effects. It does not own living-state commits, incident lifecycle, finalizers, persistence, or user-turn orchestration.
  • TypeScript Commit Effects Stage 7B: owns living-state patch commit effects only: validated patch commit requests, injected snapshot prepare store, injected atomic finalizer, committed/rejected raw logs, finalizer-result validation, raw-log success visibility confirmation/discard, and copied accepted/rejected result shapes. It does not own visible reply commits, incident lifecycle, concrete persistence, or user-turn orchestration.
  • TypeScript Commit Effects Stage 7C: owns incident lifecycle helpers and incident start/cancel/complete/completion-event/interruption Commit Effects. It owns only injected finalizer/store boundaries and in-memory shadow test support needed for current parity; it does not own user-turn orchestration, external persistence, tools, retrieval, or UI.
  • TypeScript User Turn Stage 8: owns orchestration across already-ported boundaries for USER_MESSAGE turns only. It does not own model provider internals, storage implementations beyond injected boundaries, production routing, tools, retrieval, scheduled directives, or UI.
  • Python Runtime: remains production source of truth and is used only as the behavior oracle for this slice.

Review Notes

  • Initial analysis agents agreed Stages 1-4 should not add character, role-model, commit-effects, or user-turn TypeScript folders.
  • Raw-log atomic visibility and mutation isolation are the highest-risk contracts.
  • Python's current USER_MESSAGE route is model_needed: true and next_step: "user_turn", not the old MVP-001 logged_only example.
  • Generated timestamps must match Python's +00:00 shape rather than JavaScript's default Z string.
  • Continuation analysis agents agreed Stage 5 must land before Stage 6, Stage 7 before Stage 8, and the active slice must authorize Stage 5+ before code.
  • Stage 6 analysis agents called out adapter-output projection, exact instruction strings, failure-log shapes, and adapter/model-input mutation isolation as the highest-risk parity points.
  • Stage 7 analysis agents agreed the safe continuation is Stage 7A visible conversation commit effects only; living-state, incident lifecycle, incident completion, interruption, and user-turn orchestration are too broad for the same gated slice.
  • Stage 7B analysis agents agreed the safe continuation after Stage 7A is living-state patch Commit Effects only. They identified the atomic finalizer path, exact finalizer result shape, single runtime-owned commit_time, raw-log success visibility confirmation/discard, and mutation isolation as the highest-risk parity points.
  • Stage 7C analysis agents identified raw-log atomic visibility, start's special post-visible behavior, interruption's skip/background/protected/interrupted branches, exact finalizer result shape, and ID/clock determinism as the highest-risk parity points.
  • Final review follow-up fixed concrete incident-store absence, direct route validation, raw-log clone parity, incident finalizer error-code parity, invalid lifecycle source-event rejection behavior, and explicit string-clock offset preservation. Production Python removal remains a cutover decision outside this shadow-port follow-up.
  • Final follow-up reviewers found no remaining P0/P1/P2 blockers after stale Stage 8 wording and incident finalizer raw-log-validation code mapping were corrected.
