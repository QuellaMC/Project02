MVP-004 - Durable Local Runtime Continuity

Status: accepted active slice

Created: 2026-06-04. Accepted: 2026-06-04. Active spec: docs/plan/active-slice.html. Previous slice archived at docs/plan/completed/mvp-003-runtime-event-trace-local-chat.html. Suggested implementation branch: feature/mvp-004-durable-local-runtime-continuity.

Source Context

Product direction comes from the Notion project hub Live Character Framework, especially 01 - Framework Overview, 02 - Runtime Architecture, and 08 - Runtime Logging & Trace.

Long-term direction: runtime truth should be durable enough to support debugging, inspection, replay, memory, retrieval, scheduling, provider edges, and future training data.

Local rebuild direction comes from AGENTS.md and AGENTS.repo.md. This slice must grow from the current working local chat path and keep the architecture pressure-driven. It should make the existing runtime truth durable before adding memory, providers, schedulers, model calls, or a full Runtime Kernel.

Current Product Before This Slice

MVP-003 gives the repo a local runtime-shaped chat path. Each non-exit chat input becomes one USER_MESSAGE runtime event with event identity, trace identity, ordered trace entries, raw event records, and visible conversation log records. The default chat output is still simple and user-facing, while --trace can print one JSON Line summary per processed input. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> local runtime adapter handles the event
  -> conversation core validates and replies
  -> in-memory trace/log records explain the turn
  -> chat CLI prints Mira's reply

The limitation is that the trace, raw event records, and visible conversation records are local process memory. Once the chat process exits, the runtime truth is gone.

Product After This Slice

Local chat should become a durable local session. A user can run chat, talk to Mira, exit, restart the command, and resume the same local session with recent visible context restored from stored runtime truth. 

terminal input
  -> create USER_MESSAGE RuntimeEvent
  -> append durable raw event and trace records
  -> local runtime adapter handles the event
  -> conversation core validates and replies
  -> append durable visible conversation records
  -> chat CLI prints Mira's reply

later process restart
  -> load the local session
  -> rehydrate recent visible transcript
  -> continue the conversation

This is not semantic memory yet. Mira does not summarize relationship history, search old facts, retrieve exact memories, or call a live model in this slice. MVP-004 only makes the local runtime's truth durable so later memory and retrieval slices have one real source to read.

Goal

Replace MVP-003's process-only runtime truth with a versioned local durable store for one local character chat product path. The store should persist runtime events, traces, raw event records, and visible conversation records; support session resume after process restart; and provide a narrow inspection path for debugging what happened.

Current Scope

  • One local durable storage contract for the rebuilt TypeScript product path.
  • One default dev-local store root, proposed as .project02-runtime/, with tests using temporary directories.
  • A schema/version marker so later migrations can be explicit.
  • One session catalog with stable, storage-safe local session IDs and created/updated timestamps.
  • Per-session log directories under the store root; runtime records do not need duplicate sessionId fields because the durable path scopes them to one session.
  • File-backed append/read behavior for per-session runtime traces, raw event records, and visible conversation records.
  • Atomic-enough local writes for this single-process CLI slice, with clear behavior on partial/corrupt records.
  • Session rehydration that restores recent visible transcript context from persisted conversation records.
  • Chat CLI persistence options for creating, resuming, and selecting local sessions while preserving the default chat contract.
  • A narrow read-only local inspection command that can show stored sessions and turn evidence without requiring a running chat process.
  • Compatibility with MVP-001 relay, MVP-002 default chat behavior, and MVP-003 trace mode unless a reviewed compatibility note changes the contract.

Explicit Non-Goals

  • No live model provider call, API key, provider config, prompt template, or model selection.
  • No Twilio, WhatsApp, webhook, HTTP server, browser UI, mobile app, or external provider edge.
  • No semantic memory, retrieval index, summaries, embeddings, relationship model, or long-term personality adaptation.
  • No scheduler, reminders, due directives, background worker, cron loop, or proactive message delivery.
  • No tools, external side effects, documents, calendars, accounts, authentication, permissions matrix, or user-data sync.
  • No database server, SQLite dependency, cloud storage, encryption layer, backup system, or cross-device migration.
  • No full Runtime Kernel, Character State Engine, Role Model Loop, Commit and Effects Engine, or old runtime module restoration from legacy/typescript.
  • No replay UI that re-executes model calls or mutates state from old logs.
  • No multi-character support or multi-user account system.

Finished Slice

Before MVP-004 After MVP-004
Local chat history exists only while the Node process is running. Local chat history can be restored from a durable local session store.
Runtime trace and raw event records disappear when the CLI exits. Runtime trace and raw event records survive process restart for inspection.
Starting chat always creates a fresh in-memory conversation unless tests wire state manually. Starting chat can resume a chosen local session and rebuild recent visible context.
There is no repo-owned storage version or local runtime file layout. The repo has a versioned local storage contract with explicit read/write and error behavior.
Debugging a prior turn requires terminal output or a test reproduction. A local inspect path can show sessions, event IDs, trace IDs, statuses, and visible messages after exit.
Future memory/retrieval work has no durable runtime truth to consume. Future memory/retrieval work can build from one persisted local truth layer.

Functional Requirements

ID Requirement
FR-1 The product defines a versioned local runtime storage contract with a clear store root, session catalog, per-session directories, and append-only record files.
FR-2 The default dev-local store root is ignored by Git, and tests can inject temporary store roots without touching user or repository data.
FR-3 The durable runtime log store can append and read per-session runtime trace entries, raw event records, and conversation log records while preserving MVP-003 record identity fields.
FR-4 Stored snapshots are immutable from caller perspective and do not expose mutable arrays or record objects across reads.
FR-5 A chat session can be rehydrated from stored visible conversation records so a resumed session sees recent visible context from prior process runs.
FR-6 Successful turns durably append the same trace, raw event, and visible conversation evidence that MVP-003 records in memory.
FR-7 Rejected turns durably append rejection evidence without committing fake visible conversation messages.
FR-8 The chat CLI supports explicit session creation/resume/selection while keeping the existing default chat transcript and prompt behavior stable.
FR-9 A local inspection command can list sessions and print turn-level runtime evidence after the original chat process exits.
FR-10 Partial, corrupt, missing, or future-version local store data fails with clear errors and does not silently fabricate character history.
FR-11 The existing MVP-001 relay command, MVP-002 default chat behavior, and MVP-003 trace JSONL behavior remain covered by compatibility tests.

Acceptance Criteria

ID Criterion
AC-1 A focused test can create a deterministic local store, append one successful turn to one session, reopen the store, and read back matching event IDs, trace IDs, raw records, trace entries, and visible messages from that session only.
AC-2 A resumed chat session can use visible context from a prior process run to produce the same context-aware deterministic reply behavior as an uninterrupted in-memory session, while preserving next visible message IDs without duplicating old IDs.
AC-3 Rejected input and rejected character replies are persisted as rejected runtime outcomes and leave persisted conversation records unchanged for the failed turn.
AC-4 Callers cannot mutate stored records by changing returned snapshots, input arrays, visible message objects, raw event payload summaries, or trace entries after append/read.
AC-5 The CLI can create a named or generated local session, resume that session after process restart, and select a different session without mixing visible transcripts or per-session logs.
AC-6 The local inspect command can list sessions and show event ID, trace ID, status, step names, and visible message text for a selected session without starting a chat loop.
AC-7 Corrupt JSONL records, missing schema markers, unsupported schema versions, and malformed stored visible messages fail loudly with tested errors.
AC-8 Default pnpm chat, pnpm chat -- --trace, and pnpm relay compatibility tests still pass.
AC-9 pnpm lint, pnpm typecheck, pnpm test, strict unused-symbol TypeScript, whitespace checks, and HTML sanity checks pass.

Parallel Child Tasks

This draft is intentionally shaped for five month-sized subthreads. CT-01 must freeze the shared storage contract, module map, exported types, and test fixtures first. CT-02 through CT-05 should consume that exported contract; if they start before CT-01 is merged, they should write contract tests or adapter-facing scaffolding rather than creating alternate production record shapes.

  • CT-01 - Durable Storage Contract
  • CT-02 - File-Backed Runtime Log Store
  • CT-03 - Session Catalog And Rehydration
  • CT-04 - Chat CLI Persistence UX
  • CT-05 - Inspection, Integration Review, And Docs

Implementation Boundaries

  • src/local-storage.ts owns file layout, schema version, storage-safe session identity, record codecs, error taxonomy, and test fixtures.
  • src/file-runtime-log-store.ts owns append/read behavior for per-session trace, raw event, and conversation log records.
  • src/session-store.ts owns session metadata, create/list/select behavior, and rehydration of visible transcript context.
  • The local runtime adapter remains the owner of running one USER_MESSAGE event through the conversation core.
  • The conversation core remains the owner of character profile, turn validation, deterministic replies, transcript commit rules, and any minimal public rehydration seam needed to seed a session from persisted visible messages.
  • src/chat-cli.ts owns terminal UX, session flags, default behavior compatibility, and clear error messages.
  • src/inspect-cli.ts owns read-only debug output and must not mutate runtime state.
  • The relay command remains the MVP-001 smoke path and should not move into the durable runtime layer in this slice.

Minimal CLI Surface

  • pnpm chat uses the default dev-local store root and a default local session, creating it if missing.
  • pnpm chat -- --store <path> --session <session-id> resumes or creates the selected session in the selected store.
  • pnpm chat -- --store <path> --new-session <session-id> creates a new selected session and fails clearly if that session already exists.
  • pnpm chat -- --trace keeps MVP-003 JSON Lines trace summaries on stderr.
  • pnpm inspect -- --store <path> --sessions lists local sessions without starting chat.
  • pnpm inspect -- --store <path> --session <session-id> prints read-only turn evidence for the selected session.

Test Plan

  • Contract tests for schema markers, per-session file layout, storage-safe session IDs, record codecs, and unsupported/corrupt store failures.
  • Unit tests for file-backed append/read behavior, immutable snapshots, raw payload summaries, trace ordering, and visible conversation record storage.
  • Integration tests that run a turn, reopen the store, rehydrate the session, continue with recent visible context, and append next visible message IDs without duplication.
  • Rejection-path tests for invalid input, invalid agent replies, unexpected runtime failures, corrupt JSONL, and malformed persisted messages.
  • CLI boundary tests for default chat, --store, --session, --new-session, trace mode, inspect output, clear errors, and relay compatibility.
  • Docs and HTML sanity checks for active slice, child task packets, and dated journal updates.

Review Decisions Requested

  • Storage root: this draft proposes .project02-runtime/ as the default dev-local root, ignored by Git, with explicit CLI/test overrides.
  • Storage format: this draft proposes simple versioned files and JSON Lines records rather than SQLite or a database server.
  • Session scoping: this draft proposes per-session directories under the store root rather than adding duplicate sessionId fields to every runtime record.
  • Session behavior: this draft proposes one local session catalog, a default local session, and explicit session selection, not accounts or cross-device identity.
  • Inspection behavior: this draft proposes a read-only pnpm inspect surface for stored sessions and turn evidence, not replay that mutates state.
  • Runtime scope: this draft proposes durability around the existing USER_MESSAGE local path only, not a full Runtime Kernel.

Future Pressure

Once local runtime truth is durable, later slices can add semantic memory, retrieval indexing, compaction, model I/O snapshots, scheduled events, provider webhooks, richer replay, or a broader Runtime Kernel. Those later slices should read from this durable truth layer instead of creating parallel storage for the same conversation and runtime evidence.
