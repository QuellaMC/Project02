MVP-005 - User Visible Message Projection

Status: implemented and tested, pending review

Created: 2026-05-16. Implemented: 2026-05-16. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages checked for this slice are 02 - Runtime Architecture, 08 - Runtime Logging & Trace, 06 - Character State Engine & Retrieval Management, and 09 - MVP Roadmap & Open Questions.

ConversationLog is the visible user-facing interaction projection. RawEventLog remains lossless internal truth. MVP-005 records the user side of that visible projection without adding concrete storage or a full user-turn orchestrator.

Local implementation truth comes from MVP-001, MVP-002, MVP-003, and MVP-004. MVP-004 can read a bounded recent visible message tail through an injected source, but the runtime still has no committed visible user-message record that can later feed that source.

Goal

Add the smallest Commit and Effects behavior after MVP-004: accept one normalized USER_MESSAGE, build one user-visible conversation record from that event, append one raw projection log entry through the existing raw-log boundary, append the user-visible record through the existing injected VisibleConversationLog boundary, and return a deterministic result. This slice must not add a concrete database, a user-turn orchestrator, model calls, retrieval, character state, new model actions, or assistant commit behavior changes.

Current Scope

  • One accepted source event type: normalized USER_MESSAGE with schema_version = "0.1".
  • One new visible record kind: user_visible_message.
  • One visible role: user.
  • One new commit status: user_visible_message_committed.
  • One new reject status: user_visible_message_rejected.
  • One accepted raw log kind: user_visible_message_committed.
  • One rejected raw log kind: user_visible_message_rejected.
  • Reuse the existing injected append-only VisibleConversationLog protocol from MVP-003.
  • Reuse existing normalized USER_MESSAGE validation from runtime.contracts.
  • Implement beside the existing visible-reply commit code and reuse or minimally extract existing Commit and Effects helper behavior for trusted source identity, failure shaping, snapshot copying, and shared contract error wrapping; do not copy private helper logic into a parallel implementation.
  • If VisibleConversationLog typing is too assistant-output-specific for user visible messages, widen or rename the existing protocol in a behavior-preserving way instead of adding another append interface.
  • Deep-copy visible message and raw-log snapshots before returning or appending.
  • Focused unit and integration tests for valid projection, malformed inputs, append ordering, and failure behavior.

Explicit Non-Goals

  • No full user-turn orchestrator across Runtime Kernel, Role Model Loop, and Commit and Effects.
  • No changes to Runtime Kernel routing, model-needed policy, event priority, or interruption behavior.
  • No live model provider, fake model adapter, prompt rendering, model output parsing, or Role Model Loop behavior change.
  • No change to MVP-003 assistant visible-reply commit behavior or schema.
  • No concrete ConversationLog storage adapter, migrations, transactions, query API, pagination, or indexes.
  • No recent-message source implementation backed by committed visible records.
  • No retrieval index, embeddings, keyword search, active threads, summaries, compaction, or debug inspector.
  • No character state, living state, virtual body, incidents, scheduled directives, tools, Live2D, assets, scheduler, worker, external service, UI delivery, or notification path.
  • No deduplication policy beyond the single source event being projected by the caller once; durable idempotency remains future work.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-005 should implement the contract in Python 3 and test it with unittest.

UserVisibleMessage

type UserVisibleMessage = {
  message_id: string
  trace_id: string
  source_event_id: string
  kind: "user_visible_message"
  role: "user"
  created_at: string
  schema_version: "0.1"
  text: string
  user_id?: string
  conversation_id?: string
  source: {
    runtime_event_type: "USER_MESSAGE"
  }
}

created_at is copied from the normalized source event so visible transcript ordering follows event time. The raw log entry timestamp records when projection was committed. Do not add a second visible-message timestamp in this slice.

UserVisibleMessageCommittedLogEntry

type UserVisibleMessageCommittedLogEntry = {
  kind: "user_visible_message_committed"
  trace_id: string
  event_id: string
  schema_version: "0.1"
  data: {
    source_event: RuntimeEvent
    message: UserVisibleMessage
  }
}

UserVisibleMessageRejectedLogEntry

type UserVisibleMessageRejectedLogEntry = {
  kind: "user_visible_message_rejected"
  trace_id: string
  event_id: string
  schema_version: "0.1"
  data: {
    source_event: unknown
    failure: {
      stage: "user_visible_message_validation"
      code: string
      message: string
    }
  }
}

UserVisibleMessageCommitResult

type UserVisibleMessageCommitResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "user_visible_message_committed"
  message: UserVisibleMessage
}

UserVisibleMessageRejectResult

type UserVisibleMessageRejectResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "user_visible_message_rejected"
  failure: {
    stage: "user_visible_message_validation"
    code: string
    message: string
  }
}

Functional Requirements

ID Requirement
FR-1 The projection helper accepts only a normalized USER_MESSAGE event with schema_version = "0.1".
FR-2 The helper builds exactly one UserVisibleMessage from the normalized event payload text and optional user_id / conversation_id.
FR-3 The helper generates exactly one message_id using the injected ID generator and does not reuse event_id as the visible message ID.
FR-4 The visible message trace_id, source_event_id, created_at, schema_version, and text are derived from the validated normalized event, not duplicated literals.
FR-5 For a valid event, the helper appends one user_visible_message_committed raw log entry before appending the visible message record.
FR-6 If raw-log append fails, the helper propagates the error and does not append a visible message.
FR-7 If visible-message append fails after raw logging succeeds, the helper propagates the error and leaves the committed raw log available for reconciliation.
FR-8 If source-event validation fails after trusted event_id, trace_id, and type are present, the helper appends one user_visible_message_rejected raw log and returns a reject result with no visible append.
FR-9 If trusted source identity is missing, the helper raises validation error without appending a rejection log, matching MVP-003 malformed-identity behavior.
FR-10 The raw committed/rejected log entries and returned result deep-copy snapshots so caller-side mutation cannot alter append-only truth.
FR-11 The implementation stays in the existing Commit and Effects boundary and does not introduce a new storage module or Character State Engine package.

Non-Functional Requirements

  • Keep behavior deterministic for the same normalized event, ID generator, and clock.
  • Preserve all MVP-001 through MVP-004 public contracts unless this spec explicitly adds the user visible projection path.
  • Do not rename or reshape MVP-003 assistant output records in this slice.
  • Reuse shared contract helpers instead of duplicating primitive validation.
  • Prefer small helper extraction in the existing Commit and Effects module when MVP-005 needs the same trusted-identity, failure, snapshot, or contract-wrapping behavior as MVP-003.
  • Any helper extraction or protocol widening must be covered by existing MVP-003 tests plus focused MVP-005 tests.
  • Keep constants for statuses, raw log kinds, and visible message kind local and explicit.
  • Do not add speculative adapters, empty folders, database dependencies, query helpers, replay helpers, or background workers.
  • Keep raw truth separate from the visible transcript projection.

Acceptance Criteria

  • A valid normalized USER_MESSAGE appends one UserVisibleMessage to an injected visible conversation log.
  • The same valid projection appends one user_visible_message_committed raw log entry before the visible append.
  • The visible message uses a generated message_id, source event timestamp, source event text, and optional source event user_id / conversation_id.
  • Unsupported event type, schema version, malformed timestamp, or empty text reject without visible append when trusted identity exists.
  • Missing trusted identity raises without a rejection log.
  • Raw-log append failure prevents visible append.
  • Visible append failure leaves the committed raw projection log for reconciliation.
  • Returned results and log entries are protected from caller mutation.
  • No model adapter, live provider, retrieval source, concrete storage adapter, external service, or UI delivery path is called.
  • Relevant unit and integration tests pass.
  • The development journal records files changed and tests run when the implementation is completed.
  • Future ideas discovered during planning are recorded in future-slices.html.

Test Plan

Unit Tests

  • Builds a UserVisibleMessage from a normalized USER_MESSAGE.
  • Copies optional user_id and conversation_id only when present.
  • Rejects unsupported event type, unsupported schema version, malformed created_at, missing payload, and empty text.
  • Builds committed raw log entries with deep-copied source event and visible message snapshots.
  • Builds rejected raw log entries with deep-copied source event and failure snapshots.
  • Rejects unsupported failure codes for user-visible projection logs.

Integration Tests

  • Valid normalized USER_MESSAGE to raw projection log append, visible message append, and committed result.
  • Invalid source event with trusted identity to rejected raw log and no visible append.
  • Raw-log append failure blocks visible append.
  • Visible append failure preserves the committed raw projection log.
  • Existing MVP-003 visible-reply commit tests continue to pass unchanged.

Implementation Boundaries

  • Runtime Kernel remains responsible for event intake and normalization only.
  • Commit and Effects Engine owns this projection because it is a durable visible transcript append.
  • Role Model Loop remains unchanged; it still renders context, invokes the injected adapter, parses visible-reply decisions, and logs model turns.
  • Character State Engine remains unchanged; it still has no concrete package in this repo.
  • RawEventLog remains append-only and separate from ConversationLog.
  • VisibleConversationLog remains an injected append-only boundary; a concrete adapter is still future work.
  • Do not introduce a second append protocol for user visible messages; adjust the existing append boundary only if needed and only without changing runtime behavior.
  • No database, network client, model provider, renderer, scheduler, worker, retrieval index, or tool implementation is introduced.

Failure Behavior

  • Invalid source event shape raises validation error before visible append.
  • If trusted identity exists, validation failure appends one rejection raw log and returns user_visible_message_rejected.
  • If trusted identity is missing, validation failure raises without raw or visible append because the rejection log cannot be safely addressed.
  • Raw-log append failure propagates and prevents visible append.
  • Visible append failure propagates after raw commit logging succeeds; reconciliation behavior is a future slice.
  • No retry, deduplication, transaction manager, or idempotency key is introduced.

  • Added UserVisibleMessage builders and raw committed/rejected projection log helpers without changing the MVP-003 assistant output schema.
  • Widened the existing VisibleConversationLog protocol typing to accept visible conversation records while keeping one append boundary.
  • Reused shared normalized USER_MESSAGE validation, trusted source identity extraction, failure shaping, contract-error wrapping, and snapshot copying patterns.
  • Added unit tests for message construction, optional field handling, invalid source events, committed/rejected raw log snapshots, and unsupported projection failure codes.
  • Added integration tests for valid projection append order, trusted validation rejection, missing trusted identity, raw-log append failure, and visible append failure reconciliation surface.

Pre-Code Review Notes

  • The behavior does not already exist; MVP-003 commits assistant visible replies, while user messages exist only as raw normalized events.
  • The slice is smaller than a full user-turn orchestrator because it projects only the incoming user message into the visible transcript boundary.
  • The slice is smaller than concrete conversation storage because it reuses the injected append-only interface and in-memory test fakes.
  • The slice supports the MVP-004 recent-message contract by creating a future-compatible user-side visible record, but it does not implement the source that reads those records.
  • Implementation should avoid duplicating MVP-003 private helper logic. If the user visible projection needs the same behavior as _extract_trusted_source_identity(), _build_failure(), snapshot copying, or _wrap_contract_error(), extract the smallest shared helper and keep existing tests green.
  • The only schema expansion is the user visible message record plus committed/rejected raw projection log shapes.
  • Security risk stays low because the source is already user-visible input and no external side effects are introduced.

Open Questions

  • Should assistant and user visible records later converge into one shared VisibleConversationMessage contract? Not in MVP-005; avoid reshaping MVP-003 before a second consumer needs it.
  • Should projection become idempotent by source_event_id? Not in MVP-005; durable deduplication needs a concrete store or transaction boundary.
  • Should the recent-message source read directly from the same visible log next? Likely yes, but that belongs in a later storage/source slice.

Future Ideas Discovered During Planning

  • Concrete append-only ConversationLog storage adapter with source-event idempotency.
  • Recent-message source backed by committed visible conversation records.

  • Conversation projection reconciliation for visible append failures after raw projection logs commit.
