MVP-003 - Minimal Visible Reply Commit

Status: implemented and tested, pending review

Created: 2026-05-15. Implemented: 2026-05-15. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The relevant source pages are 01 - Framework Overview, 02 - Runtime Architecture, 08 - Runtime Logging & Trace, and 09 - MVP Roadmap & Open Questions.

Current direction: the model proposes a structured CharacterDecision; Commit and Effects validates what the runtime accepts, commits durable effects, and records the result in the raw log.

Local implementation truth comes from MVP-001 and MVP-002. MVP-002 can parse a visible_reply-only CharacterDecision and return status = "decision_ready_for_commit". It intentionally stops before storing any visible reply.

Goal

Add the smallest Commit and Effects Engine behavior after MVP-002: accept a parsed visible-reply decision plus the normalized source USER_MESSAGE, validate that the decision belongs to that event, append one visible conversation output through an injected interface, append one raw commit log entry, and return a deterministic commit result. Invalid decisions with trustworthy trace identity are rejected through a raw log entry and do not create visible output.

Current Scope

  • One source event type: normalized USER_MESSAGE from MVP-001.
  • One model-turn result status: decision_ready_for_commit from MVP-002.
  • One allowed decision action: visible_reply.
  • One visible output kind: assistant_visible_reply.
  • One injected append-only VisibleConversationLog interface for the committed output.
  • One accepted raw log kind: visible_reply_committed.
  • One rejected raw log kind: visible_reply_rejected.
  • Deterministic output ID, log ID, and timestamp generation through existing injected helpers.
  • Focused unit tests for validation, output building, raw-log builders, and rejection behavior.
  • One integration test from MVP-002-style result to visible output append and raw commit log append.

Explicit Non-Goals

  • Calling a live model provider or changing Role Model Loop behavior or model-provider execution.
  • Wiring a full user-turn orchestrator through RuntimeKernel.
  • Real UI delivery, push notifications, streaming, network calls, or external side effects.
  • Concrete database adapters, migrations, or transactional storage.
  • Conversation history retrieval or adding recent messages to DecisionContext.
  • CharacterRuntimeState, living state, virtual body, incidents, scheduled directives, continuity, retrieval, tools, Live2D, assets, compaction, or replay UI.
  • State patches, incident actions, tool requests, scheduled directive actions, continuity writes, or permission-confirmation flows.
  • Generating a durable decision_id or introducing a separate decision store.
  • Changing the MVP-001 event schema or MVP-002 decision schema.

Minimal Schema

These TypeScript-style shapes define the intended behavior contract. MVP-003 should implement the contract in Python 3 and test it with unittest.

VisibleReplyCommitInput

type VisibleReplyCommitInput = {
  schema_version: "0.1"
  source_event: RuntimeEvent & {
    type: "USER_MESSAGE"
    event_id: string
    trace_id: string
    payload: {
      text: string
      user_id?: string
      conversation_id?: string
    }
  }
  role_model_result: RoleModelTurnResult & {
    status: "decision_ready_for_commit"
    model_called: true
    decision: CharacterDecision & {
      action: "visible_reply"
      visible_reply: {
        text: string
      }
    }
  }
}

VisibleConversationOutput

type VisibleConversationOutput = {
  output_id: string
  trace_id: string
  source_event_id: string
  kind: "assistant_visible_reply"
  created_at: string
  schema_version: "0.1"
  text: string
  user_id?: string
  conversation_id?: string
  source: {
    decision_action: "visible_reply"
    role_model_status: "decision_ready_for_commit"
  }
}

user_id and conversation_id are copied from the normalized source event payload when present. The commit step does not invent these values.

VisibleReplyCommittedLogEntry

type VisibleReplyCommittedLogEntry = {
  log_id: string
  trace_id: string
  event_id: string
  kind: "visible_reply_committed"
  created_at: string
  schema_version: "0.1"
  data: {
    source_event: RuntimeEvent
    role_model_result: RoleModelTurnResult
    output: VisibleConversationOutput
  }
}

VisibleReplyRejectedLogEntry

type VisibleReplyRejectedLogEntry = {
  log_id: string
  trace_id: string
  event_id: string
  kind: "visible_reply_rejected"
  created_at: string
  schema_version: "0.1"
  data: {
    source_event: unknown
    role_model_result_snapshot: unknown
    decision_snapshot?: unknown
    failure: {
      stage: "commit_validation"
      code:
        | "malformed_commit_input"
        | "identity_mismatch"
        | "unsupported_result_status"
        | "unsupported_action"
        | "empty_reply_text"
      message: string
    }
  }
}

In rejected logs, source_event is a raw source-event snapshot for audit and replay. It may be malformed or unsupported, so it is intentionally not typed as a normalized RuntimeEvent.

VisibleReplyCommitResult

type VisibleReplyCommitResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "visible_reply_committed"
  output: VisibleConversationOutput
}

VisibleReplyRejectResult

type VisibleReplyRejectResult = {
  trace_id: string
  event_id: string
  event_type: "USER_MESSAGE"
  status: "visible_reply_rejected"
  failure: {
    stage: "commit_validation"
    code: string
    message: string
  }
}

Functional Requirements

ID Requirement
FR-1 The commit boundary accepts only a normalized USER_MESSAGE source event with schema_version = "0.1".
FR-2 The commit boundary accepts only an MVP-002 result with status = "decision_ready_for_commit" and model_called = true.
FR-3 trace_id and event_id must match across the source event, role-model result, and parsed decision.
FR-4 Only action = "visible_reply" is accepted.
FR-5 visible_reply.text must be a non-empty string after trimming.
FR-6 Successful validation builds one VisibleConversationOutput using an injected output ID generator and clock.
FR-7 Successful validation appends exactly one visible output through VisibleConversationLog.
FR-8 Before appending visible output, the commit boundary appends exactly one visible_reply_committed raw log entry.
FR-9 Supported validation failures with trustworthy source trace identity append one visible_reply_rejected raw log entry and append no visible output.
FR-10 The result envelope preserves trace_id, event_id, and event_type from the normalized source event.

Non-Functional Requirements

  • Keep the implementation deterministic under injected clock and ID generator.
  • Reuse runtime.logging.build_raw_log_entry() for raw log envelopes.
  • Keep the new code under the smallest module path needed for Commit and Effects behavior.
  • Deep-copy committed output and log snapshots so caller-side mutation cannot change append-only in-memory truth.
  • Do not add speculative storage adapters, transaction managers, permission matrices, outbox workers, UI delivery, or orchestration layers.
  • Preserve MVP-001 and MVP-002 tests unless a spec-backed compatibility issue is found.

Acceptance Criteria

  • A valid MVP-002 visible-reply result can produce one visible output record.
  • The visible output append is called exactly once for a valid commit.
  • A valid commit appends exactly one visible_reply_committed raw log entry.
  • Unsupported action, unsupported status, empty reply text, or trace/event mismatch rejects without visible output.
  • A supported rejection appends exactly one visible_reply_rejected raw log entry.
  • No live model provider, external service, UI delivery, or concrete database is called.
  • Relevant unit tests pass.
  • Relevant integration tests pass.
  • The development journal records files changed and tests run.
  • Future ideas discovered during implementation are recorded in future-slices.html.

Test Plan

Unit Tests

  • Validates matching trace_id and event_id across source event, role-model result, and decision.
  • Builds a minimal VisibleConversationOutput from a visible-reply decision.
  • Copies optional user_id and conversation_id from the source event when present.
  • Rejects unsupported result status, unsupported action, empty reply text, unsupported source event type, unsupported schema version, and identity mismatch.
  • Builds committed and rejected raw log entries with deep-copied snapshots.
  • Rejects unsupported rejection failure codes.

Integration Tests

  • MVP-002-style result plus normalized source event to visible_reply_committed raw log append to visible output append.
  • Invalid visible-reply decision with valid trace identity to visible_reply_rejected raw log append and no visible output append.

Implementation Boundaries

  • Runtime Kernel remains responsible for event intake and normalization.
  • Role Model Loop remains responsible for model input rendering, fake adapter invocation, and output parsing.
  • Commit and Effects Engine owns validation, visible output construction, visible output append, and commit/reject raw logging for this slice.
  • RawEventLog remains an explicit append-only boundary.
  • VisibleConversationLog is an injected append-only test interface, not a concrete database or UI delivery layer.
  • No concrete database, network client, model provider, renderer, scheduler, worker, or tool implementation is introduced.

Failure Behavior

  • Malformed source event identity fails before visible output append. If no trustworthy trace_id and event_id are available, no raw rejection log is appended.
  • Unsupported result status, unsupported action, empty reply text, or identity mismatch appends one visible_reply_rejected entry when the source event provides trustworthy trace identity.
  • Rejected commits do not append visible output and do not append visible_reply_committed.
  • Raw log append failure prevents visible output append and prevents a successful VisibleReplyCommitResult from being returned.
  • Visible output append failure propagates after visible_reply_committed is logged, leaving an audit record that can drive reconciliation or retry.
  • No retry, dedupe, transaction, or recovery policy is implemented in this slice.

Pre-Code Review Notes

  • The behavior does not already exist; MVP-002 intentionally stopped at decision_ready_for_commit.
  • The slice is intentionally smaller than the full Phase 1 user turn loop because it does not orchestrate Runtime Kernel to Role Model Loop to Commit and Effects in one public API.
  • A minimal Commit and Effects module is justified because the framework assigns durable output commits and side effects to that boundary.
  • The visible output store is an interface only because this slice needs a commit target but not a concrete database.
  • The schema introduces only a visible output record plus commit/reject log records needed for this behavior.
  • Security stays narrow because the only effect is an in-process visible conversation output append; there are no external messages, tools, files, accounts, or money-related actions.

Post-Code Review Notes

  • The implementation adds one focused commit_effects.visible_reply module for the first Commit and Effects boundary.
  • The visible conversation store is an injected VisibleConversationLog.append(output) protocol; no concrete database, UI delivery, outbox, transaction layer, or external side effect was added.
  • Successful commits validate the normalized source event, MVP-002 result status, matching trace/event IDs, and visible_reply decision before appending visible output.
  • Successful commits append visible_reply_committed before visible output so raw-log storage failure cannot leave an unlogged visible side effect.
  • Visible output append failure now leaves a raw audit record with the intended output for reconciliation instead of an unlogged visible output.
  • Supported validation failures with trustworthy source identity append one visible_reply_rejected raw log entry and return a rejected result without visible output.
  • Rejected logs store data.source_event as a raw source-event snapshot, not a normalized RuntimeEvent, so malformed-but-identifiable inputs remain available for audit and replay.
  • Malformed source identity raises before a rejection log because there is no trustworthy trace_id and event_id.
  • Committed output and raw log snapshots are deep-copied so caller mutation cannot change append-only in-memory truth.
  • The implementation reuses runtime.logging.build_raw_log_entry(), generate_id(), and clock_timestamp() for envelope, ID, and timestamp behavior.
  • Runtime Kernel, Role Model Loop, and Commit and Effects now share runtime.contracts.validate_normalized_user_message_event() for normalized USER_MESSAGE validation.
  • Role Model Loop and Commit and Effects now share runtime.contracts.normalize_visible_reply_decision() for the visible-reply CharacterDecision contract while preserving boundary-specific error types.
  • Role Model Loop and Commit and Effects now share the decision_ready_for_commit status constant; a fuller turn-result envelope validator remains parked as a future idea.
  • No Runtime Kernel orchestration, Role Model Loop behavioral or model-provider changes, character state, incidents, tools, retrieval, Live2D, assets, scheduler, or concrete storage were introduced.
