MVP-015 - Character State Engine Context Builder Boundary v0.1

Status: implemented locally; implementation PR pending

Created: 2026-05-20. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-015-context-builder-boundary.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 09 - MVP Roadmap & Open Questions, 02 - Runtime Architecture, 03 - Role Model Loop & Decision Contract, 05 - Living State & Scheduled Life, 06 - Character State Engine & Retrieval Management, and 08 - Runtime Logging & Trace.

Notion assigns compact DecisionContext building to the Character State Engine. MVP-015 only moves the already-proven source orchestration for recent visible messages, living_state_brief, and active_incident behind that boundary while preserving the current model-facing context shape.

Local implementation truth comes from completed MVP-001, MVP-002, MVP-004, MVP-006, MVP-007, MVP-008, MVP-011, and MVP-014.

Goal

Add the smallest Character State Engine context-builder boundary that owns source requests, source-response validation, copy safety, selection, and final assembly for the existing USER_MESSAGE DecisionContext. Role Model Loop should still render the same model input, call the adapter the same way, parse the same decision contract, and append the same role-model logs.

Current Scope

  • One implemented event family remains in scope: USER_MESSAGE.
  • One call type remains in scope: user_message_visible_reply.
  • One new Character State Engine context-builder module or equivalent boundary is in scope.
  • The boundary owns orchestration for three already-implemented context sources: recent visible messages, current living state, and active incident.
  • The boundary returns the existing DecisionContext shape with the same event, character_snapshot, and allowed_actions fields.
  • The existing Role Model Loop remains responsible for rendering model input, adapter invocation, structured output parsing, and role-model turn logs.
  • Compatibility wrappers may remain in role_model.loop if needed so existing tests and callers can keep importing current symbols while the implementation delegates to Character State Engine code.

Explicit Non-Goals

  • No new DecisionContext fields, no renamed fields, and no changed field meanings.
  • No retrieval planner, Unified Retrieval Index, context.retrieve() tool, semantic search, keyword search, exact source expansion, summaries, compaction, active threads, or context budget percentages beyond the existing recent-message limits.
  • No new RuntimeEvent type, Runtime Kernel route policy, model provider, Role Model Adapter behavior, prompt behavior, output action, parser behavior, or allowed action combination.
  • No new Raw Event Log kind such as decision_context_built; keep context-build failures logged through the existing role_model_turn_failed path.
  • No storage migration, database adapter, concrete conversation store, concrete state store, incident lifecycle action, interruption policy, scheduler, body state, Live2D status, tool, asset, debug UI, or replay executor.
  • No behavioral change to run_user_message_turn() beyond threading the same injected sources through the new boundary.

Minimal Schema

CharacterContextBuilderRequest

type CharacterContextBuilderRequest = {
  schema_version: "0.1"
  event: RuntimeEvent<"USER_MESSAGE">
  call_type: "user_message_visible_reply"
  allow_state_patch: boolean
  allow_incident_start: boolean
}

The request may be represented as function parameters if that matches the current Python style. It must normalize and validate the same RuntimeEvent contract as the existing Role Model Loop context builder.

CharacterContextSources

type CharacterContextSources = {
  recent_visible_messages_source?: RecentVisibleMessagesSource
  current_state_source?: CurrentCharacterStateSource
  active_incident_source?: ActiveIncidentSource
}

These are injected read-only sources. The builder must pass copy-safe request objects to each source and must treat missing sources exactly as the current implementation does.

DecisionContext

type DecisionContext = {
  schema_version: "0.1"
  trace_id: string
  event_id: string
  call_type: "user_message_visible_reply"
  event: {
    type: "USER_MESSAGE"
    text: string
    created_at: string
    user_id?: string
    conversation_id?: string
  }
  character_snapshot: {
    recent_visible_messages: RecentVisibleMessage[]
    living_state_brief?: LivingStateBrief
    active_incident?: ActiveIncidentBrief
  }
  allowed_actions: string[]
}

MVP-015 must preserve this current shape. The only intended change is where the context is built, not what the model sees.

Functional Requirements

ID Requirement
FR-1 Add a Character State Engine context-builder boundary for the current USER_MESSAGE role-model call.
FR-2 The boundary must return byte-for-byte equivalent data values for existing successful DecisionContext cases: no sources, recent visible messages, living-state brief, active-incident brief, and combined source inputs.
FR-3 Move recent visible message request construction, source-response validation, current-event exclusion, duplicate identity checks, timestamp ordering, candidate limits, selected-message limits, and text-token budget selection behind the Character State Engine boundary without changing their constants or outcomes. The implementation must move, extract, or compatibility re-export and reuse the current role_model.loop surface by name: RECENT_VISIBLE_MESSAGES_MAX_CANDIDATES, RECENT_VISIBLE_MESSAGES_MAX_MESSAGES, RECENT_VISIBLE_MESSAGES_MAX_TEXT_TOKENS, _read_recent_visible_messages(), _build_recent_visible_messages_request(), _validate_recent_visible_messages_request(), _validate_recent_visible_message(), _is_current_event_message(), _parse_recent_message_timestamp_before_event(), _reject_duplicate_recent_message_identity(), _select_recent_visible_messages(), and approximate_text_tokens() as needed instead of reimplementing parallel logic.
FR-4 Move living-state source orchestration behind the boundary while reusing build_current_character_state_request(), build_living_state_brief(), and validate_living_state_brief_for_event().
FR-5 Move active-incident source orchestration behind the boundary while reusing build_active_incident_request(), build_active_incident_brief(), and validate_active_incident_brief_for_event().
FR-6 Role Model Loop must delegate context construction to the new boundary and keep rendering, adapter calls, parse behavior, returned RoleModelTurnResult, and raw log entry shapes unchanged.
FR-7 Existing context-build failures must still surface as RoleModelValidationError to Role Model Loop and be logged as role_model_turn_failed with stage = "context_build" and code = "malformed_context".
FR-8 The boundary must preserve current opt-in behavior: allow_state_patch requires a current-state source, and allow_state_patch plus allow_incident_start remains rejected before model rendering.
FR-9 The builder must pass deep-copy-safe request objects to sources and return context data that cannot be mutated by later source or caller mutations.
FR-10 The user-turn orchestrator must continue to pass the same visible conversation, current-state, and active-incident sources into the model-call path without changing commit order or visible output behavior.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Prefer moving existing tested helper logic over duplicating it under a new module.
  • Keep the public surface narrow: one context-builder entry point plus source protocols or compatibility exports needed by current callers.
  • Keep code future-compatible by naming the boundary clearly, but do not add unused retrieval, budget, store, or multi-event abstractions.
  • Preserve existing test determinism, fake sources, fake adapter calls, fake clocks, and fake IDs.
  • Keep Role Model Loop focused on model input rendering, adapter invocation, output parsing, and role-model logging.

Implementation Boundaries

  • character.state owns source orchestration and compact context assembly for this slice.
  • character.state.current continues to own living-state and active-incident read request, snapshot, and brief validation helpers.
  • The recent visible message source protocol, visible conversation adapter, and current recent-message helpers/constants in role_model.loop must move behind the Character State Engine boundary, be extracted into a shared module, or be compatibility-exported from the new boundary. Do not create duplicate validators, selectors, request builders, budget constants, timestamp checks, current-event filters, or duplicate-identity checks.
  • role_model.loop remains responsible for render_role_model_input(), parse_character_decision(), adapter invocation, and role_model_turn_completed/role_model_turn_failed log construction.
  • runtime.user_turn remains responsible for orchestration order and source injection; it should not learn source-specific context rules.
  • Commit and Effects modules remain untouched unless a test import must follow a moved compatibility symbol.

Review Notes

  • This is a boundary extraction slice, not a new runtime behavior slice.
  • The highest risk is accidentally changing the model-facing context while moving helper ownership. Tests should compare values, not only types.
  • Do not add a generic context framework with empty hooks for body state, directives, retrieval, active threads, or future private calls.
  • Review fix: recent-message reuse is explicit because AGENTS.md requires reusing existing logic and creating shared helpers only for a real shared boundary. MVP-015 is that boundary; it should move or extract the existing helper bodies rather than copy them into character.state.
  • Keep failure ownership clear: Character State Engine may raise validation errors, but Role Model Loop still logs context-build failure because that is where the model call would have happened.
  • If a helper is still only used by the Role Model Loop compatibility wrapper after the move, keep it private or re-export narrowly; do not create a broad public API.
  • Implementation note: chose src/character/state/context.py as the smallest clear boundary. It owns the existing DecisionContext assembly, recent-message source request/selection logic, visible-conversation adapter, living-state source read, and active-incident source read.
  • Implementation note: role_model.loop.build_decision_context() remains as a compatibility shim that delegates to build_character_decision_context() and converts Character State Engine validation failures to RoleModelValidationError so existing failure logs keep stage = "context_build".
  • Implementation note: the current DecisionContext shape, role-model input rendering, parser behavior, user-turn ordering, and raw log shapes were preserved; no retrieval, context-build log, storage, body-state, directive, private-call, or lifecycle behavior was added.
