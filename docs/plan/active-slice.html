MVP-003 - Runtime Event Trace For Local Chat

Status: accepted active slice

Created: 2026-06-04. Active spec: docs/plan/active-slice.html. Previous slice archived at docs/plan/completed/mvp-002-local-character-conversation-core.html. Suggested implementation branch: feature/mvp-003-runtime-event-trace-local-chat.

Source Context

Product direction comes from the Notion project hub Live Character Framework, especially 01 - Framework Overview, 02 - Runtime Architecture, and 08 - Runtime Logging & Trace.

Long-term direction: every trigger becomes a RuntimeEvent, the runtime handles it through one path, visible conversation output is recorded, and raw logs preserve what actually happened.

Local rebuild direction comes from AGENTS.md and AGENTS.repo.md. This slice must grow from the current working local chat path. It should not restore the old runtime framework before the product needs it.

Current Product Before This Slice

MVP-002 gives the repo a local character chat session. The chat CLI reads one terminal line, sends that string directly to the conversation core, receives a deterministic Mira reply, and prints the reply. The conversation core keeps an in-memory visible transcript for the session. 

terminal input
  -> chat CLI reads one line
  -> conversation core validates the message
  -> deterministic local character agent makes a reply
  -> conversation core stores user message + character reply in memory
  -> chat CLI prints the reply

This is enough to chat locally, but it is not yet a runtime-shaped product. There is no runtime event object, event ID, trace ID, raw event log, conversation log API, or structured record of what happened inside a turn.

Product After This Slice

Normal chat output should stay the same by default. The internal path changes so each user input becomes a small USER_MESSAGE runtime event and the runtime records a trace for that event while reusing the existing conversation core. 

terminal input
  -> chat CLI reads one line
  -> create USER_MESSAGE RuntimeEvent
  -> local runtime turn adapter handles the event
  -> runtime trace records what is happening
  -> conversation core validates and replies
  -> conversation log records visible messages
  -> raw event log records internal truth
  -> chat CLI prints the reply

The character does not need to become smarter in this slice. The important product change is inspectability: the app can chat, and the runtime can explain each local turn.

Goal

Introduce the first narrow runtime event and trace layer around local chat. One local user message should have a stable event identity, a trace identity, ordered trace entries, visible conversation log records, raw event log records, and the same visible chat behavior the user already has.

Current Scope

  • One runtime event type: USER_MESSAGE.
  • Separate event_id and trace_id values for each processed local user input.
  • Deterministic ID and clock injection for tests.
  • An in-memory runtime log store for this local session only.
  • A visible ConversationLog API that records user-visible messages committed during runtime handling.
  • A RawEventLog / RuntimeTrace API that records runtime internals, validation success or rejection, and final outcome.
  • A local runtime turn adapter that accepts a USER_MESSAGE event and reuses runCharacterTurn().
  • Chat CLI routing through the local runtime adapter instead of calling the conversation core directly.
  • Optional diagnostic trace mode for local chat, proposed as JSON Lines written to stderr so normal chat stdout stays stable.
  • Compatibility with the existing MVP-001 relay command and the existing default MVP-002 chat behavior unless this draft is explicitly revised.

Explicit Non-Goals

  • No live model provider call, API key, provider config, prompt template, or model selection.
  • No Twilio, WhatsApp, webhook, HTTP server, browser UI, or external provider edge.
  • No durable persistence, database, file-backed log, replay UI, or migration from old runtime data.
  • No memory, retrieval, tools, scheduler, Live2D, assets, plugin system, or background worker.
  • No full Runtime Kernel, Character State Engine, Role Model Loop, Commit and Effects Engine, or old runtime module restoration from legacy/typescript.
  • No multi-character support, account system, authentication, or cross-session continuity.
  • No change to Mira's deterministic local reply behavior unless required by a test-only seam.

Finished Slice

Before MVP-003 After MVP-003
The chat CLI sends raw text directly to the conversation core. The chat CLI creates a USER_MESSAGE event and sends it to a local runtime turn adapter.
A successful turn only updates the in-memory visible transcript. A successful turn updates the visible transcript, conversation log, raw event log, and runtime trace.
A failed turn prints an error but has no structured internal record. A failed turn records a trace and raw rejection without committing fake visible messages.
There is no stable ID for one input or its processing chain. Each processed input has an event_id for the trigger and a trace_id for the processing chain.
Debugging means reading tests or stepping through code. Trace mode can show the ordered runtime steps for a local turn.

Functional Requirements

ID Requirement
FR-1 The product defines a minimal USER_MESSAGE runtime event contract with event ID, trace ID, type, creation time, and normalized payload.
FR-2 Runtime event construction validates local chat input before runtime handling proceeds.
FR-3 The runtime turn adapter handles one USER_MESSAGE event by calling the existing conversation core, not by duplicating transcript or reply logic.
FR-4 A successful runtime turn records ordered trace entries from event receipt through visible reply commit.
FR-5 A successful runtime turn appends user and character messages to the conversation log with source event and trace IDs.
FR-6 Failed input validation and failed reply validation append raw rejection records and leave visible conversation records unchanged for the failed turn.
FR-7 The default chat CLI remains user-facing chat output first; trace details appear only when trace mode is enabled.
FR-8 Trace mode emits one machine-readable JSON Line per processed user input to stderr, including event ID, trace ID, status, and ordered trace step names.
FR-9 The existing relay command remains available as the MVP-001 smoke path.

Acceptance Criteria

ID Criterion
AC-1 A test can construct a deterministic USER_MESSAGE event with predictable event ID, trace ID, timestamp, and payload.
AC-2 A successful runtime turn returns the same visible reply behavior as MVP-002 while recording trace, raw log, and conversation log entries.
AC-3 The runtime adapter proves it reused runCharacterTurn() by preserving session transcript behavior and recent visible context behavior.
AC-4 Invalid user input is rejected before a character reply is produced and leaves the conversation log unchanged for that input.
AC-5 Invalid character replies are recorded as rejected runtime outcomes and leave visible logs unchanged for the failed turn.
AC-6 Default pnpm chat output remains compatible with MVP-002 tests unless a reviewed compatibility note changes it.
AC-7 pnpm chat -- --trace emits JSONL trace summaries on stderr without changing normal chat stdout.
AC-8 The MVP-001 pnpm relay smoke path still passes.
AC-9 pnpm lint, pnpm typecheck, pnpm test, strict unused-symbol TypeScript, and whitespace checks pass.

Parallel Child Tasks

This draft is intentionally shaped for five week-sized subthreads. The main thread should freeze the shared event/log interfaces before production work starts, then coordinate the child tasks through the repository's parallel-agent protocol.

  • CT-01 - Runtime Event Contract
  • CT-02 - Trace And Log Store
  • CT-03 - Local Runtime Turn Adapter
  • CT-04 - Chat CLI Trace Mode
  • CT-05 - Integration Review, Tests, And Docs

Implementation Boundaries

  • The runtime event contract owns event identity, trace identity, event type, timestamp, and payload validation.
  • The trace/log store owns append-only in-memory log records and immutable read snapshots.
  • The local runtime turn adapter owns the route from USER_MESSAGE event to existing conversation core result.
  • The conversation core remains the owner of visible transcript mutation and deterministic character replies.
  • The chat CLI owns terminal input/output, exit handling, and optional trace-summary emission.
  • The relay command remains the compatibility smoke path and should not move into the runtime layer in this slice.

Test Plan

  • Unit tests for deterministic runtime event creation, validation, and ID/clock injection.
  • Unit tests for append-only trace, raw log, and conversation log behavior with immutable snapshots.
  • Integration tests for successful local runtime turns that record trace and visible conversation output.
  • Integration tests for invalid user input and invalid agent reply rejection paths.
  • CLI boundary tests for default chat compatibility, trace mode JSONL on stderr, exit behavior, and error behavior.
  • Regression tests proving the MVP-001 relay command still satisfies its existing contract.

Review Decisions Requested

  • Trace mode format: this draft proposes JSON Lines on stderr, not extra human text in normal chat output.
  • Storage: this draft proposes in-memory logs only, with no file or database persistence.
  • Runtime scope: this draft proposes one local USER_MESSAGE event path only, not a full Runtime Kernel.
  • Compatibility: this draft proposes preserving default chat and relay output exactly unless implementation evidence forces a reviewed change.

Future Pressure

Once local chat has runtime-shaped events and traces, later slices can add durable log storage, replay, provider events, model-call snapshots, memory retrieval, scheduled events, or a broader Runtime Kernel. Those later slices should build on this event/log seam instead of introducing parallel paths.
