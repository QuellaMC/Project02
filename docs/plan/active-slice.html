Context Provider Sections

Status: active implementation slice

Created: 2026-05-31. Active branch: feature/context-provider-sections.

Source Context

Product direction remains the Notion project hub Live Character Framework, especially 01 - Framework Overview and 06 - Character State Engine and Retrieval Management. The Notion source says the Character State Engine builds compact DecisionContext and that retrieval results should arrive as selected context, not as raw store contents.

Local trigger: issue 2 from the architecture-risk list. The current DecisionContext exposes one fixed character_snapshot object with recent visible messages, living-state, active incident, interrupted incident, and an interruption flag. Future context producers would either have to add more character-specific fields or create parallel plumbing.

Goal

Add the smallest context-provider boundary that lets future systems attach named model-facing context sections without rewriting buildCharacterDecisionContext for every new source type. Preserve existing character_snapshot behavior and current rendered model input when no extra provider is configured.

Current Scope

  • Add an optional top-level context_sections envelope to DecisionContext.
  • Add a DecisionContextSectionProvider option that receives a deterministic request for the current user-message event.
  • Validate, clone, and include provider sections outside character_snapshot.
  • Forward provider options through the Role Model Loop while preserving existing source options.
  • Test success, malformed provider output, direct context validation, and rendered role-model input compatibility.

Explicit Non-Goals

  • No memory system, retrieval planner, vector database, keyword search, or source expansion.
  • No new model actions, tool calls, persistence stores, schedulers, or side effects.
  • No changes to existing character_snapshot fields or semantics.
  • No context-budget ranking beyond existing recent-visible-message selection.
  • No broad Role Model Loop prompt or instruction redesign.

Minimal Schema

Runtime schema stays schema_version: "0.1". The new optional context section shape is:

  • schema_version: current schema version.
  • section_id: non-empty provider-stable identifier, unique within one context.
  • section_type: non-empty provider-owned type label.
  • content: object payload already compacted for the model.
  • source_event_ids: event IDs that justify the section; empty is allowed for sections not derived from event records yet.

Provider request shape is deterministic and event-scoped: schema_version, trace_id, event_id, event_type, created_at, and optional conversation_id.

Acceptance Criteria

  • Default buildCharacterDecisionContext output remains byte-shape compatible with existing tests.
  • A configured provider can add a named section without changing character_snapshot.
  • Malformed provider sections are rejected with contract validation errors.
  • Direct DecisionContext validation accepts normalized sections and rejects malformed or duplicate sections.
  • Role Model Loop forwards provider sections into rendered input and still rejects malformed decision contexts.
  • No live model provider or external service is called.
  • Future retrieval and memory work is parked, not implemented.

Implementation Boundaries

  • Character State Engine: owns provider request construction, section validation, and final DecisionContext assembly.
  • Role Model Loop: forwards provider configuration and validates rendered contexts before adapter calls and log snapshots.
  • Runtime User Turn: only touched if an existing orchestration option must pass the provider through.
  • Commit and Effects Engine: unchanged.

Review Notes

  • This is a compatibility schema extension, not a replacement of character_snapshot.
  • context_sections should be omitted when empty so existing rendered input remains stable.
  • Provider payloads are generic only at the boundary; they still need schema version, identity, and object payload validation.
  • Future providers must own their own compact payload contract before being wired in.

Open Questions

  • Should future retrieval sections standardize source_refs beyond source_event_ids?
  • Should later context-budget policy rank or trim cross-provider sections?

Future Ideas

  • Implement retrieved-context sections backed by a retrieval planner and exact source expansion.
  • Add context-build raw log entries once replay/debug needs source-request traces.
  • Add section budgeting after at least two real context providers exist.
