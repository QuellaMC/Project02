MVP-013 - Raw Event Log Query/Replay Visibility for Committed Success Logs

Status: implemented locally; PR #15 open

Created: 2026-05-19. Active slice path: docs/plan/active-slice.html. Runtime language: Python 3. Test runner: Python standard library unittest. Branch: feature/mvp-013-raw-log-replay-visibility. Pull request: PR #15.

Source Context

Product direction comes from the Notion project hub Live Character Framework. The source pages checked for this slice are 08 - Runtime Logging & Trace, 02 - Runtime Architecture, and 09 - MVP Roadmap & Open Questions.

Raw Event Log is the lossless truth. MVP-013 proves that committed success logs exposed through atomic finalizers are visible through the same Raw Event Log query/debug surface as ordinary appended logs.

Local implementation truth comes from completed MVP-001, MVP-002, MVP-003, MVP-005, MVP-007, MVP-009, MVP-010, and MVP-012.

Goal

Add the smallest read/query visibility surface needed to prove that successful atomic finalizer logs are not hidden second logs. A trace query must return ordinary appended RawEventLogEntry records and finalizer-exposed success entries together, using the same read/debug path and the same entry shape.

Current Scope

  • One new read-side boundary is in scope: a minimal Raw Event Log query/debug surface for existing RawEventLogEntry records.
  • One query use case is in scope: fetch records for a single trace, with optional event ID and kind filters.
  • Two atomic success kinds are in scope: living_state_patch_committed from MVP-010 and life_incident_started from MVP-012.
  • Ordinary appended logs remain in scope, including runtime intake, user visible projection, role-model turn, visible reply commit, and rejection logs.
  • The implementation may use an in-memory fake/debug store so tests can prove visibility without choosing concrete persistence.
  • Finalizers still own atomic exposure of their already-built success log entries; MVP-013 only proves those entries are readable through the Raw Event Log surface afterward.

Explicit Non-Goals

  • No concrete database, migration, filesystem store, repository, external service, background worker, scheduler, or production persistence adapter.
  • No replay executor, rollback, reconciliation job, idempotency policy, retry policy, state versioning, or durable transaction design.
  • No debug inspector UI, HTTP endpoint, CLI command, pagination, full-text search, retrieval index, embedding, compaction, or model-facing memory tool.
  • No new RuntimeEvent type, model action, decision parser behavior, prompt behavior, context field, living-state field, incident lifecycle action, body state, tool, Live2D, or asset behavior.
  • No change to Commit and Effects ownership: Commit and Effects still validates and builds success log entries; finalizers still expose already-built committed artifacts atomically.
  • No change to failure semantics: finalizer rejection or malformed finalizer output still produces ordinary rejection logs and no durable success visibility.

Minimal Schema

RawEventLogQuery

type RawEventLogQuery = {
  trace_id: string
  event_id?: string
  kinds?: string[]
}

RawEventLogQueryResult

type RawEventLogQueryResult = {
  schema_version: "0.1"
  trace_id: string
  entries: RawEventLogEntry[]
}

RawEventLogEntry

MVP-013 must reuse the existing entry shape from runtime.logging: schema_version, log_id, trace_id, event_id, kind, created_at, and data. Do not add a persisted visibility_source, finalizer, or replay field to prove this slice.

Functional Requirements

ID Requirement
FR-1 Querying by trace_id returns ordinary appended RawEventLogEntry records from the existing append path.
FR-2 Querying by the same trace_id after a successful living-state patch turn returns the living_state_patch_committed entry exposed through the MVP-010 atomic finalizer in the same result list as ordinary appended logs.
FR-3 Querying by the same trace_id after a successful incident-start turn returns the life_incident_started entry exposed through the MVP-012 atomic finalizer in the same result list as ordinary appended logs.
FR-4 Query filters for event_id and kind must apply identically to ordinary appended entries and finalizer-exposed success entries.
FR-5 Returned entries are deep copies. Mutating a query result must not change stored append-path entries or finalizer-exposed success entries.
FR-6 Query result order is deterministic and follows the runtime visibility order for the turn, so a finalizer-exposed success entry appears before the assistant visible reply commit when the finalizer runs before that commit.
FR-7 A finalizer-exposed success entry must appear exactly once in query results. The implementation must not return both a private finalizer list entry and a separate appended duplicate.
FR-8 Finalizer rejection and malformed finalizer result paths must not expose a success entry through query results; their existing ordinary rejection logs remain queryable.
FR-9 The query/debug surface validates query inputs and rejects unsupported filter shapes without mutating log state.

Non-Functional Requirements

  • Use only Python standard library behavior; do not add dependencies.
  • Keep the implementation small enough for an in-memory fake/debug store and focused helper functions.
  • Reuse RawEventLogEntry and SCHEMA_VERSION from runtime.logging; do not create a parallel persisted log record type.
  • Keep success entry construction in existing Commit and Effects modules. MVP-013 must not move validation, snapshot construction, or committed-log construction into the read surface.
  • Keep finalizer protocols narrow. If a helper is needed for test fakes, it should expose already-built success log entries to the same underlying queryable store without teaching finalizers to rebuild log entries.
  • Keep tests deterministic with fake IDs and clocks.

Acceptance Criteria

  • Existing MVP-001 through MVP-012 behavior continues to pass.
  • A trace query over ordinary append-path logs returns intake, projection, role-model, visible-reply, and rejection entries as applicable.
  • A state-patch-enabled user turn exposes living_state_patch_committed through the same trace query result as ordinary appended logs.
  • An incident-start-enabled user turn exposes life_incident_started through the same trace query result as ordinary appended logs.
  • Filtering by kind can select an atomic success entry or an ordinary appended entry through the same query function.
  • Finalizer failure paths show rejection logs but no committed success entry.
  • Query results are copy-safe and duplicate-free.
  • No concrete storage, replay executor, debug UI, new event type, new model action, or broad framework module is added.
  • The development journal records source context, files touched, checks run, review notes, and next action.
  • Future ideas discovered during planning are recorded in future-slices.html.

Test Plan

Unit Tests

  • Query a fake/debug Raw Event Log store by trace_id and assert ordinary appended entries are returned as deep copies.
  • Query with event_id and kind filters and assert the same filtering path applies to append-path and finalizer-exposed entries.
  • Record an already-built living_state_patch_committed success entry through the atomic visibility helper and assert query results include it exactly once.
  • Record an already-built life_incident_started success entry through the atomic visibility helper and assert query results include it exactly once.
  • Reject malformed query filters without altering stored entries.

Integration Tests

  • Run a default user turn against the queryable fake/debug store and assert ordinary logs are visible through the query surface.
  • Run a living-state patch success turn and assert the trace query includes living_state_patch_committed between the role-model turn log and assistant visible reply commit.
  • Run an incident-start success turn and assert the trace query includes life_incident_started between the role-model turn log and assistant visible reply commit.
  • Run living-state and incident finalizer rejection paths and assert the relevant rejection log is queryable while the success kind is absent.
  • Run full unittest discovery.

Implementation Boundaries

  • runtime.logging may own the minimal query/read helper or in-memory debug store because it already owns RawEventLogEntry construction primitives.
  • Runtime Kernel remains unchanged except for using the same append protocol it already uses.
  • Role Model Loop remains unchanged except for tests proving its ordinary logs are visible through the query surface.
  • Commit and Effects remains the owner of committed success log entry construction for living-state patches and incident starts.
  • Atomic finalizer fakes may expose committed success entries to the same queryable log store, but they must not rebuild or reinterpret those entries.
  • The query/debug helper must not make a finalizer success entry queryable until the caller has validated the finalizer result.
  • User-turn orchestration ordering remains unchanged.

Review Notes

  • MVP-013 is a visibility proof, not a persistence slice.
  • The risk being closed is specific: MVP-010 and MVP-012 success logs bypass ordinary raw_event_log.append(), so a later debug/replay surface could miss them if the finalizer keeps them in a private list.
  • The right proof is a shared read surface over the same RawEventLogEntry shape, not a second copy of committed success logs.
  • Review fix: test/debug finalizer visibility is staged first, then confirmed only after finalizer-result validation, so malformed finalizer output cannot leave both success and rejection visible.
  • Review fix: atomic finalizer success kinds are rejected on the ordinary append path before confirmation, and visibility-store failures raised inside finalizers become ordinary rejection logs.
  • If implementation pressure suggests storage engines, replay execution, reconciliation, or UI, park those as future slices.

Open Questions

  • Should the eventual concrete store expose the same query API directly or through an adapter over a database table? Not in MVP-013.
  • Should query results eventually support pagination, time ranges, redaction, or source expansion? Not in MVP-013.
  • Should replay use query order or an explicit sequence number? MVP-013 should only define enough deterministic order for current in-memory tests.

Future Ideas Discovered During Planning

  • Debug inspector UI for traces, decisions, commits, and rejected outputs.
  • Replay executor that rebuilds a turn from raw logs plus state/context/model snapshots.
  • Pagination, redaction, retention, and permission filtering for debug views.
  • Unified query support for future tool, asset, directive, and maintenance logs.
