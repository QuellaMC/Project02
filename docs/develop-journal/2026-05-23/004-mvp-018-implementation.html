2026-05-23 - MVP-018 Implementation

Implemented MVP-018 - Minimal Complete Active Incident Commit Boundary v0.1 as an explicitly opted-in USER_MESSAGE life-action subtype.

What Changed

  • Added COMPLETE_INCIDENT_ACTION and normalize_complete_incident_life_action() to the shared runtime contract layer.
  • Extended the Role Model Loop write-action opt-in path with allow_incident_complete, complete-specific instructions, and the machine-readable allowed_life_action_type marker.
  • Added commit_effects.incident_complete for complete commit request construction, active-incident re-read validation, success and rejection raw-log entries, finalizer validation, and post-confirm failure handling.
  • Extended InMemoryLifeIncidentStore with complete finalization that stages life_incident_completed, confirms query visibility through the existing atomic helper path, and clears only the matching active incident scope after confirmation.
  • Extended runtime.user_turn so a caller can opt into exactly one of state patch, incident start, incident cancel, or incident complete, and so complete rejections stop before the assistant visible reply commit.
  • Added unit and integration tests for valid completion, malformed subtype parsing, no active incident, incident ID mismatch, raw-log mismatch, staging failure, confirm failure, source/finalizer exceptions, changed active incident after visibility confirmation, and scoped clearing.

Why It Was Needed

MVP-017 proved the cancel boundary and atomic success-log visibility rule. MVP-018 applies the same reviewed pattern to complete_incident without adding the later INCIDENT_COMPLETION runtime event, scheduler, body effects, Live2D, completed-incident context, persistence, queue, retrieval, or proactive-message behavior.

Review Notes

  • The role model still receives only one write-action opt-in per USER_MESSAGE turn. Complete cannot be composed with state patch, start, or cancel in this slice.
  • The successful life_incident_completed entry uses ATOMIC_FINALIZER_SUCCESS_KINDS, expose_committed_success_entry(), confirm_committed_success_entry_visibility(), and discard_committed_success_entry_visibility(); the ordinary append path is used only for rejections.
  • Post-confirm completion failures intentionally preserve the already query-visible life_incident_completed entry and append a later life_incident_complete_rejected audit entry.
  • No active incident is cleared before the success entry is staged and confirmed visible; scope mismatches, source errors, finalizer errors, malformed finalizer results, and stale incident IDs all reject without clearing the intended active incident.
