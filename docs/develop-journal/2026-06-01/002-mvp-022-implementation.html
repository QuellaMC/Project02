2026-06-01 - MVP-022 Runtime Component Registry Implementation

What Changed

  • Added the static RuntimeComponent registry with immutable derived views for operations, user-turn actions, model action specs, and context section providers.
  • Added RuntimeOperationRegistry and internal RuntimeAccess.execute with caller/event policy checks, input/output validators, privacy snapshots, transaction metadata, and operation audit logs.
  • Added built-in operation wrappers for visible conversation commits, role-model turns, recent-message reads, context builds, existing user-turn write actions, and incident.complete_from_event.
  • Refactored runUserMessageTurn so the current user-turn spine executes through registry-derived operations/actions/providers while preserving committed/stopped result shapes and domain log visibility.
  • Added runIncidentCompletionEvent so the deterministic INCIDENT_COMPLETION route executes incident.complete_from_event through RuntimeAccess without model calls or visible output.
  • Updated user-turn tests to assert domain log ordering separately from the new operation audit envelopes.
  • Applied review fixes so operation ownership must match the registering component, user-turn action operations are registered by their real owners, built-in output validators reject malformed statuses, recent-message/context-section reads go through registry-backed operations, and operation infrastructure failures return stopped user-turn results instead of throwing.
  • Hardened the component-system contracts after follow-up review: registry-owned component and operation definitions are frozen copies, permission/logging/transaction policies are validated as concrete contract values, and async handler results are explicitly rejected until a future queued/background executor slice exists.
  • Addressed post-commit audit safety: a completed-audit append failure after validated handler output now returns succeeded_with_audit_failure with the operation output instead of a retry-looking rejection, and malformed operation envelopes with event identity return structured request_validation rejections.

Why

MVP-022 creates one shared built-in operation path before memory, tools, scheduler, Live2D, or productivity systems are added. The runtime now has a concrete place to register future internal capabilities without adding more one-off branches to the user-turn orchestrator or bypassing Commit & Effects ownership.

Review Notes

  • The implementation keeps operation routing static, synchronous, in-process, and built in.
  • Domain commit/reject results remain owned by existing Commit & Effects functions; operation rejection is reserved for registry, policy, validation, or handler infrastructure failures.
  • Operation audit logs are additive. Existing domain raw logs remain query-visible and preserve the domain order used by replay/debug checks.
  • A completed-audit append failure can no longer make callers believe a committed visible/state/life operation failed safely before effects; the result distinguishes committed-output-with-audit-failure from ordinary rejection.
  • Final review targeted the main drift risks: no dual production path for registered reads/context/action specs, no component/operation ownership mismatch, no identity validator pretending to be an output contract, and no unhandled audit-log append failure.
  • The async/background concern is intentionally not implemented as queues in this slice. The implemented contract is explicit: all MVP-022 operations are sync_in_process; Promise-like handler output is rejected and queued execution is parked for a dedicated future slice.
  • No memory retrieval, memory writes, tools, scheduler, Live2D, dynamic plugins, storage adapter, or external side-effect policy was implemented.
