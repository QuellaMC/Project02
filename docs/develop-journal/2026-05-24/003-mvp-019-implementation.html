2026-05-24 - MVP-019 Implementation

Implemented MVP-019 - Minimal Incident Completion RuntimeEvent Boundary v0.1 as the first deterministic non-user-message runtime event path.

What Changed

  • Added a shared INCIDENT_COMPLETION event constant, normalized payload validator, kernel payload normalizer, and deterministic route with model_needed = false and next_step = "incident_completion_commit".
  • Extended ActiveIncidentRequest validation so active-incident reads support exactly USER_MESSAGE and INCIDENT_COMPLETION. Current-state reads remain user-message-only.
  • Added commit_life_incident_completion_event() to Commit & Effects. The boundary re-reads the active incident, rejects stale or mismatched events, builds the completed snapshot with the existing MVP-018 rules, stages and confirms the success raw log, then clears the active incident through the existing finalizer/store path.
  • Added event-specific success and rejection log builders that carry completion_source = "incident_completion_event" and do not fabricate role-model result, character decision, or life-action data.
  • Updated InMemoryLifeIncidentStore completion finalization to return the validated source event type, so the same store can finalize either the MVP-018 user-message path or the MVP-019 event path.
  • Added unit and integration tests for kernel intake, active-incident request reuse, event completion success, structured rejection, post-confirm clearing failure, copy safety, and no-model/no-visible-output behavior.

Why It Was Needed

Notion defines incident completion as a runtime trigger, but the local implementation first needed MVP-018's user-message completion commit path and atomic life_incident_completed raw-log visibility. MVP-019 connects the next narrow boundary without adding scheduler generation, model aftermath, body effects, Live2D, proactive output, follow-up incidents, or completed-history storage.
