2026-05-20 - MVP-014 Implementation

What Changed

  • Added src/character/state/incidents.py with InMemoryLifeIncidentStore.
  • The store implements the existing MVP-012 finalize_life_incident_start() finalizer contract.
  • The same store implements the MVP-011 read_active_incident(request) contract and validates ActiveIncidentRequest.
  • Successful starts stage the already-built life_incident_started entry through InMemoryRawEventLog.expose_committed_success_entry() before storing the active incident for the validated scope.
  • Updated the store from one global active-incident slot to scoped in-memory storage keyed by validated request identity.
  • Added an explicit reserved IncidentScope(mode="single_user_self_use") for self-use mode when both user_id and conversation_id are absent.
  • Added targeted unit tests for successful finalize/read behavior, copy safety, raw-log staging failure, direct finalizer staging failure, same-scope second-start rejection, different-scope starts, isolated reads, default self-use scope behavior, and malformed raw-log entry validation.
  • Added an integration test that runs a USER_MESSAGE turn with the concrete store adapter and verifies the active incident plus query-visible success log.
  • Opened PR #16 and updated the active plan plus implementation graph with the PR reference.

Why It Changed

MVP-014 is the first concrete LifeIncidentStore step after MVP-012 proved the incident-start finalizer contract and MVP-013 proved finalizer success logs are visible through the shared Raw Event Log query surface. This keeps the active slice narrow while removing the test-only recording fake from the successful incident-start path used by new tests.

Review Notes

  • No new RuntimeEvent type, lifecycle action, database adapter, queue, interruption policy, Role Model Loop behavior, or default active-incident source wiring was added.
  • The Commit and Effects Engine still builds and validates the started incident snapshot and committed success log entry before the store finalizes anything.
  • The store stages raw-log success visibility before storing the active incident for a scope, so raw-log staging failure leaves no active incident.
  • Second starts fail closed only for the same incident scope and do not overwrite the stored active incident.
  • Different identified user_id / conversation_id scopes can hold separate active incidents, and reads are isolated by matching scope.
  • Returned active incidents and Raw Event Log query results are copy-safe.
  • Residual risk: the store is scoped object-lifetime in-memory storage with a single-user self-use default scope. It is multi-user-shaped but still not production multi-user persistence with auth, locks, migrations, or process-restart durability.
