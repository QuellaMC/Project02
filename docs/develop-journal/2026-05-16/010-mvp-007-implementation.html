MVP-007 Implementation

Date: 2026-05-16

What Changed

  • Added intake_runtime_event() in src/runtime/kernel.py so RuntimeKernel.handle_event() and the user-turn orchestrator share the same normalize, raw-log append, and route path.
  • Updated the USER_MESSAGE route from the old MVP-001 model_needed = false / logged_only route to model_needed = true / next_step = "user_turn".
  • Added src/runtime/user_turn.py with run_user_message_turn(), a thin orchestrator over existing Runtime Kernel, Commit and Effects, MVP-006 recent visible source, and Role Model Loop boundaries.
  • Returned a copied user_turn_committed result envelope with the nested kernel route, user visible projection result, role-model result, assistant visible reply result, and committed visible record IDs.
  • Returned user_turn_stopped envelopes when user visible projection or assistant visible reply commit returns a rejected result, without adding rollback, reconciliation, or fallback text.
  • Updated old runtime route tests so they deliberately assert the new MVP-007 route semantics instead of the MVP-001 logged-only behavior.
  • Added integration coverage for one full user turn, shared kernel/orchestrator route semantics, malformed input, malformed model output, raw log order, visible append order, current-message exclusion, and result copy isolation.
  • PR review fix: changed recent-message duplicate validation so a completed prior user turn can contribute both the user visible message and assistant visible reply with the same source_event_id.
  • PR review fix: added a second-turn orchestrator regression test proving completed prior turns flow into recent_visible_messages without duplicating the current user message.
  • Updated docs/plan/active-slice.html and docs/plan/index.html from spec-only to implemented-and-tested-local status.

Why

MVP-001 through MVP-006 proved the individual boundaries. MVP-007 proves that one USER_MESSAGE turn can pass through the existing intake, visible user projection, recent visible context, fake-backed Role Model Loop, assistant visible reply commit, and raw logging path without adding storage, state, retrieval, tools, provider integration, or broader route policy.

Review Notes

  • The orchestrator is intentionally only an ordering and result-envelope layer; it does not duplicate event, decision, visible record, or raw log validation.
  • Commit and Effects remains the only boundary that appends visible user and assistant records.
  • Role Model Loop remains the only boundary that renders model input, calls the fake adapter, parses model output, and logs role-model success or failure.
  • Runtime Kernel route policy changed only for the implemented USER_MESSAGE event type.
  • The current user message is projected to the visible conversation before the model call, but the MVP-004/MVP-006 current-event exclusion still keeps it out of recent_visible_messages.
  • Completed prior turns intentionally include one user and one assistant record with the same source event. The duplicate guard now rejects duplicate message_id values and duplicate source_event_id / role pairs, not all repeated source events.
  • No concrete storage, live provider, Character State Engine package, retrieval, tool, Live2D, scheduler, transaction, rollback, or reconciliation behavior was added.
