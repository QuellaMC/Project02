MVP-006 Implementation

Date: 2026-05-16

What Changed

  • Implemented VisibleConversationRecentMessagesSource in src/role_model/loop.py.
  • Added a read-only VisibleConversationRecordSource protocol that accepts a copied visible-record request and returns committed visible conversation records.
  • Mapped user_visible_message records into the existing RecentVisibleMessage shape with role = "user".
  • Mapped assistant_visible_reply records into the existing RecentVisibleMessage shape with output_id as message_id and role = "assistant".
  • Validated request fields, record kinds, schema version, source metadata, required identity fields, conversation match, timestamps, non-empty text, and extra keys before model input rendering.
  • Reused the existing Role Model Loop recent-message validator after mapping, so ordering, current-event exclusion, duplicate detection, and budget selection remain in the existing context path.
  • Added focused unit tests for mapping, malformed requests, malformed records, non-list source output, implementation-only field stripping, and copy isolation.
  • Added an integration test proving mapped visible records flow through run_role_model_turn() into the rendered model input and completed raw log snapshot.
  • Updated docs/plan/active-slice.html and docs/plan/index.html from spec-only to implemented-and-tested status.

Why

MVP-004 already defined the read-side recent-message context contract, and MVP-005 added committed user visible records. MVP-006 connects committed user and assistant visible records to the existing context source without adding concrete storage, a user-turn orchestrator, retrieval, character state, or new write behavior.

Review Notes

  • The adapter is read-only and has no append, update, delete, transaction, persistence, file, network, clock, ID, or model-provider behavior.
  • Unsupported committed visible record kinds fail closed rather than being skipped.
  • Committed-record implementation fields such as kind, source, user_id, and output_id are not exposed in DecisionContext.
  • The implementation stays colocated with the existing recent-message validator instead of importing private helpers across modules.
  • The existing Role Model Loop continues to decide final ordering, duplicate handling, current-event exclusion, and message budget.
  • Scope did not expand into concrete ConversationLog storage, context-build raw logging, retrieval, Character State Engine extraction, or full user-turn orchestration.
