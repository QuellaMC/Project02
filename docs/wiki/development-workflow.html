Development Workflow

This workflow applies to every implementation pass in this repository. It keeps the code modular, reviewable, and compatible with future slices.

Sequence

  1. Select one small roadmap slice from the Notion source.
  2. Create a new short-lived branch from the current mainline before editing the functional spec or code. Use feature/, fix/, docs/, or chore/ as defined in the AGENTS.md Branch and Merge Policy.
  3. Check local docs and source for existing logic that can be reused.
  4. Write or update the HTML functional spec in docs/plan.
  5. Peer review the spec before code: contract, risks, tests, boundaries, and reuse.
  6. Write minimal unit tests for pure functions and minimal integration tests for boundary behavior.
  7. Run tests and confirm they fail for the intended reason when possible.
  8. Implement the smallest production code that satisfies the tests.
  9. Run the relevant tests again.
  10. Review the written code for unused code, duplicate logic, security issues, efficiency issues, and gotchas.
  11. Update the date-scoped journal with files touched, decisions, tests, and next slice.
  12. Commit the completed spec, code, tests, and journal changes.
  13. Open a pull request and treat the CI/CD workflow as the merge gate.

Pull Request Gate

Every new functional spec or coding pass should finish as a pull request. The pull request is ready for review only after lint/readability checks, source compilation, unit tests, integration tests, and full test discovery pass in the GitHub CI/CD workflow.

Fix CI/CD failures on the branch. Do not bypass lint failures or merge a branch whose workflow failed.

Pre-Code Review Checklist

  • Does the slice map to one clearly named behavior?
  • Is the expected input, output, and failure behavior written down?
  • Can existing logic be reused or extended without rewriting?
  • Is a shared helper justified now, or should it wait?
  • Are security and persistence boundaries explicit?
  • Are the tests minimal but sufficient for the contract?

Post-Code Review Checklist

  • No unused public API, unused files, or placeholder modules.
  • No duplicate validation, parsing, persistence, or logging paths.
  • Errors are explicit enough for debugging and safe enough for users.
  • Tests cover the behavior that was implemented, not a broader imagined system.
  • Docs and journal reflect the actual code, not the original intent if it changed.
