Architecture and Maintainability Audit

Status: implementation-scoped audit

Reviewed: 2026-07-11. Implementation branch: fix/plugin-activation-policy.

Source references describe the pre-refactor main baseline at 7c5673340271fa3ec4c7e10f5dab01f2f7bef5ba; branch line numbers shift as the bounded corrections remove obsolete paths.

Executive summary

The architecture is generally coherent around one user-turn runtime, one plugin host, and explicit runtime commit and storage boundaries. The main risk is not a missing framework; it is that policy, activation, inspection, and durable evidence each have a second path that can disagree with the intended owner.

The highest-impact issues are a direct plugin-host dispatch path that can bypass the same confirmation and side-effect eligibility used for model-facing discovery, an inspect path that constructs plugins and invokes a synthetic session-end lifecycle, and a file-log read path that returns terminal trace entries that were never persisted. Default plugin activation also relies on parallel factory shapes, repeated ID lists, and factory-instance identity.

This PR intentionally implements only three corrections: enforce the existing dispatch gate inside RuntimePluginHost, make default/catalog activation manifest-backed and independent of factory object identity or WeakSet-style instance tracking, and make inspect a pure read path that does not construct or close plugins. Historical inspect labeling, durable evidence provenance, and storage module splitting remain sequenced follow-ups.

Architecture and execution-flow overview

The primary paths are:

chat input
  -> config load and activation
  -> plugin construction and RuntimePluginHost
  -> role-model loop
  -> host tool dispatch
  -> runtime validation and commit
  -> trace, raw-event, conversation, and plugin evidence

inspect request
  -> config load and activation projection
  -> session and durable evidence reads
  -> JSON output

The user-turn runtime is the useful convergence point. Divergence appears before it in config and plugin composition, inside direct host dispatch, and after it in inspection and durable evidence projection. The corrections below reuse those existing boundaries rather than add a runtime kernel or another registry.

Findings

High: direct plugin-host dispatch can bypass model-facing tool eligibility

Responsibility: confirmation and side-effect eligibility for plugin tools. src/plugins/tool-policy.ts lines 192-203 define the accepted model-facing subset: the tool must be plugin-host validated, require no confirmation, and have only an allowed side-effect level. The direct dispatch path in src/plugins/hook-runner.ts lines 628-745 locates a plugin and declared tool, checks access, validates input, and calls the hook. Before this PR, it did not require the tool to remain in the shared routable set.

This is a policy bypass rather than cosmetic duplication: a caller with a RuntimePluginHost could directly invoke a confirmation-required or externally side-effecting tool that discovery and the role-model route correctly withheld. The likely cause was treating discovery filtering and execution authorization as separate concerns.

  • Smallest correction: reuse the existing routability predicate inside host dispatch and return the existing rejected tool-call/evidence shape.
  • Behavior to preserve: identity checks, access grants, input validation, timeouts, evidence redaction, and valid local-memory-write tools.
  • Compatibility decision: no compatibility shim for direct calls that policy already classifies as ineligible; they should now fail closed.

High: inspect constructs plugins and invokes synthetic session-end hooks

Responsibility: read-only inspection. In src/cli/inspect.ts lines 541-588, inspect can call configured host construction, which runs plugin factories. Lines 607-624 then invoke onSessionEnd with a synthetic USER_MESSAGE context solely to clean up those constructed plugins. File-store writes are disabled, but constructors, provider setup, close hooks, and other lifecycle behavior still run during a nominal read.

This makes inspect an execution entry point and forces it to own lifecycle cleanup. A new plugin can therefore make inspect slower, unavailable, or externally observable even when all required output already exists in manifests, activation diagnostics, and stored evidence.

  • Smallest correction: resolve inspect output from manifest-backed activation metadata without calling factory create, building a host, or invoking lifecycle hooks.
  • Behavior to preserve: config validation, secret redaction, activation reasons, granted access, session listing, and stored turn evidence.
  • Compatibility decision: because runtime config is unreleased, remove manifest-less function factories and the parallel enabledPlugins input; use plugins.<id>.enabled exclusively, with defaultMemoryProvider limited to selecting an already-active provider.

High: public file-log reads synthesize terminal trace entries that are not durable

Responsibility: truthful durable evidence. In src/runtime/storage/file-runtime-log-store.ts lines 123-177, reconcileTerminalRawTraceEvidence derives raw_event_log_appended and terminal trace steps from a terminal raw event. Public reads return those entries without writing them to trace.jsonl. The direct tests deliberately verify both the synthesized return value and the unchanged file.

Recovery from a terminal raw-event commit is valid, but the current API does not distinguish stored trace evidence from a derived projection. Read-only inspection can therefore report a trace step that the audit file does not contain, while the surrounding cross-file validators otherwise claim disagreement is corruption.

  • Smallest correction: return one coherent session-evidence result that separates stored entries, derived recovery state, and diagnostics; stop silently adding derived entries to the ordinary stored trace view.
  • Behavior to preserve: non-mutating reads, recovery when a terminal raw event is durable, and fail-closed conversation/raw-event consistency.
  • Compatibility decision: retain schema-1 decoding through an explicit versioned path; do not apply legacy conversion implicitly to every current-schema read.
  • PR scope: deferred; the dispatch and inspect fixes do not change storage format or recovery behavior.

Medium-high: default activation is represented by parallel factory and identity mechanisms

Responsibility: the built-in plugin catalog and default-enabled policy. src/plugins/catalog.ts lines 29-53 define a catalog factory type plus separate first-party, host-scoped, and default-enabled ID arrays. src/runtime/config/activation.ts lines 113-148 convert that type into another factory definition, then determine defaults by comparing factory objects. Lines 856-863 repeat reference identity to recognize canonical host-scoped defaults. A fresh registry returned by the public catalog therefore loses policy even though it carries the same catalog-defined entries. Bare injected wrappers are intentionally not host-owned and should remain opt-in through config.

Adding or changing one built-in can require edits to the catalog definitions, multiple ID lists, activation conversion, and identity checks. Object identity is an unstable source of product policy and makes equivalent factories behave differently.

  • Smallest correction: use one manifest-backed catalog definition with explicit ownership and construction scope, and canonicalize all host-owned entries before their manifest defaults or factories are consumed.
  • Behavior to preserve: explicit config disable wins, bare injected factories remain supported but opt-in, unknown IDs remain diagnosable, and configured plugins construct only after activation succeeds.
  • Compatibility decision: require manifest-backed factories, remove the unreleased enabledPlugins compatibility route, keep defaultMemoryProvider selection-only, and replace reference identity with catalog-shaped composition whose host-owned entries are always replaced by canonical definitions before activation or construction.

Medium: historical inspect combines current config with persisted activation evidence

Responsibility: historical truth. src/runtime/log.ts lines 204-253 persist a per-turn plugin registry, enabled state, access grants, health, and any declared manifest fingerprint, but not the effective runtime-config fingerprint or activation reasons. However, src/cli/inspect.ts lines 479-520 and 541 onward also resolve and display the current runtime config and current activation when inspecting an old session. After config changes, the output can present current activation beside an old turn without a clear temporal label.

  • Smallest correction: label current config/activation explicitly and use the persisted turn snapshot as the owner of historical plugin state.
  • Behavior to preserve: current config diagnostics remain useful for operators, while old turn evidence remains readable without re-running plugins.
  • Compatibility decision: change labels and projection ownership without changing the persisted turn-evidence format.
  • PR scope: deferred until pure inspect construction is established.

Medium: the storage layout module also owns all persisted record codecs

Responsibility: filesystem layout versus stored record validation. src/runtime/storage/layout.ts lines 1-94 import conversation, role-model, and plugin constructors and validators. Lines 301-350 contain the actual root, session, and plugin path layout. From line 412 onward, the same file encodes, decodes, normalizes, and semantically validates every trace, raw-event, conversation, provider, role-model, and plugin evidence shape.

  • Smallest correction: keep path names and ID normalization in layout.ts; move storage errors/schema metadata and runtime record codecs into focused storage modules.
  • Behavior to preserve: one central path owner, exact error codes, strict persisted-evidence validation, and schema-1 compatibility.
  • Compatibility decision: update imports mechanically without changing file names, record formats, schema markers, or readable versions.
  • PR scope: deferred as a mechanical, behavior-neutral follow-up.

Resolved: relay's parallel composition path is removed

Responsibility: CLI dependency composition. src/cli/relay.ts created an in-memory session and log store directly, while chat loaded config, resolved activation, constructed a configured host, and prepared durable runtime dependencies. Both converged on runLocalUserMessageEvent, so core runtime behavior was shared, but relay did not exercise configured plugins, provider selection, or durable storage.

This audit deferred to repository policy, which retained relay as the narrow MVP smoke and compatibility path. That reading no longer holds. The audit's own question was what relay stayed compatible with, and the answer had become only itself: nothing outside the repository ran it, and a smoke path that skips configured plugins, provider selection, and durable storage stops being evidence about the composition operators actually run.

Resolution: relay is deleted and chat is the one user-turn entry point. What relay was reached for — a small, deterministic composition to test through — is served by the runtime seams chat itself composes, so that coverage survives without a second command to keep in step. AGENTS.repo.md sections 3, 4, and 7 were amended so the policy this finding deferred to no longer reads as requiring it.

Minimal target architecture

  • One manifest-backed plugin catalog owns factory, ownership metadata, construction scope, and default-enabled metadata; host-owned composition is canonicalized before use.
  • One pure activation resolver turns config plus catalog metadata into activation snapshots and diagnostics.
  • Plugin construction happens only after successful activation and only on execution paths that need live plugins.
  • RuntimePluginHost is the final authorization boundary and reuses the shared routability policy before every plugin hook dispatch.
  • Inspect reads config metadata and stored evidence without constructing plugins or invoking lifecycle hooks.
  • Historical inspect uses persisted turn activation as historical truth and labels current operator config separately.
  • Durable evidence reads distinguish stored records from derived recovery state.
  • Storage path layout remains centralized while record codecs move to focused storage-owned files.

This target uses current boundaries. It does not add a component registry, dependency injection framework, runtime kernel, migration framework, or second plugin host.

Refactoring sequence

  1. In this PR, enforce the shared routability gate in direct host dispatch, replace object/WeakSet-style default-factory recognition with canonical host catalog composition plus manifest-backed activation metadata, and make inspect resolve activation without constructing or closing plugins. Add focused regression tests for each route.
  2. Label current config and persisted per-turn activation separately in inspect. Keep the current activation diagnostics, but never present them as the historical state of an old turn.
  3. Add a coherent durable session-evidence read shape with stored-versus-derived provenance. Update public trace consumers, then remove unmarked public-read synthesis.
  4. Split src/runtime/storage/layout.ts mechanically into path layout, storage contract, and persisted record codec ownership without changing formats or validators.
  5. Reassess relay only after repository policy removes its smoke/compatibility role. Done: the policy was amended and relay was removed rather than reassessed in place.

Rejected or uncertain concerns

  • visible_reply remains a terminal built-in model tool. Routing it through plugin-host dispatch would blur the commit boundary and is not a cleanup.
  • Provider adapters are justified external boundaries. Their request/response mapping should remain separate from role-model policy and runtime commit.
  • Cross-file trace, raw-event, and conversation validators remain necessary under the current three-file storage layout. Do not delete them as a shortcut.
  • Schema-1 storage reads remain an explicitly tested persistence contract. The unreleased runtime-config enabledPlugins route is not retained; all configuration and tests use plugins.<id>.enabled, while defaultMemoryProvider only chooses among active providers.
  • src/plugins/adapter-proofs/ contains test and compatibility proof mapping, not a second production plugin runtime.
  • Splitting the large user-turn runtime orchestration is deferred. No independent duplicate runtime route was proven, and a broad runtime framework would exceed the evidence in this audit.
