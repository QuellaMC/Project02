Project02 Config System

Project02 owns one small, versioned JSON config document. It separates host settings from plugin settings, while sharing one loader, schema, redaction, inspection, and mutation path across the CLI, console UI, runtime activation, and model-facing tools. The config engine stays under src/runtime/config; model-facing plugin operations are adapters over that shared boundary rather than a second config system.

The model may inspect safe config and propose one permitted plugin-field change. The host validates it, the user approves it, and the locked runtime mutation service commits it.

Canonical authored document

{
  "version": "project02.config.v2",
  "project02": {
    "storeRoot": ".project02-runtime",
    "defaultMemoryProvider": "memory.example",
    "roleModelProvider": "local"
  },
  "plugins": {
    "memory.example": {
      "enabled": true,
      "config": {
        "endpoint": "https://memory.example.test",
        "apiKey": { "$env": "MEMORY_EXAMPLE_API_KEY" }
      }
    }
  }
}

One schema and three representations

  • Authored: the operator-owned JSON document. Defaults are not written into it automatically.
  • Resolved: validated values, defaults, environment references, sources, and diagnostics used by the host.
  • Redacted: the only representation available to normal inspect output, the console, and model tools.

Project02 fields come from the host field registry. Plugin fields come from RuntimePluginManifest.config.fields. That manifest metadata is the single source for value types, allowed values, secret handling, reload requirements, console rendering, and whether an ordinary non-secret field is agent-mutable. A secret field is never agent-mutable.

Location and precedence

  1. An explicit --config path.
  2. An explicit --store root and its config.json.
  3. PROJECT02_RUNTIME_CONFIG.
  4. The default .project02-runtime/config.json.

For role-model selection, an explicit CLI flag wins over the runtime environment, which wins over project02.roleModelProvider. Environment variables remain useful deployment overrides; the config document is the durable operator choice.

Safe mutation boundary

  1. Read and strictly validate the current authored document.
  2. Validate an exact structured operation; model writes cannot submit dotted paths or whole-document patches.
  3. For model writes, require an installed manifest, a declared non-secret field, and agentMutable: true.
  4. Compare the caller's authored fingerprint while holding the cross-process mutation lock.
  5. Revalidate the new document and the target plugin's complete manifest schema while still holding the lock, then atomically replace it with mode 0600.
  6. Return the new fingerprint; never return resolved secret values.

Secret values continue through the dedicated environment-backed secret command. They are not accepted in console fields or model tool inputs. Plugin enablement, host settings, permissions, and plugin installation are also outside the model-write boundary.

Operator surfaces

  • pnpm runtime-config -- check validates authored config, resolution, and activation.
  • pnpm runtime-config -- get <path> reads a redacted value.
  • pnpm runtime-config -- ui opens the schema-driven terminal editor.
  • Existing scriptable set, unset, plugin activation, memory-provider, and secret commands remain compatible.

The terminal editor stages one change, shows a redacted old/new preview, and requires Save or Cancel. Saving is bound to the fingerprint observed before the preview, so a concurrent edit fails instead of silently overwriting it.

Plugin entries are grouped by their existing catalog construction metadata. Entries with construction: "factory", plus factories without catalog metadata, appear under Plugins. Entries with construction: "host_scoped" appear under System services. The groups share one continuous numeric selection list, preserve stable plugin-ID ordering within each group, and omit empty headings. The default catalog therefore shows character-state as a plugin and first_party.model_tools plus runtime.plugin as system services.

Runtime plugin management

One host-owned plugin, runtime.plugin, owns the model-facing plugin-management surface. Its handlers remain focused internally, but callers see one coherent runtime capability instead of separate discovery and config plugins.

  • runtime.plugin.list with scope: "all" includes cold disabled or blocked plugins without constructing their code or exposing their tools.
  • runtime.plugin.config returns one installed plugin's manifest field metadata, redacted authored/effective values, exact host activation state and reasons, diagnostics, and authored fingerprint.
  • runtime.plugin.config.update proposes one exact set or unset operation for one agent-mutable field.

Provider adapters use the corresponding wire-safe names runtime_plugin_list, runtime_plugin_config, and runtime_plugin_config_update.

Listing is always available when runtime.plugin is active and remains independent from config validity. If activation has config errors, the host retains only an immutable inventory snapshot, so blocked plugins remain discoverable while config inspection and update stay unavailable. Config inspection is added when valid config-control state exists; the update tool is added only when the configured host also has a confirmation handler. The host validates the proposal before prompting, shows a redacted exact preview, and accepts only a one-shot user approval within the existing five-second deadline. Missing, denied, cancelled, timed-out, or stale approval fails closed. The plugin manifest declares the maximum runtime_config_write capability, while list and config inspection retain their per-tool runtime_read classification and only config update requires confirmation. Changes affect subsequent plugin construction; this slice does not hot-reload plugins.

Disabling runtime.plugin removes all three model-facing management tools together, while the operator console remains available as the recovery path. The separate first_party.model_tools system service is unchanged because its terminal tools use different routing and commit semantics.

Unified plugin packages

Ordinary plugins use one package contract whether they ship with Project02 or are installed by an operator. Project02 scans bundled packages and <storeRoot>/plugins into one immutable catalog before activation. Cold discovery reads only package metadata; it does not import disabled plugin code. 

<plugin-id>/
  package.json              # must declare { "type": "module" }
  project02.plugin.json     # format, relative entry, cold manifest
  index.ts | index.js | index.mjs
{
  "format": "project02.plugin.v1",
  "entry": "./index.ts",
  "manifest": {
    "...": "existing RuntimePluginManifest"
  }
}
export async function createProject02Plugin(input) {
  return {
    manifest: input.manifest,
    providedTools: [],
    lifecycleHooks: {}
  };
}

Every entry has exactly one runtime export, the named createProject02Plugin(input) factory, and returns a normal runtime plugin. The input contains pluginId, the validated manifest, effective storeRoot, resolvedConfig, and redactedConfig. The host validates the returned plugin and requires exact manifest parity before registration. Node loads all three supported extensions as ESM; TypeScript entries are limited to Node 24's erasable syntax and are not compiled or type-checked by Project02. TypeScript plugin imports must include explicit file extensions and use import type for type-only dependencies. See also Node's package and module rules.

CommonJS, .cjs, .cts, .tsx, extensionless entries, URLs, metadata or entry symlinks, and entries outside the package directory are rejected. Adding, removing, or changing a package is observed by the next Project02 process; active processes do not hot-reload plugin code.

Installing an operator package

  1. Copy the complete package folder to <storeRoot>/plugins/<plugin-id>.
  2. Run pnpm runtime-config --store <storeRoot> check to validate its cold descriptor and config schema without executing the entry.
  3. Enable it with pnpm runtime-config --store <storeRoot> plugin enable <plugin-id>, or use pnpm runtime-config --store <storeRoot> ui.
  4. Restart the Project02 command so the enabled package is imported once during host construction.

Package provenance is host-owned rather than manifest-owned. Bundled Character State is the reference ordinary package and retains its first-party default. Operator packages remain disabled until explicitly enabled and cannot gain bundled trust or default activation by copying manifest fields. Enabled packages execute trusted Node code in the Project02 process; plugin permissions constrain host services and model exposure, not direct Node capabilities.

Compatibility and future import

project02.runtime_config.v1 remains readable. It is normalized to v2 in memory with a warning, and the next successful mutation writes the canonical v2 document. Legacy CLI paths remain aliases while project02.* is canonical.

Runtime plugin management uses an explicit pre-release clean break: the former discovery and config plugin IDs and their short tool names have no aliases or migration adapter. The only supported plugin ID is runtime.plugin, with the three exact tool names documented above. This naming break does not change the authored config-document migration described here.

A future OpenClaw importer should be an adapter into this document and the existing Project02 manifest contract. It may translate stable IDs, config schema and UI hints, activation defaults, tool declarations, compatibility metadata, and supported migrations. It must not make OpenClaw's internal config shape Project02's storage model, and imported code remains disabled until installation, access, and activation are approved.

Research influences

  • Hermes, inspected locally from explore_repo/hermes-agent at 6cb88a0: a compact terminal Save/Cancel flow and a useful distinction between authored and effective config; Project02 keeps its stronger cross-process lock and manifest schema.
  • OpenClaw, inspected locally from explore_repo/openclaw at 501f634: cold manifest inspection, schema-driven forms, authored/runtime separation, and fingerprint-bound writes; Project02 adds explicit per-call approval.
  • Codex config loader: clear source precedence and centralized loading.
  • Codex typed config: a strict typed boundary rather than independent ad hoc readers.
  • Codex plugin config edits: targeted atomic edits that preserve unrelated state.
  • Codex app-server config API: shared read/write primitives and approval-aware clients.

Explicit non-goals for v2

  • No plugin marketplace, package-manager installation, dependency resolution, remote loading, signing, or sandbox claim.
  • No JSON5 includes, profiles, raw-document model editing, or custom plugin UI code.
  • No agent mutation of secrets, activation, permissions, Project02 host settings, or config location.
  • No hot reload, filesystem watcher, or OpenClaw importer implementation in this slice.
