Project02 Config System

A Project02 home holds one versioned global JSON document plus one optional overlay per character. Every setting — the host's and each plugin's — is authorable in both unless its scope keeps it to one, and a character's value wins over the home's. One loader, schema, redaction, inspection, and target-aware mutation path serves the daemon's config verbs, runtime activation, and the model-facing tools. The config engine lives under src/runtime/config; model-facing plugin operations are adapters over that boundary, never a second config system.

The model may inspect safe config and propose one permitted plugin-field change. The host validates it, the person approves it, and the locked runtime mutation service commits it.

The host fields are declared once, in the field registry, in the order the settings page renders them: what a person decides first, then the knobs, then the switch. Each field carries its description, value type, allowed values, default value, and whether it is a secret. Every other setting belongs to a declared section, kept under a namespace of the document — plugins today — at <namespace>.<id>, its fields at <namespace>.<id>.config.<field>. Every section is declared the same way, and a plugin manifest is such a declaration as it stands. Plugin fields come from RuntimePluginManifest.config.fields, which is likewise the single source for value types, allowed values, default values, secret handling, reload requirements, and whether an ordinary non-secret field is agent-mutable. A secret field is never agent-mutable. The resolver applies a field's declared default value wherever no permitted layer authored the field, and the settings page shows it as the field's effective value.

One schema and three representations

  • Authored: the operator-owned global document and a character's overlay. Manifest defaults are not copied into either.
  • Resolved: validated values, defaults, sources, and diagnostics used by the host.
  • Redacted: the only representation available to inspect output, the config view, and model tools.

The home and layered precedence

A run selects its home with --store <dir>, or takes the default .project02; the global document is that home's config.json, and nothing else selects it. The home is bound to its physical directory at start, so a link that later points elsewhere cannot move a running daemon. A character's overlay lives at <home>/character-data/<id>/config.json. Effective values resolve in this order: 

character overlay > global config > defaults

Installed characters are enabled unless project02.enabled says otherwise — it layers like every other host field, so a global false switches them all off and a character's overlay value overrides it. A character switched off keeps its settings readable, and the same field switches it back on. An absent character field keeps inheriting future global changes; global values are never copied into the overlay. On first selection, the character package contributes only its plugin declarations and non-secret defaults. On a package-version change, Project02 adds currently missing package fields and never changes or removes existing character values.

Secrets

A secret — a plugin field declared secret: true, or the host's nvidiaApiKey — is a plain string in whichever document authored it, kept at mode 0600 like the rest of that document; a blank is refused, since removing a credential is the unset operation. Every read redacts it: a view says only that it is set. Authored fingerprints hash a secret's presence, never its value, so the fingerprint a page holds cannot leak it. A character's own secret overrides the home's, so two characters can hold different accounts for one plugin. Only an operator writes a secret, through the daemon's config verb; the model never reads one back and never proposes one.

Plugin config scopes

Every plugin manifest declares config.scope for its switch and fields, and a field may declare its own to narrow it: in a global_with_character_overrides plugin a field may be character_only or global_only, and a field that would widen its plugin's scope is rejected. One shared rule applies a scope to raw config loading, the daemon's config verbs, package defaults, approved model writes, and the merge, which takes each value only from a layer its scope permits:

PolicyHome configCharacter package or overlay
global_with_character_overridesThe home's value, and each character's unless that character sets its own.The character's value, overriding the home's.
character_onlyNothing: the home's view leaves it out, and a home write naming it is refused.The character's value.
global_onlyThe value for the home and for every character.Nothing: a character's view leaves it out, and a character write naming it is refused.

A value found where its scope forbids it never takes effect: it is reported as the warning runtime_config_authored_outside_scope at its path, and blocks nothing. Secret fields follow their scope like any other setting. character-state is character-only: it belongs wholly to the character that runs it.

Safe mutation boundary

  1. Read and strictly validate the current authored document.
  2. Validate an exact structured operation; model writes cannot submit dotted paths or whole-document patches.
  3. For model writes, require an installed manifest, a declared non-secret field, and agentMutable: true.
  4. Compare the caller's authored fingerprint while holding the cross-process mutation lock.
  5. Revalidate the new document and the target plugin's complete manifest schema while still holding the lock, then atomically replace it with mode 0600.
  6. Return the new fingerprint; never return resolved secret values.

Plugin enablement, host settings, secrets, permissions, and plugin installation are outside the model-write boundary.

Operator surfaces

The daemon is the config owner. GET /api/config renders a scope's settings from the declared fields — the home's, or one character's — and POST /api/config writes one change through the one control transaction, bound to the fingerprint the view handed out, and applies it to the running character by a reload between turns (Gateway API). The web page's settings screen is the operator's surface over those verbs: one screen for the home and for each character, every row the field shape the view carries, one field per save. A fresh home opens on it, framed as setup, until a provider is chosen. A hand edit made while the daemon runs is reflected on the next read and applied at the next change from the page or the next start; nothing watches the file.

A character's first valid write, like its first start, creates its data directory and overlay. pnpm inspect reports a home's config, activation, and sessions without writing anything.

Runtime plugin management

One host-owned plugin, runtime.plugin, owns the model-facing plugin-management surface. Its handlers remain focused internally, but callers see one coherent runtime capability instead of separate discovery and config plugins.

  • runtime.plugin.list with scope: "all" includes cold disabled or blocked plugins without constructing their code or exposing their tools.
  • runtime.plugin.config returns one installed plugin's manifest field metadata, redacted authored/effective values, exact host activation state and reasons, diagnostics, and authored fingerprint.
  • runtime.plugin.config.update applies one exact set or unset operation to one agent-mutable field once the person approves it.

Provider adapters use the corresponding wire-safe names runtime_plugin_list, runtime_plugin_config, and runtime_plugin_config_update.

Listing is always available when runtime.plugin is active and remains independent from config validity. If activation has config errors, the host retains only an immutable inventory snapshot, so blocked plugins remain discoverable while config inspection and update stay unavailable. Config inspection is added when valid config-control state exists; the update tool is added only when the configured host also has a confirmation handler. The host validates the proposal before prompting, shows a redacted exact preview, and accepts only a one-shot user approval within the existing five-minute deadline. Missing, denied, cancelled, timed-out, or stale approval fails closed. The plugin manifest declares the maximum runtime_config_write capability, while list and config inspection retain their per-tool runtime_read classification and only config update requires confirmation. An approved change is written at once, inside the tool call. A field declared reloadRequired: false takes effect right away: the host rebuilds the plugin from the freshly authored config and swaps the instance before the tool answers. Any other field takes effect at the next launch, and so does a live field of a plugin that already took a restart-only change in this process, since rebuilding it would apply that change early. The tool result tells the model which happened as appliesTo.

Disabling runtime.plugin removes all three model-facing management tools together; the daemon's config verbs remain the recovery path. visible_reply is not a plugin tool: it is how the character speaks, built into the role model and always offered, so no configuration can take it away.

Unified plugin packages

Ordinary plugins use one package contract whether they ship with Project02 or are installed by an operator. Project02 scans bundled packages and <home>/plugins into one immutable catalog before activation. Cold discovery reads only package metadata; it does not import disabled plugin code. 

<plugin-id>/
  package.json              # must declare { "type": "module" }
  project02.plugin.json     # format, relative entry, cold manifest
  index.ts | index.js | index.mjs
{
  "format": "project02.plugin.v1",
  "entry": "./index.ts",
  "manifest": {
    "...": "existing RuntimePluginManifest"
  }
}
export async function createProject02Plugin(input) {
  return {
    manifest: input.manifest,
    providedTools: [],
    lifecycleHooks: {}
  };
}

Every entry has exactly one runtime export, the named createProject02Plugin(input) factory, and returns a normal runtime plugin. The input contains pluginId, the validated manifest, the character's storeRoot, resolvedConfig, and redactedConfig. The host validates the returned plugin and requires exact manifest parity before registration. Node loads all three supported extensions as ESM; TypeScript entries are limited to Node 24's erasable syntax and are not compiled or type-checked by Project02. TypeScript plugin imports must include explicit file extensions and use import type for type-only dependencies. See also Node's package and module rules.

CommonJS, .cjs, .cts, .tsx, extensionless entries, URLs, metadata or entry symlinks, and entries outside the package directory are rejected. Adding, removing, or changing a package is observed by the next Project02 process; active processes do not hot-reload plugin code.

Installing an operator package

  1. Copy the complete package folder to <home>/plugins/<plugin-id>.
  2. Run pnpm inspect --store <home> --sessions to validate its cold descriptor and config schema without executing the entry; a package the catalog cannot publish is reported there and in every config view.
  3. Enable it on the settings page — the home's, or one character's.
  4. Restart the daemon so the enabled package is imported once during host construction.

Package provenance is host-owned rather than manifest-owned. Bundled Character State is the reference ordinary package; the Mira package enables it in Mira's overlay rather than through a global manifest default. Operator packages remain disabled until explicitly enabled and cannot gain bundled trust or default activation by copying manifest fields. Enabled packages execute trusted Node code in the Project02 process; plugin permissions constrain host services and model exposure, not direct Node capabilities.

Pre-release compatibility and future import

Runtime config accepts only project02.config.v2. Project02 is private and untagged, so retired shapes have no readers: a document that still carries the former project02.storeRoot field, or a secret written as an environment reference, is refused as unknown, and the person edits it out.

Runtime plugin management uses an explicit pre-release clean break: the former discovery and config plugin IDs and their short tool names have no aliases or migration adapter. The only supported plugin ID is runtime.plugin, with the three exact tool names documented above. Both the runtime-plugin naming break and the config contract are pre-release clean breaks.

A future third-party plugin importer should be an adapter into this document and the existing Project02 manifest contract. It may translate stable IDs, config schema and UI hints, activation defaults, tool declarations, compatibility metadata, and supported migrations. It must not make the source tool's internal config shape Project02's storage model, and imported code remains disabled until installation, access, and activation are approved.

Design principles

  • One place for every setting, layered home under character, with a real distinction between authored and effective config, on top of Project02's cross-process lock and manifest schema.
  • Cold manifest inspection, declared fields rendered as they are, authored/runtime separation, and fingerprint-bound writes, with explicit per-call approval for the model.
  • Clear precedence and centralized loading.
  • A strict typed config boundary rather than independent ad hoc readers.
  • Targeted atomic edits that preserve unrelated state.

Explicit non-goals for v2

  • No plugin marketplace, package-manager installation, dependency resolution, remote loading, signing, or sandbox claim.
  • No JSON5 includes, profiles, raw-document model editing, or custom plugin UI code.
  • No agent mutation of secrets, activation, permissions, Project02 host settings, or config location.
  • No filesystem watcher, no OS keychain or encryption at rest behind the secret flag, and no third-party importer implementation in this slice.
