Project02 Gateway API

The daemon (pnpm serve) holds every character runtime behind one gateway and speaks HTTP plus server-sent events on a loopback port. Every surface — the web page, a messaging connector — is a client of this API and nothing else, so what one surface sends, every surface sees. The contract's types live in src/gateway/api/contract.ts; this page is the wire.

The model proposes; the daemon commits. A client submits a message and reads outcomes and events. It never holds a runtime, a store, or a lease.

Finding the daemon

serve binds 127.0.0.1 on port 4310, or a free port when that one is taken, prints Gateway listening on port <port>, brings the roster up, and only then prints the one address it has — the line a client reads, and the address a person opens: 

PROJECT02_GATEWAY=http://127.0.0.1:4310/#token=<token>

The token is minted per run and travels in the URL fragment, so it never reaches a server log or a referrer. Nothing that connects before that line is printed can find a half-started daemon. The same address, opened in a browser, is the web page: the daemon serves it from its root, and the page takes the token from the fragment.

The four wire rules

Rule What it means on the wire
Status codes describe the transport A domain outcome — a refused open, a rejected turn, a storage failure — is a 200 whose body says status first. A non-200 means the request itself did not get through, and the body is always the one envelope {"error": {"code", "message"}}.
The stream is a hint; the verbs are the truth Every stream opens with a ready frame that carries the daemon's snapshot — health and the confirmations still waiting — taken the instant the stream's listener was registered, so every later event moves on from exactly that state. A client installs the snapshot and reads on; what it wants of a conversation's history it reads as one page, deduplicated by message id. There are no event ids and no replay.
One way in Loopback only: the daemon binds 127.0.0.1. Authorization: Bearer <token>, compared in constant time. The Host hostname must be 127.0.0.1 or localhost; an Origin, when present, must be http:// plus that host. No CORS headers, no cookie, no query token. One events stream per tab.
Every submission has an identity clientMessageId is required on a turn. A repeat with the same (conversationId, clientMessageId) and the same content joins the turn in flight or returns the recent outcome; the same id with different content is refused; and an id the character already holds from an earlier run of the daemon, on any segment of the conversation, is refused as duplicate_submission. That is what lets a client whose answer was lost send the line again under the same id, at once or after the daemon came back, without saying it twice; history returns the id too, for a surface that wants to know whether a line landed.

Transport status codes

Status error.code When
400 invalid_request Unreadable or mis-shaped body, or malformed Authorization syntax.
401 unauthorized Missing or wrong token.
403 forbidden_origin A foreign Origin.
404 not_found Unknown route, including an unknown /api/*, which answers behind the same auth.
413 payload_too_large Body over 64 KiB.
421 misdirected_host A Host that is not loopback.

500 internal A bug. A storage failure is never a 500; it is an outcome.

Every /api/* response carries Cache-Control: no-store.

Routes

Verb Route Body → 200 body
health GET /api/health → GatewayHealth: protocol version, home root, config and package diagnostics, the roster with each character's state and last maintenance failure.
start POST /api/characters/:id/start → StartOutcome: settled with the character's summary (its state says ready or failed), or refused (unknown_character, gateway_stopped). The operator's retry; the daemon boots the roster itself.
open POST /api/conversations/open {characterId} → OpenOutcome: opened with the conversation and user participant ids, refused (unknown_character, character_unavailable, conversation_busy), or a storage failure.
turn POST /api/turns GatewayMessage → TurnOutcome. Blocks until the turn ends — a turn waiting on a confirmation can take minutes. A browser's fetch waits without limit; Node's gives a response five minutes. The reference client uses the platform's fetch, which is why the page is its caller today; a Node client that parks turns on confirmations needs a transport without that bound, and brings one when it arrives.
history GET /api/conversations/:id/messages?before=&limit= → HistoryOutcome: the newest page without a cursor, chronological within the page, with earlier when older messages remain. limit is 1..500 (default 100); before is the opaque cursor from a previous page.
pending GET /api/confirmations → PendingConfirmation[]: every tool confirmation still waiting, with its deadline.
answer POST /api/confirmations/:id {decision: "approved" | "denied"} → AnswerOutcome: answered, expired, or unknown.
config view GET /api/config?scope=global

A query naming no such target is a 400. Described below.

A turn

POST /api/turns
Authorization: Bearer <token>
Content-Type: application/json

{
  "conversationId": "conv_…",
  "senderId": "local-user",
  "text": "hello there",
  "source": "web",
  "clientMessageId": "8b1f…"
}

source is the client's stamp on the message — web, telegram:<bot> — naming the kind of surface a line came from, for rendering. It is never a permission input, and never what a surface tells its own lines by: every browser tab stamps web, so a line is its sender's by its clientMessageId alone. Both stamps match ^[A-Za-z0-9][A-Za-z0-9:._-]{0,63}$, are persisted on the user's commit record, and come back in history. A stamp that fails the pattern never reaches a turn: on the wire the body schema answers 400 invalid_request, and a caller holding the façade in-process gets a refused outcome (invalid_message) — the same rule, checked at whichever boundary the message crosses first.

The event stream

GET /api/events answers text/event-stream. Frames are event: <kind> plus one data: line of JSON; a comment : ping arrives every 15 seconds so an idle connection survives client timeouts. A client that does not take a frame within two seconds is dropped; the daemon never buffers for a client that is gone, and never judges one by how many frames a burst left waiting. 

event: ready
data: {"protocolVersion":2,"health":{…},"confirmations":[…]}

event: turn_progress
data: {"kind":"turn_progress","characterId":"mira","conversationId":"conv_…","progress":{"kind":"user_message",…}}

event: turn_progress
data: {"kind":"turn_progress","characterId":"mira","conversationId":"conv_…","progress":{"kind":"reply_delta","draftId":"1.0","text":"I remember "}}

event: turn_progress
data: {"kind":"turn_progress","characterId":"mira","conversationId":"conv_…","progress":{"kind":"reply_delta","draftId":"1.0","text":"you said "}}

event: turn_progress
data: {"kind":"turn_progress","characterId":"mira","conversationId":"conv_…","progress":{"kind":"visible_reply","messageId":"conv_….1:message-2",…,"draftId":"1.0"}}

event: turn_completed
data: {"kind":"turn_completed","characterId":"mira","conversationId":"conv_…","source":"web","clientMessageId":"8b1f…","status":"completed","committed":true}
Event Carries
ready The protocol version and the daemon's snapshot at that instant: health (the roster, each character's state and last maintenance failure) and confirmations still waiting. A client installs it on every one it sees.
turn_progress A turn's progress: both committed roles — user_message (with source and clientMessageId) and visible_reply — and the reply's draft ahead of its commit: reply_delta (one fragment of a draft, in order) and reply_withdrawn. A committed visible_reply names the draftId it replaces. Drafts are the one thing the stream says before the log, and they say so by their kind.
turn_completed The turn's terminal status, with the reason and message when it was not completed, stamped with the submission's source and clientMessageId so every surface knows whose turn ended — even one that committed nothing. committed says whether the turn put that line in the log: a surface holding the line hands back one that was not, and leaves one that was to the thread. Nothing else answers it, since the log is read in pages and a busy turn can put a hundred messages between a line and now.
confirmation_requested A tool asking for approval: id, request, deadline, and the turn that raised it (its conversationId, source, clientMessageId). A contact-shaped surface — a bot in one chat — answers for its own turns and leaves the rest to the surface that sent them; a roster-shaped surface, where the person sees every character, shows them all and names the surface that raised one. The person is the same on every surface, and the daemon settles a confirmation once for all of them. The same shape the pending list returns.
confirmation_settled The decision: approved, denied, or cancelled — and, cancelled, why: expired (the deadline passed, whether the daemon's timer fired or an answer came too late) or stopped (the character stopped or restarted with the request parked).
state_changed A character's runtime state, with a message when something went wrong. reloading is a pause, not an outage: the character is assembling afresh from the config on disk between turns, and a delivery sent meanwhile waits for it and lands on the same conversation.
maintenance_failed A segment rotation that failed after a completed turn; health shows the same at.

The sync rule

Every committed message rides the stream once it reached disk — the user's and the character's alike — and surfaces render from the stream. A turn's HTTP answer is for status only.

Because both roles are emitted from one post-persist seam, the stream and history never disagree: a reply whose write failed is a failed turn, never a message shown that history lacks. A message typed on the phone appears in every open browser tab at once. A surface tells the lines it is still holding apart by clientMessageId, which is its own: source names the kind of surface, and two browser tabs share it, so a tab that went by source alone would take another tab's lines for its own.

Streaming replies

The reply reaches every surface as the model writes it, as a draft: a draft is not a message, every draft ends exactly once, and the parser stays the only judge.

A reply_delta {draftId, text} is a fragment of the character's reply, appended to what came before under the same draftId. It has no message id, it is never persisted, and no surface treats it as history. The draft ends in one of two ways: the visible_reply that names its draftId replaces it with the committed message, or a reply_withdrawn {draftId} ends it with nothing said — a round the parser refused, a reply whose write failed. The daemon closes every draft a round opened before the round moves on, so none is open at turn_completed, and a client never infers an ending from another event.

On the stream A chat surface
reply_delta {draftId, text} Opens a bubble for the character keyed by conversationId and draftId on the first delta; appends text on every one.
visible_reply {…, draftId} Replaces the bubble keyed draftId with the message keyed messageId, text from the event. No open bubble with that id: shows the message, as always.
reply_withdrawn {draftId} Removes the bubble.
ready Drops every open draft: the snapshot carries none, the stream is a hint, and the truth is on the newest history page.

Draft ids are round.reply, unique within the turn; a conversation runs one turn at a time, so a surface keys drafts by conversation. The committed text is the draft after the runtime's normalization (line endings, trim), which is why the commit replaces the draft rather than confirming it. Only the reply is ever drafted: what a model writes to itself beside a tool call is never on the stream. Pacing is each surface's own: a page renders every delta, a connector edits its message on a timer.

What a client never has to notice

The daemon keeps the hard parts on its side, once, so every surface stays small. A character's automatic recovery after a fatal turn lets its threads go; a delivery on a conversation the runtime let go of holds it again before running, so a client keeps its conversation id through the episode. A reconnect gets its whole world in the ready frame. A confirmation names the turn that raised it. And a turn whose answer was lost is safe to send again under its id.

Config

The daemon owns config: every write goes through its one control transaction, and a change reaches a running character by a reload between that character's turns.

A view is what a settings page renders. Its project02 fields and each plugin's fields share one shape — what this scope authored, what is in effect and which layer put it there, whether this scope may author it, whether a change reloads the character. Defaults are not resolved in: an unauthored field reads effective.source: "missing" and its defaultValueSummary names what applies. The global scope resolves the home's document alone; a character's scope resolves the merged view with that character's own secrets. A document that does not load is refused with the diagnostic, never rendered as blank fields. The store root is not a field: it is the home the daemon runs in, and health names it.

A change names one operation — set or unset on project02.<field>, plugin_enabled, plugin_field_set, plugin_field_unset, plugin_secret_set — and carries the fingerprint the view handed out. The daemon verifies it under the file locks, so a concurrent edit from the console or another page is refused with conflict, never clobbered: the page re-reads and the person saves again. A secret is sent as its value; the daemon names its environment variable and writes the scope's env file, and the view shows only that the field is set. A write the daemon cannot make — a file another writer holds for longer than it will wait, an unwritable home — is failed with the reason.

applied means the bytes are on disk. What the change does to running characters arrives as state_changed: the daemon reconciles behind the answer, and a ready character whose assembly would now differ — its effective config, its plugin values including secrets, its package version — publishes reloading, finishes the turn in flight, assembles afresh, and publishes ready. A global change a character overrides costs it nothing. A reload that cannot assemble lands in failed with the diagnostic, and the next change or start retries it.

Storage failures are outcomes

A read-only store, a busy lease, a damaged segment: the daemon answers {"status": "failed", "code": <storage code>, "message"} with a 200. A non-technical user is told what broke and what to do next; a 500 is reserved for a bug.
