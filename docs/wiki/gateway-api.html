Project02 Gateway API

The daemon (pnpm serve) holds every character runtime behind one gateway and speaks HTTP plus server-sent events on a loopback port. Every surface — the web page, a messaging connector — is a client of this API and nothing else, so what one surface sends, every surface sees. The contract's types live in src/gateway/api/contract.ts; this page is the wire.

The model proposes; the daemon commits. A client submits a message and reads outcomes and events. It never holds a runtime, a store, or a lease.

Finding the daemon

serve claims its home — one daemon per home, held as a lease in the home's lock directory for the daemon's lifetime — binds 127.0.0.1 on the home's port, and prints the one address it has the moment the socket is bound: the line a client reads, and the address a person opens. The roster comes up on the stream after it, so a character can still be starting when the address is out. 

PROJECT02_GATEWAY=http://127.0.0.1:4310/#token=<token>

The same address is kept beside the config, in <home>/daemon.json at mode 0600, written by the daemon that holds the lease and by nothing else: 

{
  "protocolVersion": 6,
  "token": "…",
  "port": 4310,
  "running": {"pid": 12345, "startedAt": "2026-09-24T10:14:07.311Z"}
}

The token and the port belong to the home, not to the run: a restart answers on the same address, so an open tab reconnects on its own and a bookmark keeps working. The token travels in the URL fragment, so it never reaches a server log or a referrer; the same address, opened in a browser, is the web page, served from the daemon's root, and the page takes the token from the fragment. A first run takes port 4310, or a free one when that is taken, and records it. A later run whose recorded port another program has taken since takes a free one, says so on stdout before the address, and records the new one — open tabs and bookmarks then need the new address, which nothing can tell them. running is removed by a clean stop and left behind by a crash: a reader never trusts it without asking the address, and the lease, not the record, is what says a daemon is alive. A record that cannot be read is replaced, with a new token, and said on stderr.

A second serve on the same home does not start a second daemon. It reads the record and asks the address for /api/health: when the daemon answers as this home's, it prints Already running on this home (pid …) and the same address line, and exits 0 — which is also how anyone gets the address of a daemon that has been running since yesterday. A holder that does not answer — it answers 503 because it is stopping, its socket has already closed ahead of its lease, it has taken the lease but not yet bound its socket, or a crash's record names a port nobody listens on — is given up to thirty seconds: every half second the lease is tried and the address asked again, so a stop-then-start takes the home over on the same address and a start-twice hands the address back; when the wait is up, or the holder is on another machine, it says so and exits 1. Ctrl-C ends the wait at once.

Stopping

Ctrl-C, SIGTERM, or SIGHUP — a closed terminal — is a stop: the daemon prints Stopping; finishing what is in flight, requests the stop at once (a boot still under way is joined, and its late ready suppressed), finishes the turns it accepted, lets the streams and answers drain, closes the socket, then rewrites the record without running and releases the lease. A second signal of any kind ends the process at once; the lease left behind is the next start's to reclaim. On Windows, the console window's close is a SIGHUP followed by a kill about ten seconds later.

The four wire rules

Rule What it means on the wire
Status codes describe the transport A domain outcome — a refused open, a rejected turn, a storage failure — is a 200 whose body says status first. A non-200 means the request itself did not get through, and the body is always the one envelope {"error": {"code", "message"}}.
The stream is a hint; the verbs are the truth Every frame carries an id, and the daemon keeps a tail of the stream — up to a megabyte of frames — for a client that returns with Last-Event-ID: it opens with resumed and exactly the frames it missed, in order, then reads on. Any other stream — no id, an id from another run of the daemon, one before the tail — opens with a ready frame that carries the daemon's snapshot: health, the confirmations still waiting, and the turns running with their drafts so far, taken in one breath with the stream's registration, so every later frame moves on from exactly that state. A client installs the snapshot and reads on; what it wants of a conversation's history it reads as one page, deduplicated by message id. The log on disk stays the truth.
One way in Loopback only: the daemon binds 127.0.0.1. Authorization: Bearer <token>, compared in constant time. The Host hostname must be 127.0.0.1 or localhost; an Origin, when present, must be http:// plus that host. No CORS headers, no cookie, no query token. One events stream per tab.
Every submission has an identity clientMessageId is required on a turn. A repeat with the same (conversationId, clientMessageId) and the same content joins the turn in flight or returns the recent outcome; the same id with different content is refused; and an id the character already holds from an earlier run of the daemon, on any segment of the conversation, is refused as duplicate_submission. That is what lets a client whose answer was lost send the line again under the same id, at once or after the daemon came back, without saying it twice; history returns the id too, for a surface that wants to know whether a line landed.

Transport status codes

Status error.code When

401 unauthorized Missing or wrong token.

404 not_found Unknown route, including an unknown /api/*, which answers behind the same auth.

421 misdirected_host A Host that is not loopback.

Every /api/* response carries Cache-Control: no-store.

Routes

A turn

POST /api/turns
Authorization: Bearer <token>
Content-Type: application/json

{
  "conversationId": "conv_…",
  "senderId": "local-user",
  "text": "hello there",
  "source": "web",
  "clientMessageId": "8b1f…"
}

source is the client's stamp on the message — web, telegram:<bot> — naming the kind of surface a line came from, for rendering. It is never a permission input, and never what a surface tells its own lines by: every browser tab stamps web, so a line is its sender's by its clientMessageId alone. Both stamps match ^[A-Za-z0-9][A-Za-z0-9:._-]{0,63}$, are persisted on the user's commit record, and come back in history. A stamp that fails the pattern never reaches a turn: on the wire the body schema answers 400 invalid_request, and a caller holding the façade in-process gets a refused outcome (invalid_message) — the same rule, checked at whichever boundary the message crosses first.

The event stream

GET /api/events answers text/event-stream. Frames are id: <run>-<seq>, event: <kind> and one data: line of JSON — the id is a random id of this run of the daemon and a count from one; a comment : ping arrives every 15 seconds so an idle connection survives client timeouts. A client that does not take a frame within two seconds is dropped; the daemon never buffers for a client that is gone, and never judges one by how many frames a burst left waiting. A client that returns sends the id of the last frame it applied as Last-Event-ID; a resumed frame carries no id, so the id it holds stands.

Event Carries
ready The protocol version and the daemon's snapshot at that instant: health (the roster, each character's state and last maintenance failure), confirmations still waiting, and turns — each turn in progress, named by its submission's conversationId, source and clientMessageId, with its character and its open drafts' text so far. A client installs it on every one it sees.
resumed The first frame of a stream the daemon could catch up instead: nothing to install, and what follows is exactly what the client missed, in order, then the live stream.
turn_progress A turn's progress: both committed roles — user_message (with source and clientMessageId) and visible_reply — and the reply's draft ahead of its commit: reply_delta (one fragment of a draft, in order) and reply_withdrawn. A committed visible_reply names the draftId it replaces. Drafts are the one thing the stream says before the log, and they say so by their kind.
turn_completed The turn's terminal status, with the reason and message when it was not completed, stamped with the submission's source and clientMessageId so every surface knows whose turn ended — even one that committed nothing. committed says whether the turn put that line in the log: a surface holding the line hands back one that was not, and leaves one that was to the thread. Nothing else answers it, since the log is read in pages and a busy turn can put a hundred messages between a line and now.
confirmation_requested A tool asking for approval: id, request, deadline, and the turn that raised it (its conversationId, source, clientMessageId). A contact-shaped surface — a bot in one chat — answers for its own turns and leaves the rest to the surface that sent them; a roster-shaped surface, where the person sees every character, shows them all and names the surface that raised one. The person is the same on every surface, and the daemon settles a confirmation once for all of them. The same shape the pending list returns.
confirmation_settled The decision: approved, denied, or cancelled — and, cancelled, why: expired (the deadline passed, whether the daemon's timer fired or an answer came too late) or stopped (the character stopped or restarted with the request parked).
state_changed A character's runtime state, with a message when something went wrong. reloading is a pause, not an outage: the character is assembling afresh from the config on disk between turns, and a delivery sent meanwhile waits for it and lands on the same conversation.
health_changed The daemon's whole state, read again the moment a config change landed and before the pass that acts on it: the roster as config now says it and the config and package problems as they stand, the shape GET /api/health returns. Every surface hears it, not only the one that wrote, and one showing config reads its view again on it, so two windows on one screen stay in step; what the pass then does to each character follows as state_changed.
maintenance_failed A segment rotation that failed after a completed turn; health shows the same at.

The sync rule

Every committed message rides the stream once it reached disk — the user's and the character's alike — and surfaces render from the stream. A turn's HTTP answer is for status only.

Because both roles are emitted from one post-persist seam, the stream and history never disagree: a reply whose write failed is a failed turn, never a message shown that history lacks. A message typed on the phone appears in every open browser tab at once. A surface tells the lines it is still holding apart by clientMessageId, which is its own: source names the kind of surface, and two browser tabs share it, so a tab that went by source alone would take another tab's lines for its own.

Streaming replies

The reply reaches every surface as the model writes it, as a draft: a draft is not a message, every draft ends exactly once, and the parser stays the only judge.

A reply_delta {draftId, text} is a fragment of the character's reply, appended to what came before under the same draftId. It has no message id, it is never persisted, and no surface treats it as history. The draft ends in one of two ways: the visible_reply that names its draftId replaces it with the committed message, or a reply_withdrawn {draftId} ends it with nothing said — a round the parser refused, a reply whose write failed. The daemon closes every draft a round opened before the round moves on, so none is open at turn_completed, and a client never infers an ending from another event.

On the stream A chat surface
reply_delta {draftId, text} Opens a bubble for the character keyed by conversationId and draftId on the first delta; appends text on every one.
visible_reply {…, draftId} Replaces the bubble keyed draftId with the message keyed messageId, text from the event. No open bubble with that id: shows the message, as always.
reply_withdrawn {draftId} Removes the bubble.
ready Replaces every open draft with the ones the snapshot carries, under their conversations: what a tab that never left would hold. The truth about the thread stays on the newest history page.
resumed Nothing: the deltas that follow continue the drafts on screen.

Draft ids are round.reply, unique within the turn; a conversation runs one turn at a time, so a surface keys drafts by conversation. The committed text is the draft after the runtime's normalization (line endings, trim), which is why the commit replaces the draft rather than confirming it. Only the reply is ever drafted: what a model writes to itself beside a tool call is never on the stream. Pacing is each surface's own: a page renders every delta, a connector edits its message on a timer.

What a client never has to notice

The daemon keeps the hard parts on its side, once, so every surface stays small. A character's automatic recovery after a fatal turn lets its threads go; a delivery on a conversation the runtime let go of holds it again before running, so a client keeps its conversation id through the episode. A delivery on a conversation this run of the daemon has not opened — a tab that reconnected after a restart keeps its id — is routed from the store's record of the conversation, so no client reopens a thread after a restart; unknown_conversation means a conversation the home does not hold, and a record that cannot be read is refused conversation_unreadable with the reason, never mistaken for one. A reconnect gets its whole world in the ready frame, or exactly what it missed after resumed. A confirmation names the turn that raised it. And a turn whose answer was lost is safe to send again under its id.

Config

The daemon owns config: every write goes through its one control transaction, and a change reaches a running character by a reload between that character's turns.

A view is what a settings page renders. Its project02 fields, in the order a page shows them, and each plugin's fields share one shape — what this scope authored, what is in effect and which layer put it there, whether a change reloads the character; a plugin's switch says the same of itself as enabledSource. Whatever a view offers, the scope can save: every host field is authorable at the home and per character, and a plugin that belongs to a character (config.scope: "character_only") is absent from the home's view. Defaults are not resolved in: an unauthored field reads effective.source: "missing" and its defaultValueSummary names what applies. The global scope resolves the home's document alone; a character's scope resolves the merged view, that character's own values over the home's. A document that does not load is refused with the diagnostic, never rendered as blank fields; a character switched off is still viewed, and its enabled field is the way back on. The home is not a field: it is where the daemon runs, and health names it.

A change names one operation — set or unset on project02.<field>, or section_enabled, section_field_set, section_field_unset on a section named by its namespace and id — and carries the fingerprint the view handed out. The daemon verifies it under the file locks, so a concurrent edit from another page is refused with conflict: the page re-reads and the person saves again. The fingerprint hashes a secret's presence, never its value, so two pages replacing the same secret at once both succeed and the later value stands. A secret is sent as its value and kept with the scope's document; every view shows only that it is set, and a home write naming a character's own plugin is refused as invalid. A write the daemon cannot make — a file another writer holds for longer than it will wait, an unwritable home — is failed with the reason.

applied means the bytes are on disk. What the change does to the roster arrives as health_changed at once, and what it does to running characters as state_changed: the daemon reconciles behind the answer, and a ready character whose assembly would now differ — its effective config, its plugin values including secrets, its package version — publishes reloading, finishes the turn in flight, assembles afresh, and publishes ready. A global change a character overrides costs it nothing. A reload that cannot assemble lands in failed with the diagnostic, and the next change or start retries it.

Storage failures are outcomes

A read-only store, a busy lease, a damaged segment: the daemon answers {"status": "failed", "code": <storage code>, "message"} with a 200. A non-technical user is told what broke and what to do next; a 500 is reserved for a bug.
