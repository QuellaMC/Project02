Project02 Gateway API

The daemon, the binary's project02 serve, or pnpm serve in a checkout, which builds the page and the binary first, holds every character runtime behind one gateway and speaks HTTP plus server-sent events on a loopback port. Every surface — the web page, a messaging connector — is a client of this API and nothing else, so what one surface sends, every surface sees. The contract's types are generated from the Rust types the socket carries, crates/p02-wire, into packages/wire/src/contract/generated/, as TypeScript declarations and as a JSON Schema; this page is the wire.

The model proposes; the daemon commits. A client submits a message and reads outcomes and events. It never holds a runtime, a store, or a lease.

Finding the daemon

serve claims its home — one daemon per home, held as a lease in the home's lock directory for the daemon's lifetime — binds 127.0.0.1 on the home's port, and prints the one address it has the moment the socket is bound: the line a client reads, and the address a person opens. The roster comes up on the stream after it, so a character can still be starting when the address is out. 

PROJECT02_GATEWAY=http://127.0.0.1:<port>/#token=<token>

A home is the daemon's own store, at storage version 15. A home an older build wrote is read as it stands; one a newer Project02 wrote is refused, and serve says so.

The same address is kept beside the config, in <home>/daemon.json at mode 0600, written by the daemon that holds the lease and by nothing else: 

{
  "protocolVersion": 13,
  "token": "…",
  "port": 41925,
  "running": {"pid": 12345, "startedAt": "2026-09-24T10:14:07.311Z"}
}

The token and the port belong to the home, not to the run: a restart answers on the same address, so an open tab reconnects on its own and a bookmark keeps working. The token travels in the URL fragment, so it never reaches a server log or a referrer; the same address, opened in a browser, is the web page, served from the daemon's root, and the page takes the token from the fragment. A first run takes whatever free port the system hands it and records it: the address is read from the printed line or the record, never known in advance. A later run whose recorded port another program has taken since takes a free one, says so on stdout before the address, and records the new one — open tabs and bookmarks then need the new address, which nothing can tell them. running is removed by a clean stop and left behind by a crash: a reader never trusts it without asking the address, and the lease, not the record, is what says a daemon is alive. A record that cannot be read is replaced, with a new token.

The desktop app runs this same daemon inside its own process, through the binary's library, and reads this very line from the daemon's console to open its window on the address; a developer's serve already holding the home is the daemon the window opens on, as a second serve is handed the address today. The home is then the person's data folder (%APPDATA%\Project02, ~/Library/Application Support/Project02, ~/.local/share/project02), the same for every version of the app, and what the daemon would have printed goes to daemon.log in the app's log folder. Installing Project02 says how a person gets the app and opens it the first time.

A second serve on the same home does not start a second daemon. It reads the record and asks the address for /api/health: when the daemon answers as this home's, it prints Already running on this home (pid …) and the same address line, and exits 0 — which is also how anyone gets the address of a daemon that has been running since yesterday. A holder that does not answer — it answers 503 because it is stopping, its socket has already closed ahead of its lease, it has taken the lease but not yet bound its socket, or a crash's record names a port nobody listens on — is given up to thirty seconds: every half second the lease is tried and the address asked again, so a stop-then-start takes the home over on the same address and a start-twice hands the address back; when the wait is up, it says so and exits 1. Ctrl-C ends the wait at once.

A connector's process finds the daemon by the same record, in the home it serves.

Stopping

Ctrl-C, SIGTERM, or SIGHUP — a closed terminal — is a stop: the daemon prints Stopping; finishing what is in flight, requests the stop at once (a boot still under way is joined, and its late ready suppressed), finishes the turn each character has in flight, the lines behind it waiting in her inbox for her next start, ends each stream once every frame queued for it is written, closes the socket and gives each exchange still in flight two seconds to finish, then rewrites the record without running and releases the lease. A client that does not take a frame within two seconds is dropped, at a stop as at any other time. A second signal of any kind ends the process at once; the lease left behind is the next start's to reclaim. On Windows, the console window's close is a SIGHUP followed by a kill about ten seconds later.

In the desktop app the stop is the same order on a token the app cancels rather than a signal: Quit, from the tray, from a Mac's application menu or Cmd-Q, first stops the Telegram connector the app runs beside the daemon, then the daemon, each given its grace (five and twenty seconds), and only then lets the app go; the Dock's Quit, a logout or a shutdown run the same order for the seconds the system waits, and past them the process ends as a crash does, which the next start recovers from as from any other.

The four wire rules

Rule What it means on the wire
Status codes describe the transport A domain outcome — a refused open, a rejected turn, a storage failure — is a 200 whose body says status first. A non-200 means the request itself did not get through, and the body is always the one envelope {"error": {"code", "message"}}.
The stream is a hint; the verbs are the truth Every frame carries an id, and the daemon keeps a tail of the stream — up to a megabyte of frames — for a client that returns with Last-Event-ID: it opens with resumed and exactly the frames it missed, in order, then reads on. Any other stream — no id, an id from another run of the daemon, one before the tail — opens with a ready frame that carries the daemon's snapshot: health, the confirmations and pairing requests still waiting, and the turns running with their drafts so far, taken in one breath with the stream's registration, so every later frame moves on from exactly that state. A client installs the snapshot and reads on; what it wants of a conversation's history it reads as one page, deduplicated by message id. The log on disk stays the truth.
One way in Loopback only: the daemon binds 127.0.0.1. Authorization: Bearer <token>, compared in constant time. The Host hostname must be 127.0.0.1 or localhost; an Origin, when present, must be http:// plus that host. No CORS headers, no cookie, no query token. One events stream per tab.
Every submission has an identity clientMessageId is required on a turn. A repeat with the same (conversationId, clientMessageId) while the line waits in her inbox or runs is answered already_queued; once a turn took it, in this run of the daemon or an earlier one, on any segment of the conversation, it is refused as duplicate_submission, naming the message it became. That is what lets a client whose answer was lost send the line again under the same id, at once or after the daemon came back, without saying it twice; history returns the id too, for a surface that wants to know whether a line landed.

Transport status codes

Status error.code When

Every /api/* response carries Cache-Control: no-store.

A turn

POST /api/turns
Authorization: Bearer <token>
Content-Type: application/json

{
  "conversationId": "conv_…",
  "text": "hello there",
  "source": "web",
  "clientMessageId": "8b1f…"
}

source is the client's stamp on the message — web, telegram:<bot> — naming the kind of surface a line came from, for rendering. It is never a permission input, and never what a surface tells its own lines by: every browser tab stamps web, so a line is its sender's by its clientMessageId alone. Both stamps match ^[A-Za-z0-9][A-Za-z0-9:._-]{0,63}$, are persisted on the user's commit record, and come back in history. A stamp that fails the pattern never reaches a turn: the body is answered 400 invalid_request.

A character also has turns of her own, while she is ready: her heartbeat gives her a moment every so often while the person is quiet, as her own settings say, and a ring on her phone that comes due, an alarm or a timer she set, gives her one that tells her what rang. Such a turn begins from no line, so it carries neither stamp: turn_running says it as it begins, with no drafts, then as it changes, and its turn_completed ends it. Most moments end with nothing on the stream between the two; a message she sends is a visible_reply of that turn. A confirmation raised in one has no turn.

The event stream

GET /api/events answers text/event-stream. Frames are id: <run>-<seq>, event: <kind> and one data: line of JSON — the id is a random id of this run of the daemon and a count from one; a comment : ping arrives every 15 seconds so an idle connection survives client timeouts. A client that does not take a frame within two seconds is dropped; the daemon never buffers for a client that is gone, and never judges one by how many frames a burst left waiting. A client that returns sends the id of the last frame it applied as Last-Event-ID; a resumed frame carries no id, so the id it holds stands.

Event Carries
ready The protocol version and the daemon's snapshot at that instant: health (the roster, each character's state and last maintenance failure, the connectors on the stream and their bots), confirmations and pairings still waiting, and turns — each turn in progress, named by its conversationId and, when a line began it, the line's source and clientMessageId, with its character and its open drafts' text so far. A client installs it on every one it sees.
resumed The first frame of a stream the daemon could catch up instead: nothing to install, and what follows is exactly what the client missed, in order, then the live stream.
turn_progress A turn's progress: both committed roles — user_message (with source and clientMessageId) and visible_reply, which names the draftId it replaces — and its rounds' tool calls: tool_calls_requested with the toolNames a round called, then a tool_call_completed for each call as it came back, accepted or rejected, with its toolName and the pluginId of the plugin that provides the tool (undeclared.<tool> for one the turn did not offer).
turn_running A turn as it runs now, whenever that changes, from the commit of its line, or from its beginning for a turn of her own, until its completion: its conversationId, the source and clientMessageId of the line that began it, both absent for a turn of her own, its character, and her drafts so far, each its whole text — a reply the model is still writing, the one thing the stream says before the log. A client replaces its copy of the turn with each.
turn_completed The turn's terminal status, with the reason and message when it was not completed, stamped with the submission's source and clientMessageId so every surface knows whose turn ended — even one that committed nothing. committed says whether the turn put that line in the log: a surface holding the line hands back one that was not, and leaves one that was to the thread. Nothing else answers it, since the log is read in pages and a busy turn can put a hundred messages between a line and now. A turn of her own carries neither stamp and says committed: true: nothing of the person's waits on it, and nobody asked for anything, so a surface says nothing of how it ended.
confirmation_requested A tool asking for approval: id, request, deadline, and the turn that raised it (its conversationId, source, clientMessageId). A contact-shaped surface — a bot in one chat — answers for its own turns and leaves the rest to the surface that sent them; a roster-shaped surface, where the person sees every character, shows them all and names the surface that raised one. The person is the same on every surface, and the daemon settles a confirmation once for all of them. The same shape the pending list returns.
confirmation_settled The decision: approved, denied, or cancelled — and, cancelled, why: expired (the deadline passed, whether the daemon's timer fired or an answer came too late) or stopped (the character stopped or restarted with the request parked).
pairing_requested An account a connector does not know, waiting for the owner's answer: connectorId, the six-digit code, the subject (id, label), the source it wrote to, requestedAt, and expiresAt, an hour on. The same shape the pairing list returns; a surface adds a request by its code, once.
pairing_settled How a request ended: its connectorId, code and subject, and the decision — approved, denied, or expired (the hour passed, whether the daemon's timer fired or an answer came too late). An approval follows the health_changed its write caused.
state_changed A character's runtime state, with a message when something went wrong or when she needs a model. A character built afresh on changed config says ready again, or needs_model when it no longer gives her one.
health_changed The daemon's whole state, read again the moment a config change or a character's package landed and before the pass that acts on it, or the moment a connector's process came onto the stream, left it, or said its bots stand otherwise than the daemon held: the roster as config now says it, the connectors on the stream with their bots, the accounts her phone knows with whether each one's key is set, and the config and package problems as they stand, the shape GET /api/health returns. Every surface hears it, not only the one that wrote, and one showing config reads its view again on it, so two windows on one screen stay in step; what the pass then does to each character follows as state_changed.
maintenance_failed A segment rotation that failed after a completed turn; health shows the same at.
phone_changed Her characterId: her phone is to be read again. Described below.

A connector needs no event of its own for config; it keeps its read of GET /api/connectors/:id/config current by one rule:

  • Read it on every ready: that is the first read, taken after the subscription so no change can fall between them, and the read after any outage the daemon could not replay.
  • Read it again on every health_changed.
  • Apply only the answer to the newest read, so an older answer never overwrites a newer one.
  • Retry a read that failed, with a backoff, instead of waiting for the next change.
  • A stream the daemon resumed replayed what was missed, health_changed included, so resumed needs no read.

A connector

A connector lets nobody in by itself: an account it does not know is the owner's to admit, and the owner's yes reaches the connector as its own config.

A connector's process opens its stream as GET /api/events?connector=<id>, and the daemon counts it on the stream from before the first frame — so the connector's own ready already shows it — until the stream ends. Health's connectors says, for each built-in connector, whether a process of it is on the stream; health_changed goes out when its first stream opens and when its last one ends, and the settings page says on the connector's block whether it is running. The connector keeps its config by the rule above.

A connector tells the daemon how its bots stand: POST /api/connectors/:id/bots with its whole table every time, {bots: […]}, at most 256 entries. An entry is one bot: its target, {scope: "global"} for the home's own bot and {scope: "character", characterId} for a character's; its username once its service has said who it is, 1 to 32 ASCII letters, digits or underscores, without the @; and its state — on (it is receiving messages), refused (the service refused its token), unreachable (the service cannot be reached), conflict (another program is polling its token) or webhook (its token is set to a webhook). A bot whose state is not known yet is left out, and a token is no part of an entry. A table that breaks a rule is a 400. The daemon holds the table in place of the one before, shows it as the connector's bots in health, and sends health_changed when it differs from the one it held. It lets the table go when the connector's last stream ends, and answers a table sent while no stream of the connector is open refused (not_connected), so health never shows the bots of a connector that is off the stream. A connector therefore sends its table after the first frame of every stream it opens, the daemon having counted it by then, and again whenever the table changes.

For an account it does not know, the connector asks: POST /api/connectors/:id/pairing with the subject — its own id for the account, one token by the pattern the stamps match, and the label the owner sees, one line of at most 128 characters with no space at either end — and the source: where the account wrote, as the stamp its lines will carry once it is paired, telegram:<bot username> for Telegram. A subject that breaks the rule is a 400. The answer is paired when the home's allowlist already holds the account, or pending with the request: the one already waiting for that account, so asking again is safe, which keeps the source the account first wrote to, or a new one under a six-digit code unique among those waiting, good for one hour, until expiresAt. The connector tells the person asking the code and the hour, and lets in exactly the accounts the allowlist in its own config entry holds — the field its declaration names as pairing, pairedUsers for telegram.

The owner answers by the code, on any surface. A denial removes the request. An approval is the daemon's own config write, through the same path as any change: the account, named by its label, goes into that field in the home's document — which every character that sets none of its own inherits — under the current fingerprint. A connector therefore hears it as health_changed, on which its next read finds the account, and then as pairing_settled. An answer at or past the deadline is answered expired, the daemon being the judge of the deadline as for a confirmation, and an hour with no answer settles the request as expired on the stream. While an approval's write runs the request keeps its place, so asking for the same account again gets the same request, and a second answer meanwhile is unknown; an approval that could not be written, another write having moved the document first among the reasons, puts the request back on the clock and is answered failed with the reason. A request lives as long as the daemon's run: the ready after a restart carries none, and asking again makes a new one.

The web page asks each request waiting on a card in the one spot it asks everything in, above the message box, among the confirmations — who asks to pair on which connector, the bot they wrote to, the code and the time left, with Allow and Don't Allow — installed from every ready, added from pairing_requested once per code, and ended by pairing_settled, the card saying how for a moment. Answering a card, the page leaves a settlement to the frame; an expiry is said once, whichever news of it reaches the page first; a request the daemon no longer knows is said to be no longer waiting; and an approval that could not be written leaves the card, with the reason.

Telegram is the first connector, run as project02 telegram. A line it carries is stamped telegram:<bot username>, with <bot id>.<chat id>.<message id> as its clientMessageId, so a message Telegram hands on again is the line it was. It hands each line to her inbox and asks Telegram past the message only once the line is queued. It answers private chats only, keeps nothing between runs — each starts from the record, its ready and its config read — and edits a draft's message in each chat at most every 1.5 seconds, to her turn as the daemon last said it. crates/p02-telegram/README.md has the rest.

Her phone

Her phone is hers: a client reads it and looks around it, and nothing it reads changes anything of hers.

GET /api/characters/:id/phone reads her phone from her data, whether she runs or not. The sync rule

Every committed message rides the stream once it reached disk — the user's and the character's alike — and surfaces render from the stream. A turn's HTTP answer is for status only.

Because both roles are emitted from one post-persist seam, the stream and history never disagree: a reply whose write failed is a failed turn, never a message shown that history lacks. A message typed on the phone appears in every open browser tab at once. A surface tells the lines it is still holding apart by clientMessageId, which is its own: source names the kind of surface, and two browser tabs share it, so a tab that went by source alone would take another tab's lines for its own.

Streaming replies

The reply reaches every surface as the model writes it, as a draft: a draft is not a message, the daemon says what she is writing, and a client works nothing out.

While a turn runs, every change of it — her line committed, a draft that grows, a draft committed or withdrawn — is told as the turn_running frame of the whole turn: each open draft under its draftId, with all its text so far. A draft has no message id, is never persisted, and no surface treats it as history. It ends in one of two ways: the visible_reply that names its draftId comes first, then the turn without that draft; or the turn without it comes alone, a draft withdrawn — a round the parser refused, a reply whose write failed. The daemon closes every draft a round opened before the round moves on, so none is open at turn_completed.

Draft ids are round.reply, unique within the turn; a conversation runs one turn at a time. The committed text is the draft after the runtime's normalization (line endings, trim), which is why the commit replaces the draft rather than confirming it. Only the reply is ever drafted: what a model writes to itself beside a tool call is never on the stream. Pacing is each surface's own: a page renders every frame, a connector edits its message on a timer to the turn as it was last told.

What a client never has to notice

The daemon keeps the hard parts on its side, once, so every surface stays small. A character's automatic recovery after a fatal turn lets its threads go; a delivery on a conversation the runtime let go of holds it again before running, so a client keeps its conversation id through the episode. A delivery on a conversation this run of the daemon has not opened — a tab that reconnected after a restart keeps its id — is routed from the store's record of the conversation, so no client reopens a thread after a restart; unknown_conversation means a conversation the home does not hold or whose record cannot be read, the message saying which. A reconnect gets its whole world in the ready frame, or exactly what it missed after resumed. A confirmation names the turn that raised it. And a line whose answer was lost is safe to send again under its id.

Config

The daemon owns config: every write goes through its one control transaction, and a running character runs on a change from her next request to her model.

A view is what a settings page renders. Its project02 fields, in the order a page shows them, and each plugin's fields share one shape — what this scope authored, what is in effect and which layer put it there, with the label, placeholder and choices its declaration gives it; a plugin's switch says the same of itself as enabledSource. A section also carries its layout, the cards to draw its fields in; a plugin's carries its page too, how to draw its row, and the access its manifest requests (Config System). Each section carries its setup, switched on or off: ready, or not with a message saying what to fill in, judged by the code that builds the plugin; a connector's is always ready. The view's own model is the same shape for whether its scope's host values give a character an AI model, as her start judges it. Whatever a view offers, the scope can save: a host field is authorable at the home and per character unless its scope keeps it to one, as a character's own enabled is hers alone, a plugin or field that belongs to a character ("character_only") is absent from the home's view, and one that belongs to the home ("global_only") from a character's. A connector's settings, under connectors, are a section like a plugin's, and what is said here of a plugin holds for them. The global scope resolves the home's document alone; a character's scope resolves the merged view, that character's own values over the home's. Either way, a value is taken only from a layer its plugin's or field's scope permits: one found elsewhere never takes effect, and the view's diagnostics carry it as the warning runtime_config_authored_outside_scope at its path. A field no such layer authored carries its declared default as its effective value, effective.source: "default", and reads "missing" when it has none. A document that does not load is refused with the diagnostic, never rendered as blank fields; a character switched off is still viewed, and its enabled field is the way back on. The home is not a field: it is where the daemon runs, and health names it.

A change names one operation — set or unset on project02.<field>, or section_enabled, section_field_set, section_field_unset on a section named by its namespace and id — and carries the fingerprint the view handed out. The daemon verifies it under the file locks, so a concurrent edit from another page is refused with conflict: the page re-reads and the person saves again. The fingerprint hashes a secret's presence, never its value, so two pages replacing the same secret at once both succeed and the later value stands. A secret is sent as its value and kept with the scope's document; every view shows only that it is set, and a write naming what the scope's view leaves out is refused as invalid. A write the daemon cannot make — a file another writer holds for longer than it will wait, an unwritable home — is failed with the reason.

applied means the bytes are on disk. What the change does to the roster arrives as health_changed at once, and the daemon reconciles behind the answer: a character it switches on starts, and one it switches off stops once her reply in flight ends. Every other change a running character meets at once, or, while her reply is in flight, before its next request to her model: when what she would be built from differs — her effective config, her plugin values including secrets — she assembles afresh, on the same conversation, and publishes ready. A global change a character overrides costs it nothing, and so does a change to a connector's section, from which no character is built. A plugin switched on before its setup is finished is left out: she runs without it, her summary's diagnostic says so, and the change that finishes it builds her with it. Config that gives her no AI model leaves her needs_model, saying what to choose: her thread opens, the lines sent to her wait in her inbox, nothing tries her again by itself, and the change that gives her one starts her on them. Other config she cannot assemble from lands her in failed with the diagnostic, the line refused or the reply in flight failed, and the next change or start retries her.

Storage failures are outcomes

A read-only store, a busy lease, a missing segment: the daemon answers {"status": "failed", "code": <storage code>, "message"} with a 200. A non-technical user is told what broke and what to do next; a 500 is reserved for a bug.
