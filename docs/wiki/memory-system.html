Project02 Memory System

A character has three ways to know something that happened before this turn, and each lives in its own layer with its own trust story: a tiny curated memory that is always in the prompt, session history it can search on demand, and at most one external retrieval-driven provider running alongside them.

The model curates and proposes; the runtime validates, caps, and commits. No layer lets raw model output or foreign plugin content write the trusted prompt directly.

Curated memory

The character-memory package keeps two capped stores per character: character notes and a user profile. Whatever the store holds is injected every session as a Curated memory block with capacity headers, so the character never has to search for what it must always know; until the character writes its first entry the store is empty and no block appears at all. The snapshot is frozen per launch: writes land on disk immediately and reach the prompt at the next launch, keeping the prompt prefix byte-stable for provider caching.

The model maintains the store through one atomic tool, memory.update: add appends an entry, replace and remove select exactly one existing entry by a unique old_text substring, and a batch either fully commits or fully rejects. Capacity overflows reject with usage numbers so the model compresses or prunes instead of silently losing entries. There is no read tool and no automatic extraction.

Session search

Everything said is recorded and indexed — past sessions and the parts of the current one that have scrolled out of the model's recent-message window alike; the character reads back windows of those transcripts with sessions.search and sessions.read. Each tool bounds what it returns, so a long message comes back shortened rather than whole; the tool contracts carry the current limits. Curated memory holds what must always be known; session search recovers what was merely said. A fact worth keeping gets promoted by the model from a transcript into memory.update.

External providers

Retrieval-driven long-term memory rides the memory_provider plugin kind: per-turn recall items enter the untrusted plugin frame (source-referenced, bounded, budget-capped), each committed turn is handed to the provider to do with as its backend decides — mem0 asks its backend to extract facts from it — and a provider exposes whichever namespaced tools its backend supports. Providers are disabled by default; enable one and, when several are enabled, select it with pnpm runtime-config default-memory-provider <pluginId>. Activation keeps at most one selected, so by default an external provider runs alongside curated memory rather than replacing it; an operator who explicitly disables character-memory can run a provider on its own.

Package Backend Notes
mem0 Mem0 platform API or a self-hosted Mem0 server REST via fetch; secret key from MEM0_API_KEY; capture lets the backend extract. mem0.add submits the text the model supplies, bounded like every provider memory item; a self-hosted server or the embedded engine answers with the stored row, while the hosted platform answers with a receipt and stores asynchronously, which the tool reports as queued rather than saved.

Trust model

Curated memory renders in a trusted prompt frame because the runtime owns every step: entries are validated and capped at write time, sections are typed and screened at render time, and the curated_context access that feeds the frame is granted only to bundled packages by catalog provenance — a manifest flag alone never earns it. Automatic per-turn recall from an external provider stays in the untrusted plugin frame under the shared token budget, and recall items without source references are dropped rather than shown. A provider's own search tool answers where every tool answers, in a tool result, which that budget does not cover.

Installing a character package is the trust decision: the package may fill any setting the operator has not set, so its character works right after install. What the operator has set always wins — on first install and on every package update. The model is the fenced writer: it may propose changes only to agentMutable fields, and credentials are never among them. Credentials prefer env files; each character's own file, set with --character, merges over the shared one, so two characters can hold different accounts for the same memory service while a shared account covers the rest.
