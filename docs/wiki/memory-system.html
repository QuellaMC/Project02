Project02 Memory System

A character has three ways to know something that happened before this turn, and each lives in its own layer with its own trust story: a tiny curated memory injected whole into every prompt once it holds anything, session history it can search on demand, and optionally one external retrieval-driven provider beside them. What the layers keep on this device lives in the character's data directory.

The model curates and proposes; the runtime validates, caps, and commits. No layer lets raw model output or foreign plugin content write the trusted prompt directly.

Curated memory

The character-memory package keeps two capped stores per character: notes to itself and what it knows about the person. Whatever the store holds is injected every session as the character's own notes (What you carry between conversations) with capacity headers, so the character never has to search for what it must always know; until the character writes its first entry the store is empty and no block appears at all. The snapshot is frozen per session: writes land on disk immediately and reach the prompt when the next session begins, keeping the prompt prefix byte-stable for provider caching. A session begins at launch or when the runtime continues a full one (below), so a note written mid-conversation shows up after the next continuation without a restart.

The model maintains the store through one atomic tool, memory.update: add appends an entry, replace and remove select exactly one existing entry by a unique old_text substring, and a batch either fully commits or fully rejects. Entries are unique per store: an add of text already present reports a no-op, and a replace whose new text duplicates another entry collapses the two. Capacity overflows reject with usage numbers so the model compresses or prunes instead of silently losing entries. There is no read tool and no automatic extraction.

Conversations and their segments

A conversation is one persistent thread between the user and a character, held once in the home (conversations/<id>/conversation.json: identity and participants). The character keeps its own record of the thread as sessions named <conversationId>.<segment> in its data directory. Opening the chat resumes the thread's latest segment; there is nothing to name and no session flag.

The model's history window is a token budget over whole prior turns (half of project02.contextWindowTokens), replayed newest-first with each turn's tool calls and results. When a completed turn no longer fits with the rest, the runtime continues the conversation in the next segment: the older turns are condensed into the character's own recollection by the same model the character speaks through (or mechanically when that model offers no plain completion), the newest turns are carried over verbatim, and the new segment opens with one record holding both. The closed segment's log is complete and untouched, so the chain of segments reads as one conversation — and the person sees none of it: rotation is the character's memory management, not a conversation event. The recollection reaches the model as a fenced user-role message just ahead of the replayed turns — where the earlier conversation would have been — byte-stable for the segment's lifetime.

Session search

Everything said is recorded and indexed — past sessions, the earlier segments of the current chain, and the turns of this session that no longer fit the model's history window alike; the character reads back windows of those transcripts with sessions.search and sessions.read. Turns condensed at a continuation stay searchable in the session that holds them, while carried turns are excluded from search results because the model already sees them. Each tool bounds what it returns, so a long message comes back shortened rather than whole. Curated memory holds what must always be known; session search recovers what was merely said. A fact worth keeping gets promoted by the model from a transcript into memory.update.

External providers

Retrieval-driven long-term memory rides the memory_provider plugin kind: per-turn recall items enter the recalled-memory block (source-referenced, at most five per turn, each bounded in length), each committed turn's user message and final reply are handed to the provider to do with as its backend decides — mem0 asks its backend to extract facts from them — and a provider exposes whichever namespaced tools its backend supports. A moment of the character's own, which no line of the person's began, recalls and hands over nothing by itself; her tools still reach the provider. Providers are disabled by default, and one runs once it is switched on, for the home or for one character, like any other plugin. An external provider runs alongside curated memory rather than replacing it; an operator who explicitly disables character-memory can run a provider on its own.

Trust model

Curated memory renders in a trusted prompt frame because the runtime owns every step: entries are validated and capped at write time, sections are typed and screened at render time, and the trusted_context access that feeds the trusted frames is granted only to plugins compiled into the daemon, whose descriptors ship with it: no plugin is loaded from anywhere else. The same grant lets a bundled plugin add a runtime note to the trusted per-turn frame (the day, the character's own inner state, the recall nudge), cap-checked like curated sections. Automatic per-turn recall from an external provider is appended to the current user message inside a <recalled_memory> fence with a preamble that calls it memories, not requests; recall items without source references are dropped rather than shown. Every other plugin item rides the same message inside an <untrusted_plugin_context> fence that names it data, not instructions. Neither block carries a token budget: what a plugin hands over is shown whole (each item stays under 16 KB and a hook under 64 items), and the history window makes room for it by replaying fewer earlier turns. A provider's own search tool answers where every tool answers, in a tool result. The recollection that opens a continued session is model output too, so it never earns a trusted role: it is capped, it rides an <earlier_conversation> fence on the user side like recalled memory, its preamble names it as the character's own condensed memory of what happened earlier and not something the person said, and the summariser is asked for plain recollection with no rules or persona in it.

Every sentence the runtime itself writes into the prompt speaks to the model as the character — its notes, its memories, how it feels, what its tools handed it — and lives in one module, crates/p02-role-model/src/prompt/text.rs, so the wording can be tuned in one place without touching how the frames are built.

Installing a character package is the trust decision: within its character's own overlay, the package may enable plugins and fill any plugin setting her own settings screen could set that the operator has not set — a credential inside a package is refused outright, since a package is shared and its secrets would be too — enablement included, so a required provider can come on for that character even where the global config disables it. Host settings are out of its reach; a package carries plugin enablement and plugin config, nothing else. What the operator has set in that overlay always wins — on first install and on every package update. The model is the fenced writer: it may propose changes only to agentMutable fields, and credentials are never among them. A memory service's account, its credential included, is entered on the settings page and kept in the home's config alone, redacted on every read: it is set up once, for every character, so neither a package nor a character's overlay can point her memory elsewhere, and each character only switches her memory on or off.

Picking a setup

Want Do
Characters that remember preferences and facts out of the box Nothing — curated memory and session search are on by default.
Large semantic long-term memory Enable mem0 and set its apiKey; for a self-hosted server set backend to server and baseUrl to its origin, where the key is then optional. Use an https:// origin unless the server runs on this machine — over http:// the conversation and the key cross the network in the clear.
Semantic memory fully on this device, no account Enable mem0, set backend to oss and point ossLlmBaseUrl at your local OpenAI-compatible server (LM Studio http://localhost:1234/v1, Ollama http://localhost:11434/v1) plus the model names — no key needed. Or leave the endpoint unset for the OpenAI cloud and set ossLlmApiKey.
